01 - System Context

What it shows

The highest-level view: who talks to the platform, and what the platform talks to in the outside world. Everything inside the platform is one black box here.

Nodes

  • Operator / Developer — the human. Does not submit tasks. Observes running tasks, debugs failures, and can intervene in a task in progress (correct the agent, add context, cancel, re-run with changes).
  • Automation (external system: CI, scheduler, cron, webhook) — what actually submits tasks to the platform over the API.
  • FlowAI Platform — the system itself.
  • LLM Providers — Anthropic, OpenAI, OSS via vLLM (external).
  • Container Registry — OCI registry holding pre-built agent images (external).
  • Identity Provider — future OAuth/SSO for multi-tenant (external, not wired in MVP).

Relationships

  • Automation → Platform over HTTPS: REST POST to /tasks. This is the primary submission path.
  • Operator → Platform over HTTPS / WebSocket: WebSocket to stream live events for a task they are watching; REST to intervene (cancel, re-run, inject messages).
  • Platform → LLM Providers over HTTPS: prompts, tool calls, completions.
  • Platform → Container Registry over OCI / HTTPS: pulls pre-built agent images per task.
  • Operator ↔ Identity Provider over OAuth; Platform ↔ IdP over OIDC (post-MVP).

Key takeaway

The platform is a broker. Two kinds of actors talk to it: automation submits, the human observes and intervenes. The platform owns scheduling, isolation, secrets, observability, and cost. It does not own the LLM or the agent framework — those live outside, and the platform coordinates with them.

02 - Task flow (runtime slice)

What it shows

The services that are touched when an external event (Jira task, GitLab issue, webhook, ...) becomes a running agent task and completes. External systems (LLM providers, Container Registry) and the operator surface are out of scope — see 01 (System Context) and 03 (Operator Surface).

Architecture in three layers

The runtime is split into three layers:

  1. Automation layer — per-source workers (Webhook Handler, Jira Poller, GitLab Handler) that turn external events into normalized messages and publish them to per-source queues.
  2. Core — the Control Plane consumes source queues, normalizes and routes by operator-defined rules, persists, assembles scope, enqueues to the correct executor queue. Per-executor queues, the State Store, the Secret Service, and the task pub/sub live here.
  3. Executor fleet — any number of independently-registered executors (local Docker, k8s cluster A, k8s cluster B, ...). Each executor pulls only from its own queue.

Services involved

  • Webhook Handler — exposes an HTTP endpoint, accepts arbitrary webhooks, publishes normalized events.
  • Jira Poller — polls Jira for new tasks, publishes them.
  • GitLab Handler — accepts GitLab webhooks (issues, comments, MRs), publishes them.
  • Control Plane — consumes source queues, normalizes, routes by operator rules, persists state, signs the scope, enqueues to the matching executor queue, fans out live events to UI.
  • Source Queues — one queue per source (q:webhook, q:jira, q:gl-issue, q:gl-comment, ...).
  • Executor Queues — one queue per registered executor (q:exec-A, q:exec-B, q:exec-local, ...).
  • State Store — tasks, projects, audit log, routing rules, registered executors, registered automations.
  • Secret Service — get-by-scope endpoint; returns plaintext for a signed scope. The Control Plane does not call it directly — it only assembles scopes from secret_ids.
  • Executor (any) — owns the agent container lifecycle: spawn, inject secrets, observe stdout, stop on control. Pulls only from its own queue. Publishes events. Subscribes to control.
  • Agent Container — per-task black box. Runs the initial instructions. Knows nothing about the platform.

Relationships

  • External source → per-source Worker: HTTPS webhook or polled API.
  • Per-source Worker → Source Queues: publishes normalized event.
  • Control Plane ← Source Queues: consumes events.
  • Control Plane → State Store: reads routing rules and registered executors; persists tasks and audit log.
  • Control Plane → Executor Queues: enqueues the normalized task to the queue of the executor chosen by the routing rule.
  • Executor ← Executor Queue: pulls.
  • Executor → Secret Service: get-by-scope, gets plaintext map.
  • Executor → Agent Container: spawn, inject secrets, observe stdout, stop on control.
  • Executor ↔ pub/sub (the executor queue doubles as the event bus): publishes task events; subscribes to control events (cancel / intervene) for its own tasks.

Key takeaway

No scheduler. Routing is done in the Control Plane from operator-defined rules ("automation X → executor Y"). Each registered executor pulls only from its own queue. This gives the operator full control over what runs where, with no central scheduler to maintain. The Control Plane and the executors never talk to each other directly after the task lands in an executor queue — they communicate only through the pub/sub (the same queue doubles as event bus and control bus).

03 - Operator surface (user-facing slice)

What it shows

The services that a human touches. What the operator uses to manage secrets, observe tasks, intervene in running tasks, and — crucially — register automations, executors, and the routing rules that decide which executor runs which task. The per-source workers, the executors themselves, the LLM providers, and the Container Registry are out of scope — they are on the Task Flow diagram (02).

What the operator configures in the Web UI

  • Automations — registers per-source integrations: webhook URLs, Jira connection (project, auth), GitLab connection (project, event filters).
  • Executors — registers executor instances: local Docker, k8s cluster A, k8s cluster B. Each with its own credentials and capabilities.
  • Routing rules — for each automation, picks the executor that should run its tasks. Example: Jira tasks from project X → executor A (k8s cluster A).
  • Secrets — CRUD on the Secret Service.
  • Task state — read; observe live events; intervene (cancel, inject message, rerun).

Services involved

  • Web UI — the single frontend. Every operator action goes through it.
  • Control Plane API — the backend behind the UI. Persists automations, executors, routing rules, tasks, audit log. Proxies secret CRUD. Routes source events to executor queues. Signs scopes. Fans out live events.
  • State Store — what the UI reads and writes (automations, executors, routing rules, task state, audit log).
  • Task pub/sub — what the Control Plane subscribes to for live event streaming to the UI.
  • Secret Service — what the UI calls directly for CRUD on secrets.

Relationships

  • Operator → Web UI: all actions — automations, executors, routing rules, secret CRUD, observation, intervention — over HTTPS / WebSocket.
  • Web UI → Control Plane API: automations, executors, routing rules CRUD; task state reads; intervention commands; secret CRUD proxy.
  • Web UI → Secret Service: direct CRUD (create, update, delete) — the UI is the only CRUD client.
  • Control Plane API → State Store: persists and reads automations, executors, routing rules, tasks, audit log.
  • Control Plane API → Task pub/sub: subscribes to task events for live UI streaming.
  • Control Plane API → Secret Service: proxies secret CRUD on behalf of the UI.

Key takeaway

The operator never talks to anything but the Web UI. The Web UI is the only CRUD client of the Secret Service. Control Plane is the only backend for the UI. The operator is the one who wires the system together: which sources, which executors, which routing. There is no other way for a human to manage secrets, watch a task, intervene, or change the routing — by design, because every other path would be a security gap.

04 - Task Lifecycle (sequence)

What it shows

The happy path of one task from "automation submits" to "task done", including how a human operator can observe and intervene while it runs.

Participants

  • Automation — external system (CI, scheduler, webhook) that submits tasks.
  • Operator (UI) — the human. Connects via WebSocket to watch; can inject messages, cancel, or rerun a task.
  • Control Plane — API service: task lifecycle, persistence, WebSocket fan-out, scope assembly. Does not talk to the Secret Service, and after the initial handoff does not talk to the Executor either — only via the Task Queue.
  • Task Queue — work queue and the pub/sub channel between control plane and executor (both directions).
  • Secret Service — separate service; its own DB. Two surfaces: CRUD (Web UI only) and get-by-scope (Executor only).
  • Scheduler — picks tasks off the queue, hands them to the executor (one-shot gRPC).
  • Executor — owns the agent container lifecycle: spawn, inject secrets, observe stdout, stop. Publishes events to the queue, subscribes to control events (cancel / intervene) for its tasks.
  • Agent Container — a per-task black box. Runs the initial instructions, talks to the LLM. Knows nothing about the platform — no API calls, no event publishing, no control channel. The executor observes its stdout and exit code.
  • LLM Provider — Anthropic / OpenAI / OSS.

Step by step

  1. Submit: Automation POSTs /tasks with prompt + tools + secret_ids.
  2. Scope & persist: Control Plane builds scope = HMAC(project, task, secret_ids, TTL), persists the task, enqueues.
  3. Observe: Operator opens a WebSocket subscription to the task id.
  4. Pick & handoff: Scheduler dequeues, hands task spec + scope to Executor (one-shot gRPC). After this, control plane and executor do not talk directly.
  5. Run: Executor pulls the image, calls POST /secrets/get-by-scope, receives the plaintext map, starts the container with secrets injected. Agent runs.
  6. Agent loop: Agent asks the LLM, executes tool calls. Its stdout is observed by the Executor, which publishes events to the queue. Control Plane fans out to the operator WebSocket.
  7. Intervene (optional): Operator asks Control Plane to cancel / intervene. Control Plane publishes a control event to the queue. Executor picks it up and forwards (or stops) the agent.
  8. Finish: Agent exits. Executor observes exit code, publishes final event. Control Plane updates state to terminal. Scope expires. Container is gone. Operator and automation both get the final outcome.

Key takeaway

Submit is automated, observation and intervention are human. Every hop is traced (OpenTelemetry). Control Plane never sees plaintext secrets — it only assembles scopes. The agent is a black box: it runs the initial instructions and does not know about the platform. Control plane and executor communicate only through the Task Queue (pub/sub, both directions) — there is no direct gRPC between them after the initial handoff. The executor owns the agent container lifecycle end-to-end.

05 - Secret Lifecycle (sequence)

What it shows

How a secret reaches the agent inside its container — through a separate Secret Service that takes two kinds of clients: the Web UI does CRUD; the Executor does get-by-scope. The Control Plane never talks to the Secret Service at all.

Participants

  • Operator — manages secrets through the Web UI only.
  • Web UI — the only CRUD client of the Secret Service.
  • Secret Service — separate service, its own DB, encrypted at rest. Two surfaces: CRUD and get-by-scope.
  • Automation — submits tasks referencing secrets by secret_id.
  • Control Plane — knows only secret_ids. Assembles a signed scope (HMAC of project, task, secret IDs, TTL). Hands the scope to the executor; never calls the Secret Service.
  • Executor — the only get-by-scope client. Calls the Secret Service with the scope token, receives a plaintext map, injects it into the container as env / tmpfs.
  • Agent Container — receives the secrets at start. Does not need to talk to the Secret Service during the run.

Step by step

  1. CRUD: Operator opens the Secrets page in the Web UI. The UI calls POST /secrets on the Secret Service with name, value, and scope (user or project). The Secret Service encrypts, persists, audit-logs, returns secret_id.
  2. Task submit: Automation calls POST /tasks on the Control Plane with secret_ids: ["a", "b"].
  3. Scope assembly: Control Plane builds scope = HMAC(project_id, task_id, secret_ids, TTL) and persists the task. The scope is opaque to everyone but the Secret Service.
  4. Spec handoff: Scheduler dequeues the task and hands task spec + scope to the Executor.
  5. Get-by-scope: Executor pulls the image, then calls POST /secrets/get-by-scope on the Secret Service with the scope. The Service validates signature, expiry, project, returns a map { "a": "...", "b": "..." }.
  6. Container start: Executor starts the container with the secrets injected (env or tmpfs).
  7. Cleanup: Task ends → container terminated → scope token expires. Plaintext is gone.

Key takeaway

Control Plane does not talk to the Secret Service. It only knows which IDs a task needs and signs a scope. The Secret Service has exactly two surfaces: CRUD (only the Web UI calls it) and get-by-scope (only the Executor calls it). The plaintext map crosses exactly one boundary: from the Secret Service to the Executor. The Executor injects it into the container, but never persists it. If the Executor is compromised, the attacker gets the plaintext for one task only, for the IDs the task requested, until the scope expires.

06 - Task State Machine

What it shows

The lifecycle of one task as a state machine. Each state is persisted to Postgres, and every transition is auditable.

States

  • Queued — task created, waiting for the scheduler.
  • Preparing — scheduler picked it, executor is pulling the image and starting the container.
  • Running — agent loop is active: prompt LLM, execute tools, repeat.
  • Succeeded — agent returned a final result.
  • Failed — pull / start error, or unhandled error during the loop, or max_steps exceeded.
  • Cancelled — user cancelled, either before start (from Queued) or gracefully during the loop.
  • Timeout — wall-clock budget exceeded.

Transitions

  • Submit puts a task into Queued.
  • Scheduler advances Queued → Preparing.
  • Container starts → Running.
  • From Running: tool_use / llm_response events keep it in Running; final result moves to Succeeded; otherwise Failed / Cancelled / Timeout.

Color code

  • Yellow — pending (waiting on the platform).
  • Blue — actively running.
  • Green — terminal success.
  • Red — terminal failure (Failed / Cancelled / Timeout).

Key takeaway

Exactly seven states. Only four of them are terminal. Every transition is recorded, so a task can be replayed in the UI event-by-event after it finishes.
