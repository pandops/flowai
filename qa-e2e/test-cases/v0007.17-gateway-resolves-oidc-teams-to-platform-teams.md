# Test case: v0007.17-gateway-resolves-oidc-teams-to-platform-teams

## Implements

`api-gateway` — `### Requirement: Gateway owns OIDC-to-canonical-team mappings`

## Intent

Happy-path and boundary test verifying deterministic Gateway-owned OIDC-team-to-platform-team resolution and persistence isolation.

## Preconditions

- Active mappings exist from `oidc-team-alpha` to `team-alpha` / `Alpha Team` and `oidc-team-beta` to `team-beta` / `Beta Team`.
- An unknown OIDC team and a duplicate `oidc-team-alpha` are available as inputs.

## Steps

1. Authenticate through OIDC with duplicate known OIDC teams and one unknown OIDC team.
2. Read `GET /auth/v1/teams` and issue working tokens for each returned team.
3. Attempt token issue for the unknown team and inspect the Gateway-to-State-Registry request observation.
4. Assert exact mapping, membership-observation, and derived-access values in the Gateway database and assert absence of OIDC/member data in State Registry as supplementary database evidence.

## Expected outcome

Gateway returns exactly one entry for each known mapping ordered by `(team_name ASC, team_id ASC)`; token issue succeeds for those entries and returns `403 team_not_accessible` for the unknown team. Unknown and duplicate OIDC teams add no entries. Exact database values place derived operator-team access only in Gateway, and State Registry receives and stores no OIDC or membership data.
