# Test case: v0007.21-gateway-database-is-isolated

## Implements

`api-gateway` — `### Requirement: Gateway isolates its persistence from State Registry`

## Intent

Deployment and security test verifying service-local persistence when both services share one PostgreSQL instance.

## Preconditions

- API Gateway and State Registry are configured with separate schemas, roles, migrations, and credentials on one PostgreSQL server.
- Both services run from their production container images.
- The OIDC fixture and authenticated administrative identities are available.

## Steps

1. Start both services against the same PostgreSQL server and wait for their public readiness endpoints.
2. Create a canonical team through the State Registry administrative API.
3. Register an OIDC mapping, authenticate an operator, and obtain the resolved team through API Gateway's supported OIDC and administrative APIs.
4. Restart both service containers without replacing the PostgreSQL server.
5. Through the State Registry administrative API, create a source system referencing the pre-restart canonical `team_id`, and repeat authenticated team resolution through API Gateway.
6. Create another canonical team and another Gateway-owned mapping after restart.

## Expected outcome

Both services become ready against one PostgreSQL server, preserve and return only their own API-visible state across restart, and continue accepting writes through their own supported APIs. Gateway-owned OIDC mapping and membership data never appears in any State Registry API representation, and neither service requires the other service's database credentials to start or operate.
