# Test case: v0002.8-environment-remains-independent

## Implements

`state-registry` — `### Requirement: State Registry remains independent from execution and identity management`.

`state-registry` — `### Requirement: State Registry uses local AES-256-GCM authenticated encryption for secret values`.

## Intent

Verify that consolidated environment ownership does not make State Registry an execution service or expose plaintext to unauthorized actors; image strings are not team-owned resources and never authorize.

## Preconditions

A `team-a` `pending` task references a same-team environment, and an eligible Executor (`scope = team`) bound to `team-a` is registered with the task's exact required tag and a single tag.

## Steps

1. From the same-team Executor, submit `POST /v1/executors/{executor_id}/claim` for the oldest eligible pending task and receive `200 claimed`.
2. Read the claimed task through trusted Gateway context for `team-a` and inspect the claim response as the claiming Executor.
3. Observe State Registry outbound calls during claim.

## Expected outcome

The claim returns the canonical task with `tasks.owner_command_id`, `tasks.executor_id`, `tasks.resolved_image`, `tasks.image_source`, `tasks.claimed_at`, and a signed team-bound scope token containing `team_id`, `project_id` (required claim; null only when the canonical environment has no project scope), `task_id`, `environment_id`, `executor_id`, `audience` (literal `state-registry.environment.open`), `key_id`, `issued_at`, and `expiry`. The Gateway task read returns `200` without plaintext values; State Registry does not call any external cryptography service; the local AES-256-GCM encrypt operation is performed only once for the claim (no source-system encryption call); and project/task scope narrows use only inside `team-a`. No `dispatched` event is appended; the FIRST `created` event is Registry-appended at claim time.
