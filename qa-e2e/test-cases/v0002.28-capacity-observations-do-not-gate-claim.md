# Test case: v0002.28-capacity-observations-do-not-gate-claim

## Implements

`state-registry` — `### Requirement: State Registry observes Executor capacity without gating discovery or claim`.

## Intent

Verify the Registry treats saturated capacity values as observations and still discovers and claims an otherwise eligible `pending` task.

## Preconditions

A `team-a` `pending` task has tag `openhands`; `executor-1` is bound to `team-a`, registered with that one tag, and observed at `max_capacity = running_count = 1`.

## Steps

1. Read `executor-1` through trusted Gateway context for `team-a`.
2. From `executor-1`, discover same-team pending tasks by exact registered tag.
3. Submit `POST /v1/executors/{executor_id}/claim` with `task_id` and `command_id`.
4. Read the task and history through the same Gateway team context.

## Expected outcome

The stored observations remain informational; discovery returns the same-team matching pending task; claim returns `200 claimed` and never any capacity-related rejection; the task projects to `created` with same-team `executor-1` set as `tasks.executor_id`, immutable `tasks.owner_command_id`, and `tasks.resolved_image` + `tasks.image_source`; and the ordered event list is exactly `[created]` with one Registry-appended `created` row whose non-null `executor_id` identifies `executor-1`.
