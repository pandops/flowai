# Test case: v0006.22-responsive-accessible-ui-states

## Implements

`web-ui` — `### Requirement: Web UI is responsive and keyboard operable`.

`web-ui` — `### Requirement: Web UI exposes consistent asynchronous and validation states`.

## Intent

Verify responsive composition, keyboard behavior, focus management, accessible states, and consistent loading, empty, validation, and error feedback across the prototype.

## Preconditions

- A mocked proxy serves the current Web UI HTTP and WebSocket contract for `team-alpha`; no API Gateway process is required.
- Fixtures can hold and fail REST and WebSocket responses deterministically.
- The browser can emulate desktop, tablet, and mobile viewports and reduced motion.

## Steps

1. Traverse primary navigation and each screen at desktop, tablet, and mobile widths using only the keyboard.
2. On task detail, focus cancellation beside status, open its confirmation dialog, tab through it, dismiss it, and inspect restored focus.
3. Inspect hover, `focus-visible`, active, disabled, and loading styles for representative buttons, links, filters, inputs, and pagination.
4. Hold dashboard, history, detail, settings, audit, and log requests to inspect loading announcements.
5. Return empty responses, validation failures, REST errors, and a disconnected live log; invoke available retries.
6. Run automated accessibility checks on the stable state of every route and dialog.

## Expected outcome

No target viewport has unintended horizontal overflow or unreachable content;
mobile navigation and card compositions remain operable; focus order is
logical, the modal traps and restores focus, and Escape does not submit the
action; every control has an accessible name and discernible interactive
state; loading and live errors are announced without replacing canonical data;
empty and error states are informative and recoverable; no state exposes
secret plaintext or trusted headers; and the automated scan reports no
serious or critical accessibility violations.
