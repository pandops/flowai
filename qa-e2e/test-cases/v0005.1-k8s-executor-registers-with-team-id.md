# Test case: v0005.1-k8s-executor-registers-with-team-id

## Implements

`executor` — `### Requirement: K8s Executor binds to a single configured team identity`.

`executor` — `### Requirement: K8s Executor participates in State Registry FIFO task claims`.

## Intent

Verify a K8s Executor registers with exactly one `scope = team`,
exactly one `team_id`, exactly one `authorized_tag`, observed
`max_capacity`, observed `running_count`, and runtime metadata, all bound to the configured
Executor team identity, with no transport-derived `identity` field
in the registration body, and that the State Registry exposes the
bound `team_id` on subsequent reads. The K8s Executor follows the
platform `executor_<runtime>_<tool>` concrete naming convention
documented in AGENTS.md: the directory, command, config YAML, Go
import path, wire `executor_type`, log/probe service names, and
`flowai.runtime` tool portion all derive from
`executor_k8s_openhands`; the selected agent tool is OpenHands and the Go
wire constant is `ExecutorTypeK8sOpenHands`. The current concrete Executor
(Docker runtime) is renamed by this change to `executor_docker_openhands`.

## Preconditions

State Registry and PostgreSQL are running. The K8s Executor is
configured with `team_id = team-A` and one `authorized_tag`. The
Executor's persistent recovery cache is an empty mounted
persistent volume. v0009: backend transport is plain HTTP; the
State Registry does not authenticate the Executor connection —
the deployment network policy owns the Executor-caller
boundary; the State Registry validates the canonical record
shape (scope, immutable `team_id`, exactly one tag) and never
derives identity from a peer certificate.

## Steps

1. Start the K8s Executor and observe its outbound `POST /v1/executors` with
   `executor_type = "executor_k8s_openhands"`
   (the concrete wire value that follows the platform
   `executor_<runtime>_<tool>` convention documented in AGENTS.md;
   here `runtime = k8s` and `tool = openhands`; see the
   `executor_<runtime>_<tool>` rule in AGENTS.md),
   `scope = team`, `team_id = team-A`, `authorized_tag = k8s-cluster-1`,
   `max_capacity = 2`, `running_count = 0`, and runtime metadata. Do not
   include an `identity` or `team_name` field in the request body.
   Capture the `201 Created` response and its server-generated UUID
   `executor_id`, then verify the Executor atomically writes it to the bbolt
   `metadata` bucket in `<cache_dir>/executor.db` before discovery or claim.
2. Read `{generated_executor_id}` through the API Gateway Executor read API.
3. Restart the Executor with the same volume and observe it re-send the same
   `PUT /v1/executors/{generated_executor_id}` request.
4. The K8s Executor never requests, generates, mounts, or reloads
   certificate material; the State Registry rejects any change to
   `scope`, `team_id`, or `authorized_tag` between re-registrations.

## Expected outcome

State Registry generates exactly one valid UUID. It is durably cached before
task intake. The first registration returns `201` and stores
`scope = team`, `team_id = team-A`, `authorized_tag = k8s-cluster-1`,
`max_capacity = 2`, and `running_count = 0`
on the canonical Executor record. Its canonical `identity` is the
server-generated UUID recorded on the `executors` row. The read returns `200` with the same
`team_id` and `authorized_tag`. The idempotent re-registration returns
`200` and the stored `team_id`, `authorized_tag`, and capacity values
remain unchanged; restart reuses the same UUID and does not generate another.
The State Registry rejects any change to `scope`, `team_id`, or
`authorized_tag` between re-registrations as `scope_change_forbidden`
or `team_binding_mismatch`. Backend transport is plain HTTP;
external HTTPS terminates at Ingress; the network policy owns
the caller boundary.
