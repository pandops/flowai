# Test case: v0006.28-capacity-full-keeps-next-task-pending

## Implements

`executor` — `### Requirement: Docker Executor runs bounded OpenHands containers`.

`executor` — `### Requirement: K8s Executor tracks child Pod capacity locally`.

`web-ui` — `### Requirement: Web UI renders searchable paginated task history`.

`web-ui` — `### Requirement: Web UI renders task detail and executor navigation`.

## Intent

Verify end to end, for both concrete Executor implementations, that an
Executor at local capacity does not claim another task, the waiting task stays
visibly `pending`, and it starts only after the occupied slot is released.

## Preconditions

- Run this case in isolated `executor_docker_openhands` and
  `executor_k8s_openhands` Playwright projects after team creation and
  Executor registration.
- Configure the current project's concrete Executor with
  `max_capacity=1` and no active task before the test.
- Reuse the Docker capacity fixture behind `v0002.13-executor-honors-capacity`
  and the K8s capacity fixture behind
  `v0005.6-local-capacity-stops-claim-without-registry-rejection`.
- The deterministic OpenHands runtime can hold the first task in `running`
  until the test explicitly releases it.
- The mocked proxy adapts live task reads and events from the real State
  Registry and does not synthesize assignment, status, or lifecycle events.

## Steps

1. Ingest a uniquely identified first task into State Registry and wait until
   the current Executor claims it and its Docker container or K8s Pod is
   running.
2. Verify in State Registry and the Web UI that the first task is `running`,
   is assigned to the captured `executor_id`, and has `created → running`.
3. While the only slot remains occupied, ingest a uniquely identified second
   eligible task for the same team, task type, and execution tag.
4. Wait longer than at least two configured Executor discovery intervals.
5. Inspect the second task in State Registry, task history, task detail, and
   the Executor's active-task list.
6. Release the first task, wait for its `finished` event and runtime cleanup,
   and verify the Executor's local slot becomes free.
7. Observe the second task until the same Executor claims it, starts exactly
   one runtime, and completes it successfully.
8. Reload both task details and compare their visible statuses and lifecycle
   timelines with State Registry.

## Expected outcome

Both matrix projects pass independently. While the first task occupies the
only local slot, the second remains `pending` with null `executor_id`, null
`owner_command_id`, no lifecycle event, no Docker container or K8s Pod, and no
entry in the Executor's active-task list. The UI labels it «Ожидает» and does
not fabricate `created`, `running`, an assignment, or a capacity-error state.
State Registry does not reject or reserve the task because capacity is owned
locally by the Executor. After the first task reaches `finished` and the slot
is released, the second is claimed by the same Executor, progresses exactly
through `created → running → finished`, appears in its active-task list only
while assigned and non-terminal, and finishes with no period in which more
than one task runtime exists for that Executor.
