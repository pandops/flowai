# Test case: v0007.22-partially-mapped-oidc-teams-are-filtered

## Implements

`auth` — `### Requirement: Gateway resolves OIDC teams in its own database before issuing operator-team bearer tokens`

## Intent

Edge-case test verifying that unknown well-formed OIDC memberships are filtered without blocking mapped teams or being auto-created.

## Preconditions

- The provider returns `oidc-team-alpha`, `oidc-team-beta`, and `oidc-team-unknown` for one operator.
- Gateway maps the first two identifiers to `team-alpha` and `team-beta`; no mapping exists for the third.
- Read-only test connections can assert exact rows in both service databases after the public flow.

## Steps

1. Complete OIDC login and call `GET /auth/v1/teams`.
2. Call `POST /auth/v1/token` once for each returned team.
3. Attempt token issue with `oidc-team-unknown` and with forged `team-gamma`.
4. Assert exact Gateway mapping, membership-observation, and derived-access rows and assert State Registry contains no OIDC identifier or membership row.

## Expected outcome

The team list contains exactly `team-alpha` and `team-beta` in deterministic order, and each can receive a one-team working token. Both unknown selections return `403 team_not_accessible`. Gateway records the observed unknown OIDC identifier only in its membership snapshot, creates no mapping or derived canonical access for it, and State Registry stores no OIDC membership data.
