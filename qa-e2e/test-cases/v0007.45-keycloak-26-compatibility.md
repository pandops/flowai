# Test case: v0007.45-keycloak-26-compatibility

## Implements

`api-gateway` — `### Requirement: Gateway obtains canonical OIDC teams from OIDC provider`

`api-gateway` — `### Requirement: Gateway owns OIDC-to-canonical-team mappings`

## Intent

Compatibility E2E proving that the provider-neutral Gateway contract works against the exact real identity-provider image `quay.io/keycloak/keycloak:26.6.3`, without adding Keycloak-specific behavior to production code.

## Preconditions

- The E2E harness can run rootless containers and publish OS-assigned loopback ports.
- Keycloak imports an isolated temporary realm containing one public PKCE client, one test operator, two team groups, and the `flowai-system-admin` realm role.
- API Gateway runs from its production image against a real isolated PostgreSQL container; a narrow public-contract State Registry team fixture supplies canonical team point reads so this provider-compatibility case does not replace the full cross-service Stage 2 deployment.

## Steps

1. Start `quay.io/keycloak/keycloak:26.6.3` with the checked-in E2E realm fixture and wait for that realm's discovery document.
2. In Playwright, perform authorization-code login with PKCE and test-only credentials; require matching state and exchange the returned code at Keycloak's advertised token endpoint.
3. Validate the ID Token through the advertised JWKS and call the advertised UserInfo endpoint.
4. Verify both configured claim sources expose exactly the two seeded opaque team identifiers and that issuer, audience, nonce, subject, expiry, and asymmetric algorithm match the provider-neutral contract.
5. Register both OIDC-team mappings through Gateway with a Keycloak-issued administrator JWT, repeat one mapping idempotently, and complete Gateway login.
6. Read the two resolved canonical teams, select each team, and verify each newly issued working token contains exactly one canonical team and a distinct `jti`.
7. Stop and restart Keycloak with the same temporary realm data, repeat discovery and login, and verify Gateway does not depend on a Keycloak-specific endpoint or claim outside configured adapters.

## Expected outcome

Keycloak 26.6.3 completes the standard browser authorization-code-with-PKCE flow. Discovery, token, UserInfo, and JWKS responses are accepted through provider-neutral configuration; exactly the seeded team identifiers are normalized. Gateway-owned mappings resolve both canonical teams, idempotency works, and one-team working tokens are issued. No Keycloak token, group identifier, membership row, password, or provider-specific field reaches State Registry or appears in browser-visible Gateway responses. Cleanup removes every temporary container and volume.

## Evidence

- RED: production Gateway login returned HTTP `501` instead of the required discovery-derived HTTP `302`.
- GREEN (provider compatibility and login start): exact image `quay.io/keycloak/keycloak:26.6.3` completed browser authorization-code with PKCE; ID Token RS256/JWKS, issuer, audience, nonce, expiry, administrator role, ID Token teams, and UserInfo teams passed. The production Gateway image performed discovery and generated a redirect with non-empty one-time `state`, `nonce`, and S256 PKCE challenge.
- GREEN (complete provider compatibility): Gateway validates the Keycloak callback, stores only encrypted provider state, registers both mappings through its public admin API using a Keycloak-issued `flowai-system-admin` JWT, returns both canonical teams, and issues two signed one-team working tokens with distinct `jti` values. Exact Gateway database assertions verify two mappings, two observations, two derived access rows, one ciphertext-only session, and two distinct token records.
