# Test case: v0005.6-local-capacity-stops-claim-without-registry-rejection

## Implements

`executor` — `### Requirement: K8s Executor tracks child Pod capacity locally`.

## Intent

Verify two distinct facts in sequence: first, that the State Registry
treats saturated stored capacity observations as informational only
and still claims an otherwise eligible same-team `pending` task when a
harness-authenticated direct claim request is issued (proving the
Registry does not gate claim on capacity); second, that the actual
K8s Executor process, while its locally observed
`running_count = max_capacity`, refrains from issuing an additional
claim request for a second same-team `pending` task until the local
slot frees (proving the local-only enforcement). Together they
confirm capacity is purely local and SHALL NOT be communicated as a
Registry-side rejection.

## Preconditions

State Registry and PostgreSQL are running. An authenticated Executor
service identity `k8s-exec-A` bound to `team_id = team-A` is
registered with `scope = team`, exactly one
`authorized_tag = k8s-cluster-A`, observed `max_capacity = 1`, and
observed `running_count = 1`. Two `pending` tasks exist for
`team-A`/`k8s-cluster-A`: `task_id_1` (older `ingested_at`) and
`task_id_2` (newer `ingested_at`).

## Steps

1. Read `k8s-exec-A` through the API Gateway Executor read API and
   confirm its stored capacity observations (`max_capacity = 1`,
   `running_count = 1`).
2. As `k8s-exec-A`, request
   `GET /v1/executors/k8s-exec-A/tasks?tag=k8s-cluster-A` and confirm
   both `task_id_1` and `task_id_2` are returned in `(ingested_at ASC,
task_id ASC)` order regardless of `running_count = max_capacity`.
3. Part A (Registry-side capacity independence): using a
   test-harness authenticated client that carries the same
   `k8s-exec-A` service identity (so the State Registry binds the
   call to `team_id = team-A`) but does NOT itself run the K8s
   Executor process loop, issue
   `POST /v1/executors/k8s-exec-A/claim` for the oldest eligible
   `task_id_1` with a fresh `command_id` directly against the State
   Registry and capture the response status code and body.
4. Part B (Executor-side local enforcement): with the actual K8s
   Executor process for `k8s-exec-A` running and its locally
   observed `running_count` equal to `max_capacity`, observe the
   Executor's outbound traffic to the State Registry for a
   configurable observation window and confirm the process issues NO
   `POST /v1/executors/k8s-exec-A/claim` request for either
   `task_id_1` or `task_id_2` while saturated.
5. Have the running task reach its tool-level terminal signal, receive
   `202 accepted` for its terminal event, wait its selected
   `finished_cleanup_delay` or `failed_cleanup_delay`, and complete
   idempotent Pod deletion so the retained Pod finally leaves the local
   capacity count. Then
   observe that the process subsequently issues a
   `POST /v1/executors/k8s-exec-A/claim` request for one of the
   remaining `pending` tasks and receives `200 claimed`.
6. Read `task_id_1`, `task_id_2`, and the Executor's event history
   through the API Gateway.

## Expected outcome

Step 1 returns `200` with `max_capacity = 1` and `running_count = 1`.
Step 2 returns `200` with both `task_id_1` and `task_id_2` summaries
in `(ingested_at ASC, task_id ASC)` order, regardless of
`running_count = max_capacity`. Step 3 (Part A) returns `200 claimed`
and NEVER returns `422 executor_at_capacity` or any capacity-based
rejection; the State Registry records a `created` event with
`executor_id = k8s-exec-A`, sets `tasks.owner_command_id` and
`tasks.executor_id` immutably, persists `tasks.resolved_image` and
`tasks.image_source`, and sets `tasks.claimed_at` even though the
stored observation is saturated — proving Registry claim is
capacity-independent. Step 4 (Part B) confirms the actual K8s
Executor process issues no claim request while saturated, including the
configured post-terminal cleanup delay while the Pod remains retained.
Step 5 confirms `running_count` does not fall and no claim is issued merely
because the terminal event was accepted; the process issues exactly one
claim request only after idempotent cleanup frees the local slot and receives
`200 claimed`. After all steps, `task_id_1`
projects to `created` with `executor_id = k8s-exec-A`, an
`owner_command_id` equal to the request `command_id`, and an ordered
event history of exactly `[created]`; `task_id_2` remains
`current_state = pending`, `executor_id = null`, with an empty event
history. No `dispatched` event appears at any point.
