# Test case: v0006.12-scoped-launch-parameters

## Implements

`state-registry` — `### Requirement: State Registry resolves scoped launch parameters`.

`state-registry` — `### Requirement: State Registry resolves launch-parameter image overrides`.

`web-ui` — `### Requirement: Web UI manages scoped launch parameters`.

## Intent

Happy-path and isolation coverage verifying that ordinary env values, secret
references and image overrides resolve across global, team, and task-type
scopes without weakening team ownership or introducing task-scoped definitions.

## Preconditions

- An administrator-created global launch-parameter definition exists.
- `team-alpha` has a required default image, one task type, one source
  system, and team- and task-type-scoped launch parameters.
- The definitions contain overlapping env keys, logical secret references,
  and image candidates.
- Mocked proxy integration mode forwards the browser-selected `team-alpha`.

## Steps

1. Create team-scoped ordinary env values and a secret through the Web UI.
2. Create task-type-scoped values and an image for the same-team
   `task_type_id`.
3. Attempt to create task-scoped launch parameters, env, and a secret for one pending task.
4. Claim the task with an eligible Executor and open its assigned parameters.
5. Attempt to bind launch parameters to another team's task type.

## Expected outcome

The resolved ordinary env values and logical secret references follow
`global → team → task_type` specificity; the task-type value wins for
duplicate keys; task-scoped definitions are rejected; the direct task image
wins when present, otherwise the
most specific applicable launch-parameter image wins before catalog defaults;
the team default remains the final fallback; no secret plaintext appears in
operator responses; and the foreign task-type binding returns the same
non-revealing `404` as unknown without mutation.
