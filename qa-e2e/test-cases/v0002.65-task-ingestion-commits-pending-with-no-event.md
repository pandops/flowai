# Test case: v0002.65-task-ingestion-commits-pending-with-no-event

## Implements

`state-registry` — `### Requirement: State Registry is the canonical team-scoped task source`.

`state-registry` — `### Requirement: State Registry defines the task lifecycle as pending then created then running then terminal`.

`state-registry` — `### Requirement: State Registry rejects invalid or out-of-order lifecycle transitions`.

## Intent

Verify that an authorized listener ingestion commits a `pending` task row with REQUIRED non-null same-team `task_type_id`, server-derived `required_tag`, no lifecycle event appended, `ingested_at` set once and immutable, `owner_command_id` NULL, `claimed_at` NULL, `resolved_image` NULL, `image_source` NULL, `executor_id` NULL, and that the FIRST `created` event is Registry-appended only after a later successful claim. Extend this case to cover missing-`task_type_id`, foreign-team-`task_type_id`, and listener-supplied-`required_tag` rejection paths so no new test-case ID is required.

## Preconditions

State Registry, PostgreSQL, and an authenticated listener identity for `team-a` and a registered source system `source-system-a` are running; `team-a` has a registered task type `tt-a1` with `execution_tag = openhands`; `team-b` has a registered task type `tt-b1`; no task exists for `(team-a, source-system-a, T-1)`.

## Steps

1. Submit `POST /v1/tasks` with `team_id = team-a`, `source_system_id = source-system-a`, `source_id = T-1`, REQUIRED `task_type_id = tt-a1`, and `payload`.
2. Read the canonical task back through trusted Gateway context and capture `current_state`, `task_type_id`, `required_tag`, `owner_command_id`, `executor_id`, `claimed_at`, `resolved_image`, `image_source`, `ingested_at`, and the canonical event history.
3. Attempt to mutate `ingested_at` on the canonical task through any other state transition and observe the response.
4. Submit `POST /v1/tasks` for the same `(team-a, source-system-a, T-1)` triple without `task_type_id` and observe the rejection without persistence.
5. Submit `POST /v1/tasks` with a body that names `task_type_id = tt-b1` (foreign-team task type) under the `team-a` listener identity and observe the rejection without persistence.
6. Submit `POST /v1/tasks` with a listener-supplied `required_tag = openhands` alongside the valid `task_type_id` (whether in the body or as a header) and observe that the Registry rejects the request with `400 listener_supplied_required_tag_forbidden` without persistence, without event append, and without listener acknowledgement.
7. Attempt to claim the committed task with `command_id = C-1` from the same-team Executor and observe the task transitions to `created` with a single Registry-appended `created` event.

## Expected outcome

After step 1 the task is durable as `current_state = pending` with REQUIRED non-null same-team `task_type_id = tt-a1`, `required_tag` derived server-side from `tt-a1.execution_tag`, NO event in `task_events`, `owner_command_id = NULL`, `executor_id = NULL`, `claimed_at = NULL`, `resolved_image = NULL`, and `image_source = NULL`; `ingested_at` is set once and is immutable. Steps 3, 4, 5, and 6 are rejected without persistence and without event append: step 3 confirms `ingested_at` immutability; step 4 confirms REQUIRED `task_type_id` enforcement; step 5 confirms the same-team `task_types.task_type_id` constraint; step 6 confirms the Registry rejects any listener-authored `required_tag` field with `400 listener_supplied_required_tag_forbidden` (no silent ignore, no silent overwrite). After step 7, exactly one `created` event exists with non-null `executor_id = claiming_executor` and payload `task <task_id> loaded by <executor_id>`; no `dispatched` event was ever appended.
