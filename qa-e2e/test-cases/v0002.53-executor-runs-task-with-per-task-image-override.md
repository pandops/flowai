# Test case: v0002.53-executor-runs-task-with-per-task-image-override

## Implements

`executor` — `### Requirement: Docker Executor runs bounded OpenHands containers`.

## Intent

Verify that the Docker Executor uses the `resolved_image` returned in the claim response verbatim when a per-task override wins, records the image source as `task_override`, and refuses to substitute its locally configured image even when the local image differs.

## Preconditions

- A `team-a` concrete Executor process (`executor_docker_openhands` per the platform `executor_<runtime>_<tool>` convention documented in AGENTS.md; `runtime = docker`, `tool = openhands`) is running team-owned (`scope = team`) with a locally configured OpenHands agent runtime image `local-X` that differs from any Registry-resolved reference.
- State Registry, PostgreSQL, and the configured 256-bit AES-256-GCM data key are available.
- A `team-a` `pending` task has been ingested by the listener with `image` set to a known opaque reference `override-B`.
- The required `team-a` `default_image` is `default-A`.

## Steps

1. The Executor discovers the `pending` task through `GET /v1/executors/{executor_id}/tasks?tag=<registered_tag>`.
2. The Executor submits `POST /v1/executors/{executor_id}/claim` with `task_id` and `command_id` and receives `200 claimed` with `resolved_image = override-B` and `image_source = task_override`.
3. The Executor appends a `running` event with a fresh `event_id` and the canonical envelope.
4. The Executor starts one labeled OpenHands container using `resolved_image = override-B` and explicitly NOT `local-X`.
5. Inspect the container metadata, the Executor's structured logs, and any cached configuration the Executor might consult.

## Expected outcome

The container is started with `override-B`; the container metadata records the image source as `task_override`; the `running` event is accepted with `202 accepted`; the Executor's local image `local-X` is neither consulted nor substituted and the task is refused if `resolved_image` cannot be pulled or started. The Executor's logs identify the source as `task_override` without logging the digest verbatim unless the configured logger redacts it.
