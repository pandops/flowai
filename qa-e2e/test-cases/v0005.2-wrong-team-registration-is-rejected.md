# Test case: v0005.2-wrong-team-registration-is-rejected

## Implements

`executor` — `### Requirement: K8s Executor binds to a single authenticated team identity`.

## Intent

Verify the State Registry rejects a K8s Executor registration whose
`team_id` does not match the team bound to the authenticated Executor
service identity, without creating or updating an Executor record, and
that `team_id` is immutable across re-registration.

## Preconditions

State Registry and PostgreSQL are running. The K8s Executor is
configured with `team_id = team-A`. Executor cache is empty and no
Executor record exists for this service identity. v0009: the State
Registry does not authenticate the Executor connection — the
deployment network policy owns the Executor-caller boundary; the
State Registry validates the canonical record shape (scope,
immutable `team_id`, exactly one tag) and the configured `team_id`
against the registered `teams` row.

## Steps

1. Send `POST /v1/executors` as `k8s-exec-A` with
   `executor_type = "executor_k8s_openhands"`, `scope = team`, `team_id = team-B`,
   `authorized_tag = k8s-cluster-1`, `max_capacity = 2`,
   `running_count = 0`, and metadata.
2. Send `POST /v1/executors` as `k8s-exec-A` with
   `executor_type = "executor_k8s_openhands"`, `scope = team`, omitting the `team_id`
   field but supplying the rest of the registration payload.
3. List Executors through the API Gateway and verify neither failed POST
   created a record for this identity.
4. Send a valid `POST /v1/executors` with `team_id = team-A`, capture the
   server-generated `{executor_id}`, and cache it.
5. Re-send `PUT /v1/executors/{executor_id}` with `team_id = team-B`.
6. Read `{executor_id}` again through the API Gateway Executor read
   API.

## Expected outcome

The first registration returns `403` (or `400 invalid_team_id`) and
no Executor row is created. The
omitted-`team_id` registration also returns `403` (or `400
invalid_team_id_count`) and still creates no row. The valid POST returns
`201` with a generated UUID. After that registration, the divergent
re-registration in step 5 returns `403` (or `409 team_id_immutable`)
without changing the stored `team_id`; the final read returns `200`
with `team_id = team-A`, unchanged `authorized_tag`, and unchanged
capacity values.
