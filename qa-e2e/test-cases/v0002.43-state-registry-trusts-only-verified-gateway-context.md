# Test case: v0002.43-state-registry-trusts-gateway-context-as-request-data

## Implements

`state-registry` — `### Requirement: State Registry requires trusted team-scoped API Gateway context`.

`state-registry` — `### Requirement: State Registry uses canonical team-bound validation`.

## Intent

Verify operator surfaces consume the Gateway-forwarded operator/team/request context as trusted request data, applying the canonical `team_id` filter and audit rules without performing transport-level authentication.

## Preconditions

A trusted Gateway context can forward verified `operator_id`, immutable `team_id = team-a`, and `request_id`; the optional display-only `team_name` is forwarded only when the verified operator team carries one; an untrusted direct client can copy arbitrary headers and payload fields. v0009: the State Registry does not authenticate the Gateway connection; non-Gateway callers bypassing the trust boundary are an external network-policy concern; the State Registry validates the identifier shape of the forwarded context.

## Steps

1. Through a Gateway-forwarded context, perform an authorized task read, subscription, control, environment write, and secret write using the verified `operator_id`, `team_id`, and `request_id`.
2. Repeat each call directly without the Gateway context while copying all forwarded fields.
3. Submit a context whose canonical operator team check failed or whose context represents more than one team.
4. Read `team-a` resources and audits through a valid trusted context.

## Expected outcome

Valid Gateway-mediated requests are authorized solely by immutable `team_id` and audited with `operator_id` and `request_id`. Direct copied headers and invalid or multi-team contexts are rejected without reading or changing tenant data; unauthenticated payload fields never broaden access. The State Registry applies the same `team_id` filter to reads, subscriptions, controls, environment writes, secret writes, and audit reads as it would to a verified Gateway context; direct calls that bypass the Gateway are not authenticated and are accepted only when their `team_id` matches the canonical record of the resource they touch. The deployment network policy prevents non-Gateway callers from spoofing the context; the State Registry never authenticates the Gateway connection.
