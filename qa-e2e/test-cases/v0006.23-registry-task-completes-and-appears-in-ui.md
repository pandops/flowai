# Test case: v0006.23-registry-task-completes-and-appears-in-ui

## Implements

`web-ui` — `### Requirement: Web UI renders searchable paginated task history`.

`web-ui` — `### Requirement: Web UI renders task detail and executor navigation`.

## Intent

Verify end to end, for both concrete Executor implementations, that a task
ingested into State Registry is claimed and successfully completed, then
appears in the Web UI with its canonical Executor, terminal status, and
ordered lifecycle events.

## Preconditions

- Define one isolated Playwright runtime scenario for
  `executor_k8s_openhands` and one for `executor_docker_openhands`; each
  scenario executes `v0006.24`, then `v0006.25`, then `v0006.23` as ordered
  steps so the same captured runtime and canonical identifiers are retained.
- The K8s run reuses the deployed State Registry, PostgreSQL, k3d cluster,
  mocked OpenHands runtime, registered team, source system, task type, and
  running Executor from
  `qa-e2e/executor_k8s_openhands/tests/v0005.4-claimed-task-runs-as-pod-with-running-then-terminal-events.spec.ts`.
- The Docker run reuses the State Registry, PostgreSQL, Docker-compatible
  runtime, deterministic OpenHands runtime, registered team, source system,
  task type, and running Executor from
  `qa-e2e/state-registry/tests/contracts/12-v0005-real-docker-runtime-smoke.spec.ts`.
- In each isolated run, the preceding definitions provide one created team and
  exactly one registered concrete Executor for that team's execution tag with
  free capacity.
- The Web UI is running against a mocked proxy that exposes the current UI
  HTTP and WebSocket contract by reading the real test State Registry; the
  proxy does not serve static task or event fixtures.
- Task history is initially open for the same test team with filters that do
  not exclude the new task.

## Steps

1. Run steps 2–8 once with `executor_k8s_openhands` and once with
   `executor_docker_openhands`, using isolated teams and task identifiers.
2. Through the listener State Registry API, submit one uniquely identified
   task for the current run's source system and task type; capture its returned
   `task_id` and require `201 Created`.
3. Wait until the task with that exact `task_id` appears in the open Web UI
   task history without re-seeding or replacing proxy data.
4. Open the task from the history result and verify its canonical metadata.
5. Let the current run's concrete Executor discover, claim, and execute the
   task through its deterministic successful OpenHands branch.
6. Verify the assigned Executor link shows the current concrete Executor and
   opens its detail page.
7. Observe the task detail until its current lifecycle status becomes
   `finished`; inspect its lifecycle timeline and compare it with the same
   task's event history read directly from State Registry.
8. Reload the task detail and verify the terminal state, Executor, and timeline
   again.

## Expected outcome

Both matrix runs pass independently. In each run, the UI displays the exact
State Registry `task_id`; the task progresses from its pending projection to
the claimed/running projection and finally to `finished`; the assigned
Executor link identifies the concrete service used by that run—respectively
`executor_k8s_openhands` or `executor_docker_openhands`; and the lifecycle
timeline displays exactly `created`, `running`, and `finished` once each in
State Registry order. No event is fabricated while the task is pending, no
`dispatched` or cancellation lifecycle state appears, and reload reconstructs
the same `finished` state, Executor, and three events through the mocked proxy.
Each direct State Registry assertion and visible UI assertion refers to the
same run-specific captured `task_id`, so neither run can pass using seeded,
unrelated, or cross-runtime UI data.
