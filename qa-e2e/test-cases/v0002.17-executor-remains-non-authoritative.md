# Test case: v0002.17-executor-remains-non-authoritative

## Implements

`executor` — `### Requirement: Executors preserve configured ownership without transport identity`.

`executor` — `### Requirement: Docker Executor remains local and non-authoritative`.

## Intent

Verify the Executor uses its registered scope (`team` or `system`) and either its immutable `team_id` binding (team-owned) or the parent task's `team_id` (system-owned) throughout its process lifetime, rejects mismatched team data and `team_name`-based authorization, uses `resolved_image` verbatim with no local fallback, and retains no durable canonical state or plaintext secret.

## Preconditions

A concrete Executor (`executor_docker_openhands` per the platform `executor_<runtime>_<tool>` convention documented in AGENTS.md; `runtime = docker`, `tool = openhands`) is bound to `team-a` with `scope = team` and has successfully claimed a `team-a` `pending` task via `POST /v1/executors/{executor_id}/claim` with `command_id = C-1`; the claim response carried `resolved_image` and `image_source`; the assigned task references a team-bound scoped environment. v0009: the State Registry does not authenticate the Executor; the `X-FlowAI-Executor-Id` and `X-FlowAI-Team-Id` headers are trusted request data derived from the Executor's configuration.

## Steps

1. Run the same-team task to completion.
2. Restart the Executor and observe that its registered scope, configured `team_id`, and server-generated `executor_id` round-trip successfully over plain HTTP.
3. Attempt to inject a State Registry response, scope token, or control whose `team_id` differs from `team-a`; observe the Executor rejects each locally without starting a runtime or injecting environment values.
4. Attempt to inject a `team_name = team-b` field while keeping `team_id = team-a`; observe the Executor does not treat it as authorization.
5. Attempt to start a runtime with a different image than `resolved_image`; observe the Executor refuses the task.
6. Inspect local durable storage and read `team-a` State Registry records through the trusted Gateway path.

## Expected outcome

The Executor accepts only data whose `team_id` matches its configured immutable team binding (team-owned) or whose task-side `team_id` matches the parent task's `team_id` (system-owned); it rejects foreign-team responses, foreign-team scope tokens, and any payload relying on `team_name` for authority, never substitutes its local image for `resolved_image`, and refuses tasks when `resolved_image` cannot be pulled or started. Canonical team ownership, tasks, assignments, events, environment metadata, and secret versions remain only in State Registry; the Executor retains no durable canonical state or plaintext secret, never authorizes teams, and never changes its `scope` or `team_id` across restart; the runtime image source recorded on each container reflects the four-level precedence. The server-generated `executor_id` is an identifier, not authentication proof.
