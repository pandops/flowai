# Test case: v0007.1-token-carries-canonical-team-claims

## Implements

`auth` — `### Requirement: Gateway resolves OIDC teams in its own database before issuing operator-team bearer tokens`

`api-gateway` — `### Requirement: Gateway exposes versioned auth and mapping APIs`

## Intent

Happy-path test verifying OIDC team resolution, accessible-team listing, selection, and one-team token issuance.

## Preconditions

- OIDC provider maps `operator-1` to canonical OIDC teams `oidc-team-alpha` and `oidc-team-beta`.
- API Gateway's database maps them to State Registry-owned `team-alpha` / `Alpha Team` and `team-beta` / `Beta Team`.

## Steps

1. Log in as `operator-1` through API Gateway and OIDC provider.
2. Verify the accessible-team response.
3. Select `team-alpha` through `POST /auth/v1/token` and inspect the issued working token's verified claims.
4. Log in as an operator whose OIDC teams have no active Gateway mapping.

## Expected outcome

The Gateway returns both canonical teams in deterministic order. The working token contains a known `kid`, allowed algorithm, configured `iss` and `aud`, `sub`, canonical `operator_id=operator-1`, exactly one immutable `team_id=team-alpha`, `team_name=Alpha Team`, `iat`, future `exp`, and unique `jti`; it contains no second team or OIDC team list. The unmapped operator receives an empty accessible-team list and no working token.
