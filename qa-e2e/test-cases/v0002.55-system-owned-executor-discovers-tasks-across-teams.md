# Test case: v0002.55-system-owned-executor-discovers-tasks-across-teams

## Implements

`state-registry` — `### Requirement: State Registry lists pending tasks by exact tag, scoped to the Executor's eligibility`.

## Intent

Verify that a system-owned Executor can discover `pending` tasks from multiple teams when they share the Executor's registered tag, that each returned `TaskSummary` carries its own `team_id` and metadata fields, and that the response is metadata-only (no task payload values, decrypted environment values, secret material, or event history; payload is delivered only in a successful `200 claimed` response for the assigned task).

## Preconditions

- State Registry and PostgreSQL are running.
- `team-a` and `team-b` each have at least one `pending` task with the registered tag, each referencing a REQUIRED non-null same-team `task_type_id` whose `execution_tag` matches the Executor's registered tag.
- A system-owned Executor has registered with `scope = system`, `team_id = null`, and the shared registered tag.

## Steps

1. As the system-owned Executor, call `GET /v1/executors/{executor_id}/tasks?tag=<registered_tag>` and inspect the response.
2. Verify each returned `TaskSummary` carries `task_id`, `team_id`, `task_type_id`, `required_tag` (server-derived), `source_system_id`, `source_id`, `current_state = pending`, `ingested_at`, `project_id`, `environment_id`, `image` (nullable), `owner_command_id = null`, `executor_id = null`, `claimed_at = null`, `resolved_image = null`, and `image_source = null`.
3. Filter or partition the response by `team_id` and confirm that summaries from both `team-a` and `team-b` are present.
4. Confirm the response shape does NOT contain task payload values, decrypted environment values, secret material, nonce bytes, ciphertext bytes, tag bytes, key material, or event history; the response is metadata-only.
5. Submit `POST /v1/executors/{executor_id}/claim` for one `team-a` task with a fresh `command_id` and confirm the `200 claimed` response is the only place the payload and `resolved_image` are delivered to the assigned Executor; no other payload exposure exists.
6. Confirm the response shape does not leak aggregate counts, cursors, or pagination metadata that would distinguish teams beyond what each `TaskSummary` already exposes.

## Expected outcome

The discovery call returns `200` with metadata-only summaries from both teams in the same response. Each summary carries its own `team_id`, `task_type_id`, and server-derived `required_tag`, and the response never includes task payload values, decrypted environment values, secret material, or event history. The aggregate response does not expose cross-team totals or cursors that the team-owned Executor would not see. The only place the task payload and `resolved_image` are delivered to the assigned Executor is the `200 claimed` response for that exact task.
