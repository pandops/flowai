# Test case: v0002.18-executor-pulls-matching-task

## Implements

`executor` — `### Requirement: Docker Executor discovers and claims the oldest eligible same-team matching task`.

## Intent

Verify the Docker Executor starts only an exact-tag `pending` task after explicit FIFO claim with `command_id`.

## Preconditions

A `team-a` `pending` task has tag `openhands`, another `team-a` `pending` task has tag `k8s`, and the concrete Executor identity (`executor_docker_openhands` per the platform `executor_<runtime>_<tool>` convention documented in AGENTS.md; `runtime = docker`, `tool = openhands`) is team-owned (`scope = team`) bound to `team-a`, registered with exactly `openhands`, and has a local slot.

## Steps

1. Start FIFO discovery and observe the Executor request only its authenticated team and exact registered tag, ordered `(ingested_at ASC, task_id ASC)`.
2. Observe the Executor choose the same-team matching `task_id` and submit `POST /v1/executors/{executor_id}/claim` with `command_id = C-1`.
3. After `200 claimed`, capture the Registry-appended `created` event (`executor_id = executor-1`, payload `task <task_id> loaded by executor-1`) and the claim response's `resolved_image` + `image_source`.
4. Capture the Executor-emitted `running` event before container startup.
5. Read both tasks and the claimed task's event history through trusted Gateway context for `team-a`.

## Expected outcome

FIFO discovery returns only the same-team `openhands` task; the claim succeeds with `200 claimed` whose body includes `task`, `environment_id`, `scope_token`, `resolved_image`, `image_source`, and `claimed_at`; the Registry-emitted first `created` event is appended inside the same claim transaction and has non-null `executor_id` identifying the claiming Executor and payload meaning `task <task_id> loaded by executor-1`; one container starts using `resolved_image` verbatim; the Executor-emitted `running` event posted later via `POST /v1/tasks/{task_id}/events` returns `202 accepted` with non-null assigned `executor_id` and envelope `team_id = team-a` that State Registry verifies against the authenticated Executor team; the claimed task projects through `[created, running]` (no `dispatched` event exists); and the `k8s` task remains `pending` and unassigned. The Executor's local slot is consumed only after `200 claimed` is received; the FIRST Registry-emitted `created` row lives in the same claim transaction and is not the same response shape as later `running`/`finished`/`failed` event appends.
