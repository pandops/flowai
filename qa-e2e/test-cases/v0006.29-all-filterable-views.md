# Test case: v0006.29-all-filterable-views

## Implements

`web-ui` — `### Requirement: Web UI filters every filterable view consistently`.

## Intent

Verify through one data-driven browser suite that every filter rendered on
every filterable Web UI view works alone and in combination, resets correctly,
survives navigation where required, and behaves identically on desktop and
mobile.

## Preconditions

- The mocked proxy serves deterministic same-team datasets with at least two
  distinguishable values for every filter dimension, more than one page where
  pagination exists, one valid multi-filter intersection, and one combination
  that returns no results.
- The filter manifest covers dashboard, task history, Executor inventory,
  launch parameters, ordinary-variable revision history, secret-version
  history, team audit history, and Executor active tasks.
- Every rendered filter control exposes a stable semantic `data-filter-key`
  and accessible name. The test fails when a rendered key is missing from the
  manifest or a manifest key is not rendered on its applicable view.
- Desktop and mobile projects use the same data and expected query model.

## Steps

1. Open each filterable view and compare its rendered `data-filter-key` set
   with the test manifest before interacting with it.
2. For each filter control on that view, apply each representative option or
   search value alone and compare visible items, total count, request query,
   pagination, and accessible active state with the fixture model.
3. Apply the view's valid multi-filter combination and verify the exact
   intersection rather than the union of individual results.
4. Change page or page size where available and verify filters remain applied,
   ordering stays deterministic, and no item is duplicated or skipped.
5. Reload the URL, navigate away and back with browser history, and compare
   restored controls and results with the documented shareable or view-local
   state policy.
6. Apply the no-match combination and inspect the no-results state, retained
   filter controls, reset action, request count, and pagination.
7. Activate reset and verify the documented default filter values, first page,
   default page size, URL, count, and result set are restored.
8. Repeat steps 1–7 at the mobile breakpoint and operate all controls using
   only the keyboard.

## Expected outcome

The manifest and rendered filters match exactly on every applicable view, so
an untested filter cannot be added silently. Every individual filter returns
the exact fixture subset; combined filters use intersection semantics;
pagination, URL, reload, and browser navigation preserve the documented
state; no-match combinations show an informative empty result without losing
the controls; and reset restores the documented defaults and first page.
Desktop tables and mobile cards produce identical item identifiers and counts.
All filters have accessible names, visible `focus-visible` state, keyboard
operation, and announced result-count changes. No filter leaks a foreign-team
item, secret plaintext, or state from another view.
