# Test case: v0002.71-concurrent-claim-is-atomic

## Implements

`state-registry` — `### Requirement: State Registry claims the oldest eligible task atomically under FIFO`.

## Supersedes

`autotests/test-cases/v0002.4-concurrent-claim-is-atomic.md`. v0002.4 verifies the same FIFO atomic-claim behavior with a shared `state-registry` requirement header; v0002.71 intentionally re-verifies the contract under a tighter precondition (no older eligible task in the FIFO order for either Executor) and the additional explicit post-step where each Executor re-discovers and confirms the task is no longer visible to the winner's scope, so the two definitions remain assigned to distinct verification scenarios while preserving a single immutable v0002.4 ID on the earlier chronological definition.

## Intent

Verify that two eligible Executors racing to claim the same task produce exactly one `200 claimed` and one `409 task_already_claimed`, that exactly one `created` event exists on the task, and that the task disappears from the winner's scope of discovery.

## Preconditions

State Registry, PostgreSQL, and two eligible team-owned Executors with `team_id = team-a` and the same registered tag are running; one pending task T-1 exists with no older eligible task in the FIFO order for either Executor.

## Steps

1. From both Executors, concurrently submit `POST /v1/executors/{executor_id}/claim` with `task_id = T-1` and distinct `command_id`s.
2. Read each response and confirm one receives `200 claimed` and the other receives `409 task_already_claimed`.
3. Read the canonical task and confirm `executor_id` is the winner, `owner_command_id` is the winner's `command_id`, `current_state = created`, `resolved_image` and `image_source` set, and `claimed_at` set once.
4. Read the canonical task event history and confirm exactly one `created` event exists with `executor_id` equal to the winner.
5. From each Executor, re-discover eligible pending tasks and confirm T-1 is no longer visible to the winner's scope.

## Expected outcome

Exactly one `200 claimed`. Exactly one `409 task_already_claimed`. Exactly one `created` event with `executor_id = winning_executor`. The task disappears from the winner's discovery scope. No `dispatched` event is appended. Each Executor sees the result of atomicity: the loser cannot mutate anything.
