# Test case: v0002.78-aes-256-gcm-no-decrypt-on-denial

## Implements

`state-registry` — `### Requirement: State Registry opens environments only for assigned same-team Executors`.

`state-registry` — `### Requirement: State Registry uses local AES-256-GCM authenticated encryption for secret values`.

## Intent

Verify that every invalid or unavailable open attempt returns the same non-revealing `404 environment_unknown_or_unavailable` shape with zero decrypt operations and no plaintext, nonce, ciphertext, tag, key, or associated-data disclosure in logs, audit, or error responses.

## Preconditions

State Registry, PostgreSQL, the configured AES-256-GCM key, and a decrypt-operation counter are running; a claimed task with a valid open token exists; a battery of invalid tokens is prepared.

## Steps

1. Send a request without a token, with an empty token, and with a malformed token.
2. Send a token whose `team_id`, `project_id`, `task_id`, `environment_id`, `executor_id`, or `audience` claim differs from canonical records.
3. Send a token whose MAC has been tampered with after signing.
4. Send a token whose protected header `alg` is outside the allow-listed `HS256`/`HS384`/`HS512` HMAC set, whose `kid` differs from the payload `key_id`, whose `key_id` is outside the documented active key window including a retired key identifier, or whose `expiry`/`issued_at` are invalid.
5. Send a token under a different Executor identity whose otherwise-valid claims would pass canonical checks.
6. Replay an unused but still-valid token for a task that has reached terminal state.
7. Observe the decrypt-operation counter for every call.

## Expected outcome

Every invalid or unavailable open attempt returns the same non-revealing `404 environment_unknown_or_unavailable` response; the decrypt-operation counter records zero decrypt operations for any invalid case; logs, audit, and error responses contain no plaintext, no nonce bytes, no ciphertext bytes, no authentication tag bytes, no key material, and no associated-data values beyond identifier-level metadata; the response shape and code are identical across every invalid case so the endpoint cannot be used as a validation oracle. The valid token in a separate step runs exactly one decrypt operation under every canonical check.
