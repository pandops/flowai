# Test case: v0002.73-claim-resolved-image-and-image-source

## Implements

`state-registry` — `### Requirement: State Registry resolves the effective image at claim by four-level precedence`.

## Intent

Verify that on successful claim, the Registry persists `tasks.resolved_image` and `tasks.image_source` in the same transaction that appends the first `created` event, and that the claim response carries both fields for the same-step handoff to the Executor.

## Preconditions

State Registry and PostgreSQL are running; a team-owned Executor with `team_id = team-a` and one tag is registered; one pending task exists for that team and tag with no `tasks.image` override, no `task_types.default_image`, no `source_systems.default_image`, but a non-null `teams.default_image` (always present).

## Steps

1. Submit `POST /v1/executors/{executor_id}/claim` with the task's `task_id` and a fresh `command_id`.
2. Read the response body and confirm `resolved_image = teams.default_image` and `image_source = team_default`.
3. Read the canonical task through trusted Gateway context and confirm `resolved_image = teams.default_image`, `image_source = team_default`, `current_state = created`, `claimed_at` set, and `owner_command_id` set to the supplied `command_id`.
4. Read the canonical task event history and confirm exactly one `created` event with `executor_id = <claimant>`.
5. Restart the State Registry process and re-read the canonical task; confirm `resolved_image`, `image_source`, `executor_id`, and `owner_command_id` are unchanged.

## Expected outcome

The claim response carries `resolved_image` and `image_source` from the team-default level of precedence because no closer source applies. Both are persisted in the same transaction as the first `created` event. The persisted `resolved_image` and `image_source` survive restart and remain immutable from claim onward. No `dispatched` event is appended.
