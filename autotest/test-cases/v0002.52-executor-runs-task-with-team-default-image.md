# Test case: v0002.52-executor-runs-task-with-team-default-image

## Implements

`executor` — `### Requirement: Docker Executor runs bounded OpenHands containers`.

## Intent

Verify that the Docker Executor starts a labeled OpenHands container using the image returned in the claim response as `resolved_image`, and that the image-source metadata on the container records `team_default` when only the team's `default_image` was set. The Executor never consults a local fallback image.

## Preconditions

- A `team-a` concrete Executor process (`executor_docker_opehands` per the platform `executor_<runtime>_<tool>` convention documented in AGENTS.md; `runtime = docker`, `tool = openhands`) is running and team-owned (`scope = team`) registered with `team-a` and one authorized tag.
- State Registry and PostgreSQL are available. The configured 256-bit AES-256-GCM data key is loaded.
- A `team-a` `pending` task with no per-task `image` exists.
- An authenticated system administrator has set `team-a`'s required `default_image = default-A` at registration.

## Steps

1. The Executor discovers the `pending` task through `GET /v1/executors/{executor_id}/tasks?tag=<registered_tag>` and finds one matching task ordered by the FIFO `(ingested_at ASC, task_id ASC)` rule.
2. The Executor submits `POST /v1/executors/{executor_id}/claim` with `task_id` and `command_id` and receives `200 claimed` with `resolved_image = default-A` and `image_source = team_default`.
3. The Executor appends a `running` event with envelope `team_id = team-a`, `executor_id`, `task_id`, `event_id`, `event_type = running`, `occurred_at`, and a payload.
4. The Executor starts one labeled OpenHands container for the claimed task using `resolved_image` from the claim response verbatim.
5. Inspect the container metadata, the Executor's structured logs, and the durable storage of the Executor process.

## Expected outcome

The container is started with the `default-A` image reference; the container metadata records the image source as `team_default`; the `running` event is accepted with `202 accepted`; no value in the Executor logs or durable storage records the digest verbatim without redaction. The Executor does not consult a local image configuration; it uses `resolved_image` verbatim and refuses the task when `resolved_image` cannot be pulled or started. The team's `default_image` is required and immutable through any operator or admin path.
