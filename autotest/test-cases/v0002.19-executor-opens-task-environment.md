# Test case: v0002.19-executor-opens-task-environment

## Implements

`executor` — `### Requirement: Docker Executor opens task-bound environments from State Registry`.

## Intent

Verify environment values are opened only after a successful FIFO claim (`200 claimed`) and are confined to the assigned runtime.

## Preconditions

The concrete `team-a` Executor (`executor_docker_opehands` per the platform `executor_<runtime>_<tool>` convention documented in AGENTS.md; `runtime = docker`, `tool = openhands`) has received `200 claimed` for a `team-a` task with a same-team environment reference and signed scope token containing matching `team_id`, `project_id` (required claim; null only when the canonical environment has no project scope), `task_id`, `environment_id`, `executor_id`, `audience` (literal `state-registry.environment.open`), `key_id`, `issued_at`, and unexpired `expiry` (`expiry > issued_at`, `expiry - issued_at <= 5 minutes`); the protected header carries `alg` (allow-listed `HS256`/`HS384`/`HS512`), `kid`, and `typ` (`scope-token+json`) with `kid == payload key_id`; and `issued_at <= server_now + 30 seconds`. The configured AES-256-GCM data key is loaded.

## Steps

1. Call `GET /v1/environments/{environment_id}/open?task_id={task_id}` with the assigned Executor identity and the compact three-part scope token carried in the `X-FlowAI-Scope-Token` request header (no scope-token fields in the body).
2. Start only that task container with the returned values.
3. Stop the task and inspect Executor logs and durable storage.

## Expected outcome

The open request returns `200` with env-style values only after State Registry verifies that the query `task_id` matches the payload `task_id` claim and the canonical assigned task, that the protected-header `kid` equals the payload `key_id`, that the allow-listed HMAC MAC verifies under constant-time comparison, that the `audience`, `issued_at`/`expiry` window, every claim (including the project-scope rule for `project_id`), the authenticated Executor team, same-team assignment, project/task applicability, and non-terminal task state all match, and that the `key_id` falls inside the documented active key window; the State Registry then performs the local AES-256-GCM decrypt operation with associated-data binding team identifier, logical secret identifier, and version. Values are injected only into the assigned task's container; and plaintext, nonce bytes, ciphertext bytes, authentication tag bytes, key material, and associated-data values beyond identifier-level metadata appear in neither logs nor durable Executor storage, error responses, or any audit entry.
