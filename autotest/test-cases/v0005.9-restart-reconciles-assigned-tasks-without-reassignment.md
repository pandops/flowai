# Test case: v0005.9-restart-reconciles-assigned-tasks-without-reassignment

## Implements

`executor` — `### Requirement: K8s Executor reconciles to State Registry after restart without reassignment`.

`executor` — `### Requirement: K8s Executor remains non-authoritative`.

## Intent

Verify that after Kubernetes replaces the single-replica K8s Executor
Deployment Pod, the replacement Executor
loads its persistent recovery cache and durable event outbox,
re-registers with the same bound `team_id` and `authorized_tag`,
reuses its State Registry-generated cached `executor_id`,
loads claimed non-terminal tasks exclusively from persistent cache, and
matches each cached `owner_command_id` to the existing Pod's `flowai.command_id`
label to identify which in-flight Pod to continue observing,
re-attaches to existing Pods in Kubernetes without creating new
Pods, reconnects to the same OpenHands conversation at its previous
progress, retries pending events with their original `event_id`, does not
duplicate a `running` event for an already-running
task, and emits exactly one terminal `finished` or `failed` event from the
OpenHands tool-level terminal signal rather than from Pod exit.

## Preconditions

State Registry and PostgreSQL are running; the harness has created a fresh,
uniquely named local `kind` cluster for this suite run and will capture
diagnostics before deleting it during teardown rather than reuse an existing
cluster. The OpenHands API is mocked deterministically for restart/reconnect
timing. A K8s Executor runs inside the cluster as a single-replica
Deployment with a dedicated ServiceAccount, namespace-scoped RBAC,
non-overlapping replacement strategy, and `<cache_dir>` backed by a
dynamically provisioned `ReadWriteOnce` PVC. A repository-pinned
local-path provisioner is ready, and the claim explicitly names its
test StorageClass rather than relying on a cluster default. The
Executor is configured with `scope = team`,
`team_id = team-A`, and exactly one
`authorized_tag = k8s-cluster-A`. v0009: the State Registry does
not authenticate the Executor connection — the deployment network
policy owns the Executor-caller boundary; the State Registry
validates the canonical record shape (scope, immutable `team_id`,
exactly one tag) and never derives identity from a peer certificate.
One task `task_id_running` has been
FIFO-claimed by `k8s-exec-A` with
`owner_command_id = command-running` and a Kubernetes Pod named
`pod-running` is alive in the cluster carrying the labels
`flowai.executor_id = k8s-exec-A`,
`flowai.team_id = team-A`,
`flowai.task_id = task_id_running`,
`flowai.command_id = command-running`,
`flowai.executor_scope = team`,
`flowai.resolved_image_source`, and
`flowai.runtime = k8s`; the latest task event in its history is a
Registry-appended `created` event (with non-null
`executor_id = k8s-exec-A` and payload meaning `task task_id_running
loaded by k8s-exec-A`) followed by an Executor-appended `running`
event with `executor_id = k8s-exec-A`, `team_id = team-A`, and
`event_id = 0190-k8s-running-pre-restart`. A second task
`task_id_terminal` has been FIFO-claimed by `k8s-exec-A` with
`owner_command_id = command-terminal` and its Pod `pod-terminal`
carries the same canonical labels with
`flowai.task_id = task_id_terminal` and
`flowai.command_id = command-terminal`; `pod-terminal` is still alive
at the moment of restart and OpenHands will emit
`execution_status = finished` after reconciliation.

## Steps

1. Delete the running K8s Executor Deployment Pod and wait for Kubernetes to
   start a replacement Pod authenticated as `k8s-exec-A` and bound to
   `team_id = team-A`. Confirm the local-path PVC and PV remain bound with the
   same identities and both task Pods remain alive because neither has an
   owner reference to the deleted Executor Pod.
   Preserve and mount the Executor recovery volume containing owner-only
   `<cache_dir>/executor.db` with task/Pod/conversation mappings, a stable
   claim intent, and an event outbox entry whose Registry response was lost
   after send. Verify the bbolt database has a supported schema version and
   the versioned `metadata`, `assignments`, and `event_outbox` buckets.
   Confirm the replacement process acquires `<cache_dir>/executor.lock` before its
   PUT refresh. While it holds the lock, start a second process against the
   same cache volume and capture its health and outbound calls.
2. Have the replacement process re-register via
   `PUT /v1/executors/k8s-exec-A` with the same
   `scope = team`, `team_id = team-A`,
   `authorized_tag = k8s-cluster-A`, observed `max_capacity`,
   observed `running_count`, and metadata.
3. Have the replacement process attempt to re-register with
   `team_id = team-B` (a divergent `team_id`) and confirm the
   rejection.
4. Have the replacement process read `executor_id = k8s-exec-A` from the cache and
   load its claimed non-terminal tasks exclusively from
   that cache, without calling any assignments-list endpoint.
   Inspect the bbolt metadata, assignment, and outbox entries and confirm no
   environment or secret plaintext is stored. Simulate an
   uncertain claim response and confirm the retry uses the original
   `(task_id, command_id)`; confirm a new assignment row is committed after
   `200 claimed` and before any `running` event or Pod creation.
5. Have the replacement process match each cached task's `owner_command_id`
   (`command-running` and `command-terminal`)
   to the existing Pod labels `flowai.command_id` to identify
   `pod-running` and `pod-terminal`, then re-attach to those Pods
   through the Kubernetes API without creating new Pods.
   Reconnect to the cached OpenHands conversation identity and retry the
   uncertain outbox event with its original `event_id`; State Registry
   idempotently returns the original acceptance without a duplicate row.
6. Have the reconciled OpenHands conversation emit
   `execution_status = finished` while `pod-terminal` remains running.
   Have the replacement process emit a single `finished` event to
   `POST /v1/tasks/task_id_terminal/events` with the seven-field
   envelope (`task_id = task_id_terminal`,
   `executor_id = k8s-exec-A`, `team_id = team-A`,
   `event_id = 0190-k8s-finished-post-restart`,
   `event_type = finished`, `occurred_at = 2026-07-13T16:30:00Z`,
   `payload = {"phase":"terminal_state","openhands_status":"finished"}`),
   receive `202 accepted`, wait the configured `finished_cleanup_delay`,
   and then idempotently delete `pod-terminal` without another task event.
7. Read `task_id_running` and `task_id_terminal` and their event
   histories through the API Gateway.

## Expected outcome

The deleted Executor Pod is replaced by exactly one ready Deployment Pod. The
same PVC is mounted, both task Pods survive without recreation, and no task Pod
is garbage-collected with the old Executor Pod. The PVC was dynamically
provisioned through the explicitly named pinned local-path StorageClass, not an
ambient default, and remains bound to the same PV across replacement. Step 2
returns `200`; the
stored `team_id`, `authorized_tag`, and
Executor record remain unchanged. Step 3 returns `403` (or
`409 team_id_immutable`) without changing the stored `team_id`.
Step 4 loads both `task_id_running` and `task_id_terminal` from persistent
cache with their immutable `owner_command_id` values and performs no
assignments-list request. The cache is owner-only bbolt with the expected
schema version and versioned `metadata`, `assignments`, and `event_outbox`
buckets containing the Registry-generated executor ID, claim intents,
assignments, and outbox delivery states; it contains no environment or secret
plaintext and is never silently reset or replaced. An
uncertain claim is retried with the same command ID, and no `running` event or
Pod creation can precede the durable assignment row. No new Pod is created for
`task_id_running`; the existing `pod-running` is re-attached by
matching its `flowai.command_id` label to `task_id_running`'s
`owner_command_id`. Step 6 returns `202 accepted`. The final reads
return: `task_id_running` with `current_state = running` (unchanged),
an event history of exactly `[created, running]` where the `created`
row carries non-null `executor_id = k8s-exec-A` and a payload meaning
`task task_id_running loaded by k8s-exec-A`, and NO new `running`
row after the restart; `task_id_terminal` with
`current_state = finished`, `executor_id = k8s-exec-A`, and an
ordered event history of exactly `[created, running, finished]`
where the pre-restart `running` row keeps `0190-k8s-running-pre-restart`
and the post-restart `finished` row carries
`0190-k8s-finished-post-restart` with `team_id = team-A`. The Pod remains
counted against local capacity during `finished_cleanup_delay`, is deleted
afterward, and its exit code never determines task success. No `dispatched`
event appears in either history at any time.

If the same scenario is repeated with a missing, unreadable, corrupt, or
different-`executor_id` cache, an unknown newer schema, or a failed migration,
the Executor becomes unhealthy, claims no new task, and leaves existing Pods
untouched for operator recovery.
The concurrent second process cannot acquire `executor.lock`, remains
unhealthy, and sends no Registry request or Kubernetes mutation.
