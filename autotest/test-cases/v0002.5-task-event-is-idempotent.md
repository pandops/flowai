# Test case: v0002.5-task-event-is-idempotent

## Implements

`state-registry` — `### Requirement: State Registry accepts Executor-emitted lifecycle events under the Executor's ownership scope`.

## Intent

Verify that retrying an Executor-emitted lifecycle event does not duplicate history or advance the projection twice.

## Preconditions

A `team-a` task is claimed by authenticated `team-a` Executor `executor-1` (`tasks.executor_id = executor-1`, `tasks.owner_command_id = C-1`) and its ordered event list is `[created]` (the Registry-appended first claim event with non-null `executor_id = executor-1` and payload `task <task_id> loaded by executor-1`).

## Steps

1. Post a `running` event to `POST /v1/tasks/{task_id}/events` as `executor-1`, carrying envelope `team_id = team-a`, non-null `executor_id = executor-1`, stable `event_id = 0190-running-0001`, `event_type = running`, `occurred_at = 2026-07-13T10:00:00Z`, and `payload = {"runtime":"openhands"}`.
2. Repeat the identical request with the same event fields.
3. Read the task and `GET /v1/tasks/{task_id}/events` through trusted Gateway context for `team-a`.

## Expected outcome

Both posts return the same `202 accepted` result; the task remains owned by `team-a` and projects to `running`; and the ordered event list is exactly `[created, running]`, with `event_id = 0190-running-0001` present once, its envelope `team_id = team-a` equal to the authenticated Executor's team and the task's `team_id`, its non-null `executor_id` unchanged, and every other submitted field preserved. No `dispatched` event exists.
