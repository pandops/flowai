# Test case: v0002.23-successful-ordered-lifecycle

## Implements

`state-registry` — `### Requirement: State Registry defines the task lifecycle as pending then created then running then terminal`.

`state-registry` — ``### Requirement: State Registry appends the first `created` event atomically on successful claim``.

## Intent

Verify the successful happy path projects `pending -> created -> running -> finished` from the immutable ordered event history; the FIRST `created` event is Registry-appended in the claim transaction with non-null `executor_id = claiming_executor`; only `running` and `finished` are Executor-emitted.

## Preconditions

State Registry and PostgreSQL are running; a listener and an Executor are each bound to `team-a`; the Executor is registered with the task's exact tag; trusted Gateway context for `team-a` can read tasks and events.

## Steps

1. Submit a new `team-a` task through the listener and retain its `task_id`; the task is `current_state = pending` with empty event history.
2. From the same-team Executor, claim the oldest eligible pending task with `command_id` and observe `200 claimed`.
3. Post `running` with envelope `team_id = team-a` that State Registry verifies against the authenticated Executor team, non-null assigned `executor_id`, and a strictly later `(occurred_at, event_id)` tuple.
4. Post `finished` with `team_id = team-a`, the same assigned `executor_id`, and a strictly later tuple.
5. Read the task and history through trusted Gateway context for `team-a`.

## Expected outcome

Ingestion commits the `pending` task with no event. Claim appends the FIRST Registry-emitted `created` event with `executor_id = claiming_executor` and payload meaning `task <task_id> loaded by <executor_id>`, sets `tasks.owner_command_id`, `tasks.executor_id`, `tasks.claimed_at`, `tasks.resolved_image`, and `tasks.image_source`. State Registry verifies `team_id = team-a` against the authenticated Executor team for every Executor-emitted write. The task retains immutable `team_id = team-a`, projects to `finished`, and remains assigned to the same Executor. The ordered history is exactly `[created, running, finished]`; the Registry-appended `created` row has non-null `executor_id` identifying the claiming Executor; the Executor-emitted `running` and `finished` rows have non-null assigned `executor_id` equal to the claimer, submitted `team_id` equal to the task team, and preserved identifiers and payloads; no `dispatched` event exists.
