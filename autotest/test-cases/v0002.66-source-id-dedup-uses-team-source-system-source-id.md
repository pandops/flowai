# Test case: v0002.66-source-id-dedup-uses-team-source-system-source-id

## Implements

`state-registry` — `### Requirement: State Registry deduplicates listener tasks within a team`.

## Intent

Verify that listener deduplication uses `(team_id, source_system_id, source_id)`, that the same `source_id` MAY exist independently in different teams only because each team registers its own source system, never because one source-system identity is shared across teams, and that a cross-team submission through a single shared source-system identity is rejected.

## Preconditions

State Registry and PostgreSQL are running; `team-a` and `team-b` exist; `source-system-a` is registered against `team-a`; a listener identity for `team-a` and the authorized `source-system-a` is configured.

## Steps

1. Listener for `team-a` submits `source_id = D-1` under `source-system-a` (the authorized binding) and observes the canonical pending task.
2. Listener for `team-a` retries the same triple and observes the same canonical task with no new event.
3. Admin attempts to register a separate source system `source-system-b` against `team-b` and then submits `source_id = D-1` from a `team-b` listener under `source-system-b`; observe the new canonical team-owned task.
4. Listener for `team-b` against `source-system-a` (which belongs to `team-a`) submits `source_id = D-1` and observes the response.
5. Listener for `team-a` submits a different `source_id` against the same authorized `source-system-a` and observes a fresh pending task.

## Expected outcome

Step 1 commits a `team-a` pending task. Step 2 returns the existing canonical task with no event. Step 3 commits an independent `team-b` pending task because `source-system-b` is a separate identity registered under `team-b`. Step 4 is rejected without persisting or acknowledging because `source-system-a` belongs to `team-a`, not `team-b`. Step 5 commits a fresh `team-a` pending task.
