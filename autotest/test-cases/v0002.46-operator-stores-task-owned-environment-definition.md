# Test case: v0002.46-operator-stores-task-owned-environment-definition

## Implements

`state-registry` — `### Requirement: State Registry stores team-owned environment definitions`.

## Intent

Verify a same-team operator can store a task-owned environment definition with a parent `task_id` and that only the parent task in the same team may use it.

## Preconditions

- Web UI, trusted API Gateway, State Registry, and PostgreSQL are running.
- A `team-a` task exists and has been ingested through the listener path with `created` state.
- Trusted Gateway context contains verified `operator_id`, immutable `team_id = team-a`, display-only `team_name`, and `request_id`.

## Steps

1. Through Web UI and API Gateway under trusted Gateway context for `team-a`, submit a non-secret environment definition that names the parent `task_id` of the existing task.
2. Read the definition back through the same trusted team context and inspect `parent_task_id`, `team_id`, and the rest of the response.
3. List team-owned environments through the same trusted team context and confirm the new row appears with the expected `parent_task_id`.
4. Query the team-scoped audit entry for the create action and confirm `parent_task_id` is recorded and the audit does not contain non-secret values.

## Expected outcome

The create call returns `201` with a stable `environment_id`, the response carries `team_id = team-a` and `parent_task_id` equal to the existing task, the list includes the row with that parent, the audit entry identifies the resource and team without non-secret value leakage, and no foreign or cross-team data appears in any response.
