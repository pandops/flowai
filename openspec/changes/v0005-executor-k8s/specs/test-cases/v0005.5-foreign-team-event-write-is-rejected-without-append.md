# Test case: v0005.5-foreign-team-event-write-is-rejected-without-append

## Implements

`executor` — `### Requirement: K8s Executor scopes discovery, claim, task events, environment opens, and control reads to its bound team`.

## Intent

Verify the State Registry rejects a task-event post whose `team_id`
does not match the Executor's bound `team_id` with a non-revealing
`404` and appends no event, and that the K8s Executor therefore
creates no Pod for the cross-team identifier.

## Preconditions

State Registry and PostgreSQL are running. `team-B` is registered with
one `pending` task (`team_id = team-B`,
`required_tag = k8s-cluster-B`). A K8s Executor service identity
`k8s-exec-A` bound to `team_id = team-A` is registered with
`scope = team` and `authorized_tag = k8s-cluster-A` but also
mistakenly holds the `team-B` task's `task_id` from a prior
cross-team discovery attempt.

## Steps

1. As `k8s-exec-A`, post a `running` event to
   `POST /v1/tasks/{task_id_B}/events` carrying
   `task_id = task_id_B`, `executor_id = k8s-exec-A`,
   `team_id = team-A`, `event_id = 0190-k8s-running-cross-0001`,
   `event_type = running`, `occurred_at = 2026-07-13T16:10:00Z`, and
   `payload = {"pod_name":"pod-cross"}`.
2. As `k8s-exec-A`, retry the same `running` event byte-for-byte with
   the same `event_id`.
3. Read the `team-B` task and its event history through the API
   Gateway.
4. Inspect the K8s Executor's local Pod/state for any Pod created for
   `task_id_B`.

## Expected outcome

Both event posts return a non-revealing `404` whose body shape is
indistinguishable from an unknown `task_id` response. The `team-B`
task read returns `200` with `current_state = pending` (the task
was never claimed because the cross-team event write is rejected) and
`executor_id = null`; its event history is empty because no claim
ever appended a `created` event for a foreign-team identifier, and no
event was appended for the rejected cross-team write. No Pod exists
for `task_id_B` in the K8s Executor's local state.
