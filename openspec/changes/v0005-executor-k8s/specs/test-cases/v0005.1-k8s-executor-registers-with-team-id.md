# Test case: v0005.1-k8s-executor-registers-with-team-id

## Implements

`executor` — `### Requirement: K8s Executor binds to a single authenticated team identity`.

`executor` — `### Requirement: K8s Executor participates in State Registry task approvals`.

## Intent

Verify a K8s Executor registers with exactly one `team_id`, exactly one
`authorized_tag`, observed `max_capacity`, observed `running_count`, optional
display-only `team_name`, and runtime metadata, all bound to the authenticated
Executor service identity, and that the State Registry exposes the bound
`team_id` on subsequent reads.

## Preconditions

State Registry and PostgreSQL are running. An authenticated Executor service
identity `k8s-exec-A` is bound to `team_id = team-A`. Executor identifier
`k8s-exec-A-1` does not exist.

## Steps

1. Send `PUT /v1/executors/k8s-exec-A-1` with `executor_type = "k8s"`,
   `team_id = team-A`, `authorized_tag = k8s-cluster-1`, `team_name =
   "Alpha Cluster"` (display-only), `max_capacity = 2`, `running_count = 0`,
   and runtime metadata.
2. Read `k8s-exec-A-1` through the API Gateway Executor read API.
3. Re-send the same `PUT /v1/executors/k8s-exec-A-1` request unchanged.

## Expected outcome

The first registration returns `200` and stores `team_id = team-A`,
`authorized_tag = k8s-cluster-1`, `team_name = "Alpha Cluster"`,
`max_capacity = 2`, and `running_count = 0` on the canonical Executor record.
The read returns `200` with the same `team_id` and `authorized_tag`. The
idempotent re-registration returns `200` and the stored `team_id`,
`authorized_tag`, and capacity values remain unchanged.
