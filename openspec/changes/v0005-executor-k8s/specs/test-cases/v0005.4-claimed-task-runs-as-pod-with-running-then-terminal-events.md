# Test case: v0005.4-claimed-task-runs-as-pod-with-running-then-terminal-events

## Implements

`executor` — `### Requirement: K8s Executor runs only Kubernetes Pods`.

## Intent

Verify the same-team FIFO claim returns `200 claimed` with
`tasks.resolved_image`, `tasks.image_source`, `tasks.claimed_at`,
`tasks.owner_command_id`, `environment_id`, and the State
Registry-issued scope token; the K8s Executor uses `resolved_image`
verbatim and refuses the task if the image cannot be pulled or started;
the K8s Executor emits a `running` event after `200 claimed`, creates
the Kubernetes Pod carrying the canonical `task_id`, `command_id`,
`team_id`, `executor_id`, `executor_scope`, and `resolved_image_source`
labels and the runtime label `flowai.runtime=k8s`; and the K8s
Executor uses the OpenHands terminal conversation status rather than the
long-running server Pod's exit code, emits exactly one terminal `finished`
or `failed` event,
whose envelope matches the seven-field shape, all scoped to the
Executor's bound `team_id`, retains the Pod for the configured
`finished_cleanup_delay` or `failed_cleanup_delay`, selected by the accepted
terminal event, while it remains
counted against capacity, and then deletes it idempotently. Verify the
State Registry appends the
FIRST lifecycle event `created` with non-null `executor_id` equal to
the claiming Executor and a payload meaning `task <task_id> loaded
by <executor_id>`; no `dispatched` event appears.

## Preconditions

State Registry and PostgreSQL are running. An authenticated Executor
service identity `k8s-exec-A` bound to `team_id = team-A` is
registered with `scope = team`, exactly one
`authorized_tag = k8s-cluster-A`, `max_capacity = 1`, and
`running_count = 0`. Two FIFO-ordered `pending` tasks have
`team_id = team-A`, `required_tag = k8s-cluster-A`, and environment
identifiers: `task_finished` followed by `task_failed`. A Kubernetes API
fake and controllable clock are wired so the test can capture Pod
create/watch/delete calls and cleanup deadlines.

## Steps

1. As `k8s-exec-A`, request
   `GET /v1/executors/k8s-exec-A/tasks?tag=k8s-cluster-A` and capture
   `task_finished` as the oldest matching `task_id`.
2. As `k8s-exec-A`, request
   `POST /v1/executors/k8s-exec-A/claim` for that `task_id` with a
   stable `command_id` and capture the response (including
   `resolved_image`, `image_source`, `claimed_at`, the
   `tasks.owner_command_id`, `environment_id`, and the State
   Registry-issued team-bound scope token).
3. As `k8s-exec-A`, post a `running` event to
   `POST /v1/tasks/{task_id}/events` carrying `task_id`,
   `executor_id = k8s-exec-A`, `team_id = team-A`,
   `event_id = 0190-k8s-running-0001`, `event_type = running`,
   `occurred_at = 2026-07-13T16:00:00Z`, and
   `payload = {"pod_name":"pod-1"}`.
4. Have the K8s Executor create the Kubernetes Pod with the agent
   runtime using `tasks.resolved_image` verbatim and observe the Pod
   create call; confirm the Pod carries the immutable labels
   `flowai.executor_id`, `flowai.team_id`, `flowai.task_id`,
   `flowai.command_id`, `flowai.executor_scope`,
   `flowai.resolved_image_source`, and the runtime label
   `flowai.runtime=k8s`.
5. Have OpenHands emit terminal `execution_status = finished` while its
   long-running agent-server Pod remains running. Have the K8s Executor
   post exactly one `finished` event with the same
   envelope shape (`task_id`, `executor_id`, `team_id = team-A`,
   `event_id = 0190-k8s-finished-0001`, `event_type = finished`,
   `occurred_at = 2026-07-13T16:05:00Z`,
   `payload = {"phase":"terminal_state","openhands_status":"finished"}`).
6. Configure `finished_cleanup_delay = 30s` and
   `failed_cleanup_delay = 5s`; verify this successfully finished Pod remains
   present and counted in `running_count` before the delay expires, then
   advance the test clock through the deadline and verify one idempotent
   Pod deletion with no additional task event.
7. After cleanup frees the slot, repeat discovery, claim, accepted
   `running`, and Pod creation for `task_failed`. Have OpenHands emit
   terminal `execution_status = failed`; post exactly one `failed` event
   with `payload = {"phase":"terminal_state","openhands_status":"failed"}`
   and receive `202 accepted`.
8. Verify the failed Pod remains present and counted before its configured
   `failed_cleanup_delay = 5s`, is not retained for the finished delay,
   and is deleted idempotently when the five-second deadline expires with
   no additional task event.
9. Read both canonical tasks and their event histories through the API
   Gateway.

## Expected outcome

Step 1 returns `200` with the matching `task_id`. Step 2 returns
`200 claimed` and includes `tasks.resolved_image`,
`tasks.image_source`, `tasks.claimed_at`,
`tasks.owner_command_id`, `environment_id`, and the State
Registry-issued scope token. Step 3 returns `202 accepted`. The
Kubernetes Pod is created ONLY after the `running` event post returns
`202 accepted`, uses `tasks.resolved_image` verbatim, and carries the
canonical labels listed in step 4. Step 5 returns `202 accepted`. The
`task_finished` returns `200` with `current_state = finished` and
`executor_id = k8s-exec-A`; the event read returns exactly three
events ordered `[created, running, finished]`. The Registry-appended
`created` event carries non-null `executor_id = k8s-exec-A` and a
payload meaning `task <task_id> loaded by k8s-exec-A`; the
`running` and `finished` rows each carry `team_id = team-A`, the
seven-field envelope, and the submitted `event_id`, `occurred_at`,
and `payload` values unchanged. No `dispatched` event appears in the
history at any time. The Pod exit code is never consulted as the
successful-completion signal. Its Pod occupies the local capacity slot for
exactly `finished_cleanup_delay`, is deleted once afterward, and cleanup
emits no fourth task event. `task_failed` returns `current_state = failed`
with exactly `[created, running, failed]`; its Pod remains counted for
`failed_cleanup_delay`, is deleted after that independently configured
deadline, and cleanup appends no fourth event.
