# Test case: v0005.3-team-isolated-discovery-and-approval-no-leak

## Implements

`executor` — `### Requirement: K8s Executor scopes discovery, approval, task events, environment opens, and control reads to its bound team`.

`executor` — `### Requirement: K8s Executor participates in State Registry task approvals`.

## Intent

Verify that collection-level discovery filters by `team_id` BEFORE shaping
results, so a tag whose matching `created` tasks all belong to other teams
yields the NORMAL empty result (`204 No Content` or `200` with an empty task
list and no count, cursor, total, or pagination metadata), indistinguishable
from "no tasks match this tag anywhere"; that point-resource lookups for a
foreign-team `task_id` (approval, task detail read) return a non-revealing
`404` indistinguishable from "resource does not exist"; and that the K8s
Executor never creates a Pod and never appends an event for any cross-team
identifier.

## Preconditions

State Registry and PostgreSQL are running. Two authenticated Executor service
identities exist: `k8s-exec-A` bound to `team_id = team-A` and `k8s-exec-B`
bound to `team_id = team-B`. Each K8s Executor is registered with exactly one
`authorized_tag` (`k8s-cluster-A` for `k8s-exec-A`, `k8s-cluster-B` for
`k8s-exec-B`). Two `created` tasks exist: one with
`team_id = team-A` and `required_tag = k8s-cluster-A`, the other with
`team_id = team-B` and `required_tag = k8s-cluster-B`.

## Steps

1. As `k8s-exec-A`, request
   `GET /v1/executors/k8s-exec-A/tasks?tag=k8s-cluster-A` and record the
   returned payload and any `count`, `cursor`, `total`, or pagination
   metadata present in the response.
2. As `k8s-exec-A`, request
   `GET /v1/executors/k8s-exec-A/tasks?tag=k8s-cluster-B` and record the
   returned payload and any `count`, `cursor`, `total`, or pagination
   metadata present in the response.
3. As `k8s-exec-A`, request
   `POST /v1/executors/k8s-exec-A/approvals` for the `team-B` task's
   `task_id`.
4. As `k8s-exec-A`, read the foreign task by `task_id` via the task detail
   read API (for example `GET /v1/tasks/{task_id}`).
5. Read both tasks and their event histories through the API Gateway.
6. Inspect the K8s Executor's local Pod/state for any Pod created for the
   `team-B` task.

## Expected outcome

Step 1 returns `200` with exactly the `team-A` task summary and no
`team-B` rows. Step 2 returns `204 No Content` (or `200` with an empty
task list); the response payload contains NO `count`, `cursor`, `total`,
or pagination metadata that would distinguish this outcome from "no
tasks match this tag anywhere". Step 3 returns a non-revealing
`404` whose body shape is indistinguishable from "resource does not
exist" for the `team-B` `task_id`. Step 4 returns a non-revealing `404`
identical in shape to step 3. No Pod exists for the `team-B` task and no
event has been appended to its event history. Both task reads in step 5
return `200` with `current_state = created` and `executor_id = null`;
their event histories remain `[created]` only.
