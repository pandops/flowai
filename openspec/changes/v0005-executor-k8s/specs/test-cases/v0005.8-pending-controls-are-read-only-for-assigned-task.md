# Test case: v0005.8-pending-controls-are-read-only-for-assigned-task

## Implements

`executor` — `### Requirement: K8s Executor reads pending controls only for assigned tasks in its bound team`.

## Intent

Verify the K8s Executor reads and applies pending operator controls
only for tasks assigned to it in its bound `team_id`, and that any
cross-team or unassigned control read returns a non-revealing `404`
with no control applied.

## Preconditions

State Registry and PostgreSQL are running. Two authenticated K8s
Executor service identities exist: `k8s-exec-A` bound to
`team_id = team-A` and `k8s-exec-B` bound to `team_id = team-B`. Each
is registered with `scope = team` and exactly one `authorized_tag`
(`k8s-cluster-A` and `k8s-cluster-B` respectively). Two claimed
tasks exist: `task_id_A` projected to `created` and assigned to
`k8s-exec-A` in `team-A`, and `task_id_B` projected to `created` and
assigned to `k8s-exec-B` in `team-B`. Each task has a pending
operator control recorded against it through the API Gateway.

## Steps

1. As `k8s-exec-A`, request `GET /v1/tasks/task_id_A/controls` and
   capture the response.
2. Apply the control to `task_id_A`'s Pod and observe the resulting
   task events posted to `POST /v1/tasks/task_id_A/events` carry the
   seven-field envelope (`task_id`, `executor_id`,
   `team_id = team-A`, `event_id`, `event_type`, `occurred_at`,
   `payload`).
3. As `k8s-exec-A`, request `GET /v1/tasks/task_id_B/controls`.
4. As `k8s-exec-B`, request `GET /v1/tasks/task_id_A/controls`.
5. Read both tasks and their event histories through the API Gateway.

## Expected outcome

Step 1 returns `200` with the pending control for `task_id_A`;
`k8s-exec-A` applies it to `task_id_A`'s Pod and the resulting task
events include `team_id = team-A`. Step 3 returns a non-revealing
`404` with no control applied to `task_id_B`. Step 4 returns a
non-revealing `404` with no control applied to `task_id_A`. Both
task reads return `200` with `executor_id` unchanged and only the
expected task events appended; `task_id_A`'s history grows by exactly
the control-applied events (and continues to show the FIFO claim
contract with `created` as the Registry-appended first event); no
`dispatched` event is ever present; `task_id_B`'s history does not
include any cross-team read or apply.
