# Test case: v0005.9-restart-reconciles-assigned-tasks-without-reassignment

## Implements

`executor` — `### Requirement: K8s Executor reconciles to State Registry after restart without reassignment`.

`executor` — `### Requirement: K8s Executor remains non-authoritative`.

## Intent

Verify that after a K8s Executor process restart the Executor re-registers
with the same bound `team_id` and `authorized_tag`, re-reads its assigned
tasks from the durable State Registry state, observes existing Pods in
Kubernetes, does not duplicate a `running` event for an already-running
task, and emits exactly one terminal `finished` or `failed` event per Pod
that terminates.

## Preconditions

State Registry and PostgreSQL are running. An authenticated K8s Executor
service identity `k8s-exec-A` bound to `team_id = team-A` is registered with
exactly one `authorized_tag = k8s-cluster-A`. One task `task_id_running`
has been approved to `k8s-exec-A` and a Kubernetes Pod named
`pod-running` is alive in the cluster; the latest task event in its history
is a registry-accepted `running` event with `executor_id = k8s-exec-A`,
`team_id = team-A`, `event_id = 0190-k8s-running-pre-restart`. A second
task `task_id_terminal` has been approved to `k8s-exec-A` and its Pod
`pod-terminal` is still alive at the moment of restart but will be
terminated after the restart completes.

## Steps

1. Trigger a hard K8s Executor process restart, then start a fresh
   process authenticated as `k8s-exec-A` bound to `team_id = team-A`.
2. Have the fresh process re-register via `PUT /v1/executors/k8s-exec-A`
   with the same `team_id = team-A`, `authorized_tag = k8s-cluster-A`,
   observed `max_capacity`, observed `running_count`, and metadata.
3. Have the fresh process attempt to re-register with
   `team_id = team-B` (a divergent `team_id`) and confirm the rejection.
4. Have the fresh process re-read its assigned tasks from the State
   Registry (filtered by `executor_id = k8s-exec-A` and `team_id = team-A`).
5. Have the fresh process observe the existing Pods `pod-running` and
   `pod-terminal` in Kubernetes.
6. Have the fresh process terminate `pod-terminal` and emit a single
   `finished` event to `POST /v1/tasks/task_id_terminal/events` with the
   seven-field envelope (`task_id = task_id_terminal`,
   `executor_id = k8s-exec-A`, `team_id = team-A`,
   `event_id = 0190-k8s-finished-post-restart`, `event_type = finished`,
   `occurred_at = 2026-07-13T16:30:00Z`,
   `payload = {"exit_code":0}`).
7. Read `task_id_running` and `task_id_terminal` and their event histories
   through the API Gateway.

## Expected outcome

Step 2 returns `200` and the stored `team_id`, `authorized_tag`, and
Executor record remain unchanged. Step 3 returns `403` (or
`409 team_id_immutable`) without changing the stored `team_id`. Step 4
returns `200` with both `task_id_running` and `task_id_terminal` listed.
No new Pod is created for `task_id_running`; the existing `pod-running`
is re-attached. Step 6 returns `202 accepted`. The final reads return:
`task_id_running` with `current_state = running` (unchanged), an event
history of exactly `[created, dispatched, running]`, and NO new
`running` row after the restart; `task_id_terminal` with
`current_state = finished`, `executor_id = k8s-exec-A`, and an ordered
event history of exactly `[created, dispatched, running, finished]`
where the pre-restart `running` row keeps `0190-k8s-running-pre-restart`
and the post-restart `finished` row carries `0190-k8s-finished-post-restart`
with `team_id = team-A`.
