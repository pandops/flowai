# Test case: v0005.9-restart-reconciles-assigned-tasks-without-reassignment

## Implements

`executor` — `### Requirement: K8s Executor reconciles to State Registry after restart without reassignment`.

`executor` — `### Requirement: K8s Executor remains non-authoritative`.

## Intent

Verify that after a K8s Executor process restart the Executor
re-registers with the same bound `team_id` and `authorized_tag`,
re-reads its claimed non-terminal tasks from the durable State
Registry state by canonical `tasks.executor_id =
authenticated_executor_id`, matches each returned task's immutable
`tasks.owner_command_id` to the existing Pod's `flowai.command_id`
label to identify which in-flight Pod to continue observing,
re-attaches to existing Pods in Kubernetes without creating new
Pods, does not duplicate a `running` event for an already-running
task, and emits exactly one terminal `finished` or `failed` event from the
OpenHands tool-level terminal signal rather than from Pod exit.

## Preconditions

State Registry and PostgreSQL are running. An authenticated K8s
Executor service identity `k8s-exec-A` bound to `team_id = team-A`
is registered with `scope = team` and exactly one
`authorized_tag = k8s-cluster-A`. One task `task_id_running` has been
FIFO-claimed by `k8s-exec-A` with
`owner_command_id = command-running` and a Kubernetes Pod named
`pod-running` is alive in the cluster carrying the labels
`flowai.executor_id = k8s-exec-A`,
`flowai.team_id = team-A`,
`flowai.task_id = task_id_running`,
`flowai.command_id = command-running`,
`flowai.executor_scope = team`,
`flowai.resolved_image_source`, and
`flowai.runtime = k8s`; the latest task event in its history is a
Registry-appended `created` event (with non-null
`executor_id = k8s-exec-A` and payload meaning `task task_id_running
loaded by k8s-exec-A`) followed by an Executor-appended `running`
event with `executor_id = k8s-exec-A`, `team_id = team-A`, and
`event_id = 0190-k8s-running-pre-restart`. A second task
`task_id_terminal` has been FIFO-claimed by `k8s-exec-A` with
`owner_command_id = command-terminal` and its Pod `pod-terminal`
carries the same canonical labels with
`flowai.task_id = task_id_terminal` and
`flowai.command_id = command-terminal`; `pod-terminal` is still alive
at the moment of restart and OpenHands will emit
`execution_status = finished` after reconciliation.

## Steps

1. Trigger a hard K8s Executor process restart, then start a fresh
   process authenticated as `k8s-exec-A` bound to `team_id = team-A`.
2. Have the fresh process re-register via
   `PUT /v1/executors/k8s-exec-A` with the same
   `scope = team`, `team_id = team-A`,
   `authorized_tag = k8s-cluster-A`, observed `max_capacity`,
   observed `running_count`, and metadata.
3. Have the fresh process attempt to re-register with
   `team_id = team-B` (a divergent `team_id`) and confirm the
   rejection.
4. Have the fresh process re-read its claimed, non-terminal tasks
   from the State Registry by canonical
   `tasks.executor_id = authenticated_executor_id` (`k8s-exec-A`),
   WITHOUT filtering by `tasks.owner_command_id`; the response lists
   each claimed task and each task row carries its immutable
   `tasks.owner_command_id`.
5. Have the fresh process match each returned task's
   `tasks.owner_command_id` (`command-running` and `command-terminal`)
   to the existing Pod labels `flowai.command_id` to identify
   `pod-running` and `pod-terminal`, then re-attach to those Pods
   through the Kubernetes API without creating new Pods.
6. Have the reconciled OpenHands conversation emit
   `execution_status = finished` while `pod-terminal` remains running.
   Have the fresh process emit a single `finished` event to
   `POST /v1/tasks/task_id_terminal/events` with the seven-field
   envelope (`task_id = task_id_terminal`,
   `executor_id = k8s-exec-A`, `team_id = team-A`,
   `event_id = 0190-k8s-finished-post-restart`,
   `event_type = finished`, `occurred_at = 2026-07-13T16:30:00Z`,
   `payload = {"phase":"terminal_state","openhands_status":"finished"}`),
   receive `202 accepted`, wait the configured `finished_cleanup_delay`,
   and then idempotently delete `pod-terminal` without another task event.
7. Read `task_id_running` and `task_id_terminal` and their event
   histories through the API Gateway.

## Expected outcome

Step 2 returns `200` and the stored `team_id`, `authorized_tag`, and
Executor record remain unchanged. Step 3 returns `403` (or
`409 team_id_immutable`) without changing the stored `team_id`.
Step 4 returns `200` with both `task_id_running` and
`task_id_terminal` listed; each task row carries its immutable
`tasks.owner_command_id` (`command-running` and `command-terminal`)
and the request itself is filtered only by
`tasks.executor_id = k8s-exec-A`. No new Pod is created for
`task_id_running`; the existing `pod-running` is re-attached by
matching its `flowai.command_id` label to `task_id_running`'s
`owner_command_id`. Step 6 returns `202 accepted`. The final reads
return: `task_id_running` with `current_state = running` (unchanged),
an event history of exactly `[created, running]` where the `created`
row carries non-null `executor_id = k8s-exec-A` and a payload meaning
`task task_id_running loaded by k8s-exec-A`, and NO new `running`
row after the restart; `task_id_terminal` with
`current_state = finished`, `executor_id = k8s-exec-A`, and an
ordered event history of exactly `[created, running, finished]`
where the pre-restart `running` row keeps `0190-k8s-running-pre-restart`
and the post-restart `finished` row carries
`0190-k8s-finished-post-restart` with `team_id = team-A`. The Pod remains
counted against local capacity during `finished_cleanup_delay`, is deleted
afterward, and its exit code never determines task success. No `dispatched`
event appears in either history at any time.
