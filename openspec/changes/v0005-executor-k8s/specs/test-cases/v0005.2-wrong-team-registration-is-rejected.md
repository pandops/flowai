# Test case: v0005.2-wrong-team-registration-is-rejected

## Implements

`executor` — `### Requirement: K8s Executor binds to a single authenticated team identity`.

## Intent

Verify the State Registry rejects a K8s Executor registration whose `team_id`
does not match the team bound to the authenticated Executor service identity,
without creating or updating an Executor record, and that `team_id` is
immutable across re-registration.

## Preconditions

State Registry and PostgreSQL are running. An authenticated Executor service
identity `k8s-exec-A` is bound to `team_id = team-A`. Executor identifier
`k8s-exec-A-1` does not exist.

## Steps

1. Send `PUT /v1/executors/k8s-exec-A-1` as `k8s-exec-A` with
   `executor_type = "k8s"`, `team_id = team-B`, `authorized_tag =
   k8s-cluster-1`, `max_capacity = 2`, `running_count = 0`, and metadata.
2. Send `PUT /v1/executors/k8s-exec-A-1` as `k8s-exec-A` with
   `executor_type = "k8s"`, omitting the `team_id` field but supplying the
   rest of the registration payload.
3. Read `k8s-exec-A-1` through the API Gateway Executor read API.
4. Repeat the valid registration from `v0005.1` to seed `k8s-exec-A-1` with
   `team_id = team-A`.
5. Re-send `PUT /v1/executors/k8s-exec-A-1` with `team_id = team-B` while
   still authenticated as `k8s-exec-A`.
6. Read `k8s-exec-A-1` again through the API Gateway Executor read API.

## Expected outcome

The first registration returns `403` (or `400 invalid_team_id`) and the
Executor read returns `404 executor_unknown`. The omitted-`team_id`
registration also returns `403` (or `400 invalid_team_id_count`) and the
read still returns `404 executor_unknown`. After the valid registration,
the divergent re-registration in step 5 returns `403` (or `409
team_id_immutable`) without changing the stored `team_id`; the final read
returns `200` with `team_id = team-A`, unchanged `authorized_tag`, and
unchanged capacity values.
