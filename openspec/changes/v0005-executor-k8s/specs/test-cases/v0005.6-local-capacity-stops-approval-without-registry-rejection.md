# Test case: v0005.6-local-capacity-stops-approval-without-registry-rejection

## Implements

`executor` — `### Requirement: K8s Executor tracks child Pod capacity locally`.

## Intent

Verify two distinct facts in sequence: first, that the State Registry treats
saturated stored capacity observations as informational only and still approves
an otherwise eligible same-team task when a harness-authenticated direct
approval request is issued (proving the Registry does not gate approval on
capacity); second, that the actual K8s Executor process, while its locally
observed `running_count = max_capacity`, refrains from issuing an additional
approval request for a second same-team task until the local slot frees
(proving the local-only enforcement). Together they confirm capacity is purely
local and SHALL NOT be communicated as a Registry-side rejection.

## Preconditions

State Registry and PostgreSQL are running. An authenticated Executor service
identity `k8s-exec-A` bound to `team_id = team-A` is registered with exactly
one `authorized_tag = k8s-cluster-A`, observed `max_capacity = 1`, and
observed `running_count = 1`. Two `created` tasks exist for
`team-A`/`k8s-cluster-A`: `task_id_1` and `task_id_2`.

## Steps

1. Read `k8s-exec-A` through the API Gateway Executor read API and confirm
   its stored capacity observations (`max_capacity = 1`,
   `running_count = 1`).
2. As `k8s-exec-A`, request
   `GET /v1/executors/k8s-exec-A/tasks?tag=k8s-cluster-A` and confirm both
   `task_id_1` and `task_id_2` are returned in the response.
3. Part A (Registry-side capacity independence): using a test-harness
   authenticated client that carries the same `k8s-exec-A` service identity
   (so the State Registry binds the call to `team_id = team-A`) but does
   NOT itself run the K8s Executor process loop, issue
   `POST /v1/executors/k8s-exec-A/approvals` for `task_id_2` directly
   against the State Registry and capture the response status code and
   body.
4. Part B (Executor-side local enforcement): with the actual K8s Executor
   process for `k8s-exec-A` running and its locally observed
   `running_count` equal to `max_capacity`, observe the Executor's outbound
   traffic to the State Registry for a configurable observation window and
   confirm the process issues NO `POST /v1/executors/k8s-exec-A/approvals`
   request for either `task_id_1` or `task_id_2` while saturated.
5. Free a local slot on the K8s Executor process (for example by
   completing or terminating the running Pod and emitting the terminal
   event so `running_count` drops below `max_capacity`) and observe that
   the process subsequently issues a `POST /v1/executors/k8s-exec-A/approvals`
   request for one of the remaining `created` tasks and receives
   `200 approved`.
6. Read `task_id_1`, `task_id_2`, and the Executor's event history through
   the API Gateway.

## Expected outcome

Step 1 returns `200` with `max_capacity = 1` and `running_count = 1`. Step 2
returns `200` with both `task_id_1` and `task_id_2` summaries, regardless of
`running_count = max_capacity`. Step 3 (Part A) returns `200 approved` and
NEVER returns `422 executor_at_capacity` or any capacity-based rejection; the
State Registry records a `dispatched` event with `executor_id = k8s-exec-A`
even though the stored observation is saturated — proving Registry approval
is capacity-independent. Step 4 (Part B) confirms the actual K8s Executor
process issues no approval request while saturated. Step 5 confirms the
process issues exactly one approval request after the local slot frees and
receives `200 approved`. After all steps, `task_id_2` projects to
`dispatched` with `executor_id = k8s-exec-A` and an ordered history of
exactly `[created, dispatched]`; `task_id_1` remains `current_state =
created`, `executor_id = null`, ordered history `[created]`.
