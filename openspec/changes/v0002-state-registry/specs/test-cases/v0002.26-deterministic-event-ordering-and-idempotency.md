# Test case: v0002.26-deterministic-event-ordering-and-idempotency

## Implements

`state-registry` — `### Requirement: State Registry orders accepted lifecycle events deterministically`.

## Intent

Verify equal-time lifecycle events use `event_id` as the deterministic tie-breaker and an idempotent retry does not duplicate history.

## Preconditions

A `team-a` task is `dispatched` to same-team Executor `executor-1`; registry-owned events precede `2026-07-13T13:00:00Z`.

## Steps

1. Post `running` with `event_id = 0190-tie-0001`, `team_id = team-a`, and `occurred_at = 2026-07-13T13:00:00Z`.
2. Post `finished` with greater monotonic `event_id = 0190-tie-0002`, the same `team_id = team-a`, and the same timestamp.
3. Retry the complete `running` event unchanged.
4. Attempt a fresh event at that timestamp with an `event_id` not greater than the latest tuple and include an `accepted_sequence` field.
5. Attempt a fresh event whose submitted `team_id` does not match the authenticated Executor team.
6. Read history twice through trusted Gateway context for `team-a`.

## Expected outcome

State Registry verifies `team_id = team-a` against the authenticated Executor team on every event write. The valid posts and retry return their original `202 accepted`; the fresh non-increasing tuple is rejected and `accepted_sequence` cannot override it; the cross-team request is rejected with `403 team_mismatch`. Both reads return exactly `[created, dispatched, running, finished]`; equal-time rows are ordered by ascending `event_id`; the retry appears once; and no caller-supplied sequence participates in acceptance or ordering.
