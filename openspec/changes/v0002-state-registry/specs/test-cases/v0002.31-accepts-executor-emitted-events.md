# Test case: v0002.31-accepts-executor-emitted-events

## Implements

`state-registry` — `### Requirement: State Registry accepts Executor-emitted lifecycle events`.

## Intent

Verify the State Registry accepts complete `running`/`finished`/`failed` event envelopes from the assigned Executor, projects state in the same transaction, and rejects unassigned or terminal-out-of-order writers without appending events.

## Preconditions

A `team-a` task is `dispatched` to `team-a` Executor `executor-1`; history is `[created, dispatched]`; same-team `executor-2` is authenticated.

## Steps

1. As `executor-1`, post valid `running` with `team_id = team-a`, non-null assigned `executor_id`, and a strictly later ordering tuple.
2. Retry that event unchanged.
3. As `executor-1`, post valid `finished` with `team_id = team-a` and a strictly later tuple.
4. As unassigned `executor-2`, attempt a fresh task event carrying `team_id = team-a`.
5. As `executor-1`, attempt a fresh task event carrying `team_id = team-b`.
6. Read task and history through trusted Gateway context for `team-a`.

## Expected outcome

State Registry verifies `team_id` against the authenticated Executor team on every event write. Valid assigned-Executor events return `202 accepted`, update projection transactionally, and append once by `(task_id, event_id)`; retry returns the original result; the unassigned same-team writer is rejected with `403 not_assigned`; the cross-team writer is rejected with `403 team_mismatch`. Final history is `[created, dispatched, running, finished]`; the Registry-owned rows have `executor_id = null` and inherit the task team; the Executor-emitted rows have non-null `executor_id = executor-1` and submitted `team_id = team-a` equal to the authenticated Executor team.
