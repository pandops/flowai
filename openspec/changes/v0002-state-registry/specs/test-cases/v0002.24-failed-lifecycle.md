# Test case: v0002.24-failed-lifecycle

## Implements

`state-registry` — `### Requirement: State Registry defines the event-sourced task lifecycle`.

## Intent

Verify the failure path projects `created -> dispatched -> running -> failed` and preserves the assigned Executor's failure details.

## Preconditions

State Registry and PostgreSQL are running; a listener and an Executor are each bound to `team-a`; the Executor is registered with the task's exact tag; trusted Gateway context for `team-a` can read tasks and events.

## Steps

1. Submit a new `team-a` task and retain its `task_id`.
2. Request approval from the same-team Executor.
3. Post `running` with `team_id = team-a` that State Registry verifies against the authenticated Executor team, non-null assigned `executor_id`, and a strictly later ordering tuple.
4. Post `failed` with `team_id = team-a`, the same Executor, and a strictly later tuple.
5. Read the task and history through trusted Gateway context for `team-a`.

## Expected outcome

State Registry verifies `team_id = team-a` against the authenticated Executor team for every event write. The task retains immutable `team_id = team-a`, immutable assignment, and projects through exactly `[created, dispatched, running, failed]`. The Registry-owned `created` and `dispatched` rows have `executor_id = null` and inherit the task team; the Executor-owned terminal row has non-null assigned `executor_id`, submitted `team_id` equal to the task team, preserved payload, preserved ordering tuple, and no `finished` event exists.
