# Test case: v0002.10-store-versioned-encrypted-secret

## Implements

`state-registry` — `### Requirement: State Registry stores team-owned secrets with immutable versions`.

## Intent

Verify encryption at rest, immutable versions, and plaintext-free logs and operator responses.

## Preconditions

A `team-a` environment exists; trusted Gateway context is verified for a `team-a` operator; OpenBao Transit is available.

## Steps

1. Through Web UI and API Gateway under trusted Gateway context for `team-a`, create a logical secret under the same-team environment with one plaintext value and retain the returned `secret_id` and `version`.
2. Through the same team-scoped path, replace the secret's plaintext value and retain the returned `secret_id` and new `version`.
3. Optionally restart the State Registry while preserving PostgreSQL.
4. Through trusted Gateway context for `team-a`, read the logical secret metadata and its version metadata and observe the operator responses, application logs, and audit records.
5. As the assigned same-team Executor for a `team-a` task that references this environment, open the environment and verify the resolved env-style values plus the version identifier used.

## Expected outcome

The initial create and the replacement each return identifiers and version numbers without any plaintext in the operator responses. After any restart, the logical secret metadata and version metadata remain readable through trusted Gateway context and continue to expose identifiers and version numbers without plaintext. Opening as the assigned same-team Executor resolves the current version and returns env-style values; older version metadata remains immutable. Operator responses, application logs, and audit records never contain either submitted plaintext value. The structural `secrets` to `secret_versions` foreign-key relationship is verified separately by the State Registry migration/integration tests in `tasks.md`, not as an E2E step here.
