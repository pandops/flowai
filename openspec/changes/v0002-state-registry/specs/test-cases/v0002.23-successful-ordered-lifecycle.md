# Test case: v0002.23-successful-ordered-lifecycle

## Implements

`state-registry` — `### Requirement: State Registry defines the event-sourced task lifecycle`.

## Intent

Verify the successful happy path projects `created -> dispatched -> running -> finished` from the immutable ordered event history.

## Preconditions

State Registry and PostgreSQL are running; a listener and an Executor are each bound to `team-a`; the Executor is registered with the task's exact tag; trusted Gateway context for `team-a` can read tasks and events.

## Steps

1. Submit a new `team-a` task and retain its `task_id`.
2. Request approval from the same-team Executor.
3. Post `running` with `team_id = team-a` that State Registry verifies against the authenticated Executor team, non-null assigned `executor_id`, and a strictly later `(occurred_at, event_id)` tuple.
4. Post `finished` with `team_id = team-a`, the same assigned `executor_id`, and a strictly later tuple.
5. Read the task and history through trusted Gateway context for `team-a`.

## Expected outcome

State Registry verifies `team_id = team-a` against the authenticated Executor team for every event write. Ingestion, approval, and both Executor events succeed. The task retains immutable `team_id = team-a`, projects to `finished`, and remains assigned to the same Executor. The ordered history is exactly `[created, dispatched, running, finished]`; the Registry-owned `created` and `dispatched` rows have `executor_id = null` and inherit the task team; the Executor-owned `running` and `finished` rows have non-null assigned `executor_id`, submitted `team_id` equal to the task team, and preserved submitted identifiers and payloads.
