# Design: State Registry

## Runtime Shape

- A system-administrator identity authenticates and creates teams, source systems, and task types exclusively through `POST /admin/teams`, `POST /admin/source-systems`, and `POST /admin/task-types`. State Registry persists immutable `team_id`, immutable required `default_image`, display-only `team_name`, immutable `source_system_id`, immutable `task_type_id`, required `execution_tag`, and optional per-source-system and per-task-type `default_image`. The team resource is create-only: there is no `PUT`, `PATCH`, or `DELETE` team endpoint, and listeners, Executors, and Gateway paths never create or update teams. An Executor body that names a `team_id` not referencing an existing team is rejected without persistence. The system-administrator identity MAY additionally read `GET /admin/tags` and `GET /admin/tasks` (see *Admin-only read projections* below) under the same authentication; no other identity may call any `/admin/*` path.
- Event listeners authenticate with a service identity bound to exactly one authorized `team_id` and one authorized `source_system_id`. Every task submission supplies that immutable `team_id`, that immutable `source_system_id`, the external `source_id`, and a REQUIRED `task_type_id`; State Registry verifies the `team_id` against the authenticated listener authorization, the source-system identity against the registered source system for that team, and the `task_type_id` against a registered task type whose immutable `team_id` equals the authenticated listener's team. The Registry derives `tasks.required_tag` from the referenced task type's `execution_tag`. The Registry SHALL reject any ingestion body that supplies a listener-authored `required_tag` field (whether at the top level, nested under a body wrapper, or as a request header) with `400 listener_supplied_required_tag_forbidden` without persistence, event append, or acknowledgement; the listener SHALL NOT submit an independently authoritative `required_tag` and the Registry SHALL NOT silently trust, silently ignore, or silently overwrite a listener-supplied `required_tag` value. A mismatched team, source system, task type, or listener-supplied `required_tag` is rejected without persistence, acknowledgement, or disclosure.
- PostgreSQL stores the canonical, normalized 3NF projection of team-owned platform state plus the immutable event logs that drive it.
- A uniqueness constraint on `(team_id, source_system_id, source_id)` provides task-ingestion idempotency. Repeated same-team submissions return the existing canonical task with `current_state = pending` and append no event; the same external `source_id` MAY independently exist across teams, but only when each team has its own separately registered `source_system_id` carrying that source — never because one `source_system_id` is shared across teams. One `source_system_id` belongs to exactly one team; cross-team claims against one source-system identity are rejected. The Registry SHALL reject any ingestion body that contains a listener-authored `required_tag` field (whether at the top level, nested under a body wrapper, or as a request header) with `400 listener_supplied_required_tag_forbidden`; the listener SHALL NOT supply an independently authoritative `required_tag`.
- Each task belongs to exactly one immutable `team_id`, declares exactly one required tag, and carries `ingested_at` set once at ingestion and never updated. Each Executor service identity belongs to either exactly one immutable `team_id` (`scope = team`) or to no `team_id` (`scope = system`), and every Executor registers exactly one authorized tag with State Registry, alongside Executor type, observed `max_capacity`, observed `running_count`, and runtime metadata. The Executor's `scope` is registration-time, immutable from registration onward, and recorded on the `executors` row.
- Executors discover `pending` tasks by tag in FIFO `(ingested_at ASC, task_id ASC)` order. When the Executor's `scope = team`, the discovery SHALL additionally require `tasks.team_id = executors.team_id`; when `scope = system`, the team predicate is omitted and the Executor MAY see `pending` tasks from any team. Eligibility precedes ordering; ordering precedes pagination; counts apply to the eligibility-filtered set only. Discovery is read-only, MUST NOT reserve or assign a task, and MUST NOT read, compare, or enforce `max_capacity` or `running_count`. Image strings are not team-owned resources and SHALL NOT participate in authorization.
- The Executor alone decides when local capacity permits a new discovery or claim request; State Registry does not gate the request.
- Before starting, an Executor claims a specific `task_id` with a `command_id` through `POST /v1/executors/{executor_id}/claim`. State Registry claims only when the task is `pending`, the tag matches, the eligibility predicate from the Executor's scope holds, and the requested task is the OLDEST currently eligible `pending` task for that authenticated Executor. In one transaction, claim SHALL set immutable `tasks.owner_command_id` (from the request), immutable `tasks.executor_id`, persist `tasks.resolved_image` and `tasks.image_source` from the four-level image resolution rule, append the FIRST lifecycle event `created` with `executor_id = claiming_executor` and payload `task <task_id> loaded by <executor_id>`, and remove the task from the requesting Executor's scope of discovery. Exactly one eligible concurrent requester succeeds. The complete claim-conflict taxonomy SHALL be: (a) `task_id` unknown or foreign to the authenticated Executor returns non-revealing `404` with no mutation and no event; (b) `task_id` already claimed under a different `command_id` for an authorized visible task returns `409 task_already_claimed` with no mutation and no event; (c) the same `(task_id, command_id)` by the original claiming Executor returns the original `200 claimed` body with no new event and no field update; (d) an eligible but non-oldest `pending` `task_id` returns `409 older_task_must_be_claimed_first` with no mutation and no event; (e) a `task_id` whose current state is not `pending` and is not the same `(task_id, command_id)` of an existing claim returns non-revealing `404` with no mutation and no event. The Registry SHALL never return a capacity-related rejection.
- The assigned Executor appends `running`, `finished`, and `failed` events. Every Executor-emitted task event envelope SHALL carry `event_id`, `task_id`, `executor_id`, non-null `team_id`, `event_type`, `occurred_at`, and `payload`; `task_events.team_id` SHALL be persisted on append and SHALL inherit the parent task's team. State Registry SHALL verify that the envelope `team_id` equals the authenticated Executor's immutable `team_id` and equals the parent task's immutable `team_id` before accepting. Event-denial taxonomy: a same-team Executor whose envelope `team_id` differs from its authenticated immutable team is rejected with `403 team_mismatch`; a same-team Executor that is not the current `tasks.executor_id` is rejected with `403 not_assigned`; a foreign-team task or Executor point identifier is rejected with the non-revealing `404` shape used for an unknown identifier; out-of-order or otherwise invalid transitions are rejected without append or projection change.
- Accepted event read ordering is `(occurred_at ASC, event_id ASC)`. `event_id` is a stable monotonic identifier and serves as the idempotency key and equal-timestamp tie-breaker. If an Executor retries the same event with the same `event_id`, State Registry returns the original acceptance without appending a duplicate. After resolving an idempotent retry, State Registry rejects every new lifecycle event whose `(occurred_at, event_id)` tuple is not strictly greater than the latest accepted tuple for that task; there is no caller-supplied `accepted_sequence` override.
- API Gateway is the only operator caller. It authenticates with a trusted Gateway service identity and sends verified context containing `operator_id`, `team_id`, and `request_id`; the optional display-only `team_name` is forwarded only when the verified operator team carries one. State Registry authorizes only with the immutable `team_id`; `team_name`, when present, is display and audit context and never grants access, and its absence never weakens authorization anchored to `team_id`.
- Every operator list, point read, count, aggregation, history, control, audit, environment, and secret query starts with the trusted `team_id` predicate. The team predicate is applied before pagination, cursor construction, totals, counts, or aggregation so metadata cannot reveal another team.
- WebSocket subscription authorization is fixed to the trusted Gateway `team_id` at upgrade time. Backfill selection, replay cursors, live fan-out, and every emitted frame are team-filtered before delivery. A frame from another team is a review-blocking isolation failure.
- Environments and logical secrets belong to one team. Same-team operators manage them through API Gateway; optional project and task scope narrow applicability within that team and never authorize cross-team access. Secret plaintext is encrypted with local AES-256-GCM authenticated encryption (256-bit data key, fresh random 96-bit nonce per encryption, 128-bit authentication tag, authenticated associated data binding team identifier, logical secret identifier, and secret version), and opaque provider-neutral `key_id`/`key_version` metadata is recorded on each immutable `secret_versions` row. The Registry refuses decryption when the configured key is missing, the active key window excludes the `key_id`, the associated data binding does not match, the nonce or tag is invalid, or any canonical authorization check fails. An environment definition is either team-wide (no `task_id` parent) or task-owned (a parent `task_id` in the same team); the row's `team_id` is immutable in both cases and only the parent task in the same team may use a task-owned definition. A `secrets` row inherits scope from the parent environment, so a secret under a task-owned environment is task-owned too. Application logs, audit records, and error responses contain no plaintext, no nonce bytes, no ciphertext bytes, no authentication tag bytes, no key material, and no individual claim values beyond identifier-level metadata.
- Task-running image references are managed by State Registry, not by the Executor. State Registry persists REQUIRED `default_image` per team on `teams` (set at `POST /admin/teams`), OPTIONAL `default_image` per task type on `task_types`, OPTIONAL `default_image` per source system on `source_systems`, OPTIONAL `image` override per task on `tasks`, plus `resolved_image` and `image_source` on `tasks`. On atomic claim, State Registry resolves the effective image using precedence `tasks.image` (override) -> `task_types.default_image` (task type) -> `source_systems.default_image` (source system) -> `teams.default_image` (always present); persists `tasks.resolved_image` and `tasks.image_source` in the same transaction that appends the first `created` event; and includes both in the claim response. The assigned Executor SHALL use `resolved_image` verbatim, SHALL NOT consult any other source, and SHALL NOT maintain a local fallback image. The resolved image is computed and persisted in the same transaction as claim and is immutable from claim onward. Image strings are not team-owned resources, and image equality across teams carries no authority.
- Assigned Executors open env-style values directly from State Registry with authenticated identity and a signed scope token whose compact three-part form is `<header>.<payload>.<signature>`. The protected header carries `alg` (allow-listed to `HS256`, `HS384`, or `HS512`), `kid`, and `typ`; the payload carries `team_id`, `project_id` (required claim; nullable only when the canonical environment has no project scope), `task_id`, `environment_id`, `executor_id`, `audience` (literal `state-registry.environment.open`), `issued_at`, `expiry`, and `key_id`. State Registry signs each token with the declared allow-listed HMAC algorithm under a server-controlled key handle selected by the bound `key_id`. State Registry first verifies that the protected-header `kid` equals the payload `key_id`, then recomputes the signature under that algorithm using the server-side key handle, then compares it with a constant-time comparison before any other check. Only after the MAC verifies does it check the `key_id` against the documented active key window for rotation, the `audience` against the expected literal identifier, the `issued_at` against `server_now + 30 seconds` (premature-beyond-skew rejection), the `expiry` is strictly later than `issued_at` and no greater than five minutes after `issued_at`, and every other claim against canonical team ownership, task assignment, environment applicability, and project/task scope before performing the local AES-256-GCM decrypt operation. State Registry SHALL never log token plaintext, individual claims, MAC bytes, key material, derived key bytes, nonce bytes, ciphertext bytes, authentication tag bytes, or any associated-data values beyond identifier-level metadata; operational logs and audit records SHALL record only the token identifier, claim presence, key identifier, decision, and outcome. State Registry SHALL reject tokens presented by an authenticated Executor whose identity is not the current assigned Executor for the referenced task, and SHALL reject every token when the referenced task is in a terminal state or unassigned, before any decrypt operation. State Registry MAY allow a same assigned identity retry of the same token within TTL when every check still passes; the retry SHALL NOT bypass canonical claim, transition, or assignment checks, SHALL NOT extend TTL, and SHALL NOT revive an expired token.
- Audit entries include `team_id`, actor identity and type, action, resource type and identifier, `request_id`, outcome, and timestamp. Audit metadata and logs never contain secret plaintext or decrypted environment values.

## Admin-only read projections

- `GET /admin/tags` is a global projection of every registered `task_types` row. It is accepted only from an authenticated system-administrator identity and is rejected before any data access when the authenticated identity is not a system administrator. Each response entry contains EXACTLY `team_id`, `task_type_id`, and `execution_tag`; the Registry SHALL NOT add, omit, rename, or re-order these fields, SHALL NOT include `default_image`, and SHALL NOT include any other column from any table. The Registry orders entries deterministically by `(team_id ASC, execution_tag ASC, task_type_id ASC)`, supports cursor pagination with a default page size of 50 and a maximum page size of 200, and accepts optional exact-match `team_id` and `tag` filters. The endpoint never creates, updates, or deletes any row, never reads or writes tasks, assignments, events, environments, secrets, or audit entries, never returns task payload values, decrypted environment values, secret material, or event history, and never grants tenant authority from cross-team tag equality. There is no `tags` table, no tag create/update/delete API, and no system-admin authentication-mechanism definition.
- `GET /admin/tasks` is a global read-only task-summary projection. It is accepted only from an authenticated system-administrator identity and is rejected before any data access when the authenticated identity is not a system administrator. Each response entry contains EXACTLY `task_id`, `team_id`, `task_type_id`, `source_system_id`, `source_id`, `required_tag`, `current_state`, `owner_command_id`, `executor_id`, `ingested_at`, and `claimed_at`; the Registry SHALL NOT add, omit, rename, or re-order these fields, SHALL NOT include `image`, `resolved_image`, `image_source`, `project_id`, `environment_id`, or task payload values, and SHALL NOT include any other column from any table. The Registry orders entries deterministically by `(ingested_at DESC, task_id DESC)`, supports cursor pagination with a default page size of 50 and a maximum page size of 200, and accepts optional exact-match `team_id`, `state`, `tag`, and `task_type_id` filters. The endpoint never creates, updates, or deletes any row; never reads or writes events, environments, secrets, control requests, or audit entries; never returns task payload values, decrypted environment values, secret material, or event history; and never grants tenant authority from cross-team tag equality. "All" tasks means a traversable, paginated global collection; the response SHALL never be unbounded. This admin projection does NOT change the canonical `Task` resource returned by claim, by same-team Gateway reads, by same-team Executor discovery, or by any other non-admin endpoint.
- Both admin reads share the same authorization failure semantics as every other `/admin/*` endpoint: any caller without an authenticated system-administrator identity is rejected with `401 unauthenticated` or `403 not_authorized` BEFORE any team, source system, task type, task, assignment, event, environment, secret, control, or audit row is read or written, and BEFORE any payload, secret, environment, decrypted value, or event-history content is materialized. Neither endpoint ever mutates state; both return closed non-revealing error responses for invalid cursors, malformed filter values, or any other invalid input, and never expose system-admin authentication-mechanism internals, certificates, tokens, or claims in responses, logs, or audit entries.

## Authorization Failure Semantics

- Invalid or absent listener, Executor, API Gateway, or system-administrator service credentials fail authentication or role authorization before protected data is read.
- An authenticated caller that names a task, Executor, environment, secret, control, event, audit, source system, or task type resource owned by another team receives the same non-revealing `404` used for an unknown identifier.
- Foreign-team rejection performs no mutation, event append, audit disclosure, pagination/count change, aggregation contribution, WebSocket subscription, or decrypt operation.
- Caller-supplied headers, payload tenant fields, URL identifiers, and `team_name` are never trusted to select an authorization scope. The authenticated service binding or trusted Gateway `team_id` context establishes the only tenant scope. Image equality between tasks in different teams SHALL NOT establish any tenant authority.

## 3NF Table Ownership

State Registry persists its durable surface in a third normal form PostgreSQL schema. Each domain entity lives in its own table, every non-key attribute depends on the whole primary key, and transitive dependencies are removed into their own tables. Tenant-owned parents expose a unique `(team_id, entity_id)` key, and child tables use matching composite foreign keys or an equivalent database-enforced relationship so a child cannot reference a parent from another team. The Registry does not publish an ER diagram; this section names the tables and ownership rules directly so the migration set is unambiguous.

- `teams` owns immutable `team_id`, the REQUIRED opaque `default_image` (set at registration, immutable through any admin or operator path), and display metadata such as `team_name`. Changing display metadata never changes authorization identity or ownership.
- `executors` owns Executor identity, ownership `scope` (`team` or `system`), an immutable `team_id` when `scope = team` and `team_id = NULL` when `scope = system`, the single authorized tag, Executor type, runtime metadata, and the latest observation columns `max_capacity` and `running_count`. Each row is keyed by `executor_id`; rows with `scope = team` reference an existing `teams.team_id`; rows with `scope = system` reference no team. The row is updated in place when the Executor reports new observations; the durable history of capacity observations lives in `executor_events`. The Registry SHALL NOT publish an ER diagram as part of the contract. A re-registration that names a different `scope` than the original SHALL be rejected without mutation; a team-owned registration whose `team_id` does not reference an existing team SHALL be rejected without persisting any Executor or team row; Executor registration never creates or updates a team.
- `task_events` owns the immutable task lifecycle log. Each row is keyed by `event_id`, references the owning task with an enforced same-team relationship, and carries `executor_id`, `event_type`, `occurred_at`, and `payload`. Every row persists the parent task's immutable `team_id`; the first `created` event emitted on claim stores that `team_id` with non-null `executor_id = claiming_executor`; Executor-emitted events store that same `team_id` with non-null `executor_id = authenticated_assigned_executor` after envelope verification. No `accepted_sequence` column or recovery bypass exists. Accepted rows are read by `(occurred_at ASC, event_id ASC)`.
- `executor_events` owns the immutable Executor self-event log keyed by `event_id`, separate from `task_events`. Every row persists `executor_id NOT NULL`; the Executor's `team_id` is non-null when `scope = team` and null when `scope = system`. Both are verified against the authenticated service identity and the envelope `team_id` before append. Capacity and lifecycle observations append here; the latest observation is mirrored onto `executors` in the same transaction.
- `environment_definitions` owns non-secret environment metadata, immutable `team_id`, values, optional `project_id` and `task_id` applicability, and an optional parent `task_id` for task-owned rows. The `task_id` parent SHALL reference a task with the same `team_id`; rows with `task_id IS NULL` are team-wide. A task reference to an environment is valid only when both rows have the same `team_id` and either the environment is team-wide, or the environment's parent `task_id` equals the referencing task, and the project/task applicability (when set) is satisfied.
- `secrets` owns each logical secret's stable identifier, immutable `team_id`, environment association, name, applicability metadata, revocation state, and inherits its scope from the parent environment: when the parent environment is team-wide the secret is team-scoped, and when the parent environment is task-owned the secret is task-owned and only the parent task in the same team may open it. It references an environment in the same team.
- `tasks` owns the canonical task record: `task_id`, immutable `team_id`, immutable `source_system_id`, `source_id`, REQUIRED non-null `task_type_id` whose own immutable `team_id` equals `tasks.team_id`, server-derived `required_tag` computed from the referenced `task_type.execution_tag`, optional per-task `image` override (opaque container image reference with an immutable digest), immutable `ingested_at`, nullable `resolved_image` and `image_source` set atomically at claim and null until the first `created` event, `payload`, projected `current_state` (`pending` initially with no event; `created` after the first `created` event on claim; `running`/`finished`/`failed` thereafter), `tasks.owner_command_id` (null before claim, set once at successful claim, immutable from claim onward), `tasks.executor_id` (null before claim, set once at successful claim, immutable from claim onward), nullable `tasks.claimed_at` (null until successful claim, set once, immutable thereafter), optional environment reference. The unique key on `(team_id, source_system_id, source_id)` enforces ingestion idempotency. A composite foreign key or equivalent database constraint from `tasks.task_type_id` and `tasks.team_id` to `task_types.task_type_id`/`task_types.team_id` enforces that every task references a registered task type in the same team and that no task may cite a foreign-team task type. `tasks.image` SHALL be set in the same ingestion transaction and SHALL NOT be replaced by a later listener retry of the same triple; `tasks.resolved_image` and `tasks.image_source` SHALL be set in the same transaction that appends the first `created` event and SHALL be derived from `tasks.image` -> `task_types.default_image` -> `source_systems.default_image` -> `teams.default_image`, in that exact order. `tasks.owner_command_id` is nullable before claim and immutable from claim onward; `tasks.executor_id` is nullable before claim and immutable from claim onward; `tasks.claimed_at` is nullable before claim and immutable from claim onward. The parent task's `team_id` remains immutable for the row's lifetime regardless of Executor scope. `current_state` is updated in the same transaction as every accepted event append.
- `secret_versions` owns immutable AES-256-GCM ciphertext versions and provider-neutral `key_id`/`key_version` metadata. Every row references `secrets`; team ownership is inherited and enforced through that parent, and plaintext is never stored. Each row persists a 96-bit nonce, a 128-bit authentication tag, ciphertext bytes, and the associated-data binding that ties ciphertext to team identifier, logical secret identifier, and version. The Registry never logs nonce, ciphertext, tag, or key material.
- `audit_entries` owns append-only, team-scoped audit records containing `team_id`, actor, action, resource, `request_id`, outcome, and timestamp without plaintext values, nonce, ciphertext, tag, key material, or derived key bytes.
- `task_control_requests` owns append-only operator controls, references a task in the same team, and uses an idempotency key scoped to `(team_id, task_id, operator_id, action)`.
- `source_systems` owns immutable `source_system_id`, immutable `team_id`, an opaque listener identity reference, and an optional `default_image`. The row is keyed by `source_system_id`; `team_id` references an existing team. The opaque listener identity reference is constrained by a database-enforced global uniqueness index so that one listener principal maps to exactly one `(team_id, source_system_id)` pair across the entire `source_systems` table; a second registration that supplies a listener identity reference already in use under the same team, a different team, or any other variation SHALL be rejected without mutation. A source-system identity never changes team, and a listener identity reference cannot be transferred between source systems or between teams.
- `task_types` owns immutable `task_type_id`, immutable `team_id`, the required `execution_tag`, and an optional `default_image`. The row is keyed by `task_type_id`; `team_id` references an existing team.
- The normalized relationships include `teams 1:N executors` (when `scope = team`), `teams 1:N tasks`, `teams 1:N environment_definitions`, `teams 1:N secrets`, `teams 1:N source_systems`, `teams 1:N task_types`, `executors 1:N executor_events`, `executors 1:N tasks`, `tasks 1:N task_events`, `tasks 1:N task_control_requests`, `tasks 1:N environment_definitions` (a task may be the parent of zero or more task-owned environment definitions, all in the same team), `source_systems 1:N tasks`, `task_types 1:N tasks`, `environment_definitions 1:N secrets`, `secrets 1:N secret_versions`, and each task references exactly one registered task type in the same team through the composite `(task_type_id, team_id)` foreign key; one task type may be referenced by many tasks. System-owned Executors do not reference `teams`; their child rows in `executor_events` persist `team_id = NULL`. Child ownership is inherited from and constrained to the parent team when `team_id` is non-null; no child can be reparented across teams. `environment_definitions.task_id`, `tasks.image`, `tasks.resolved_image`, `tasks.image_source`, `tasks.owner_command_id`, `tasks.executor_id`, and `tasks.ingested_at` are set by the documented transactions; `executors.scope` is a non-null column with values restricted to `team` or `system`; `teams.default_image` is non-null and immutable through any non-admin operator path. `source_systems.listener_identity` is constrained by a database-enforced global uniqueness index; `tasks.task_type_id` is non-null and constrained by `(tasks.task_type_id, tasks.team_id) = (task_types.task_type_id, task_types.team_id)`.

## Tenant Assumptions and Boundaries

- A task, environment, secret, audit, source system, task type, and operator authentication context each belong to exactly one team. An Executor authentication context belongs to either exactly one team (`scope = team`) or no team (`scope = system`). Multi-team contexts and cross-team resource sharing are not part of this change; cross-team Executor claim is a documented `scope = system` trade-off that does not weaken per-task invariants.
- Environment definitions and logical secrets may be scoped team-wide or task-owned. Task-owned rows are still team-owned: their `team_id` is immutable and the parent `task_id` is constrained to a task in the same team. Task ownership does not create project RBAC, multi-team context, or cross-team access.
- The runtime image for a task is resolved by State Registry at claim from the per-task `image` override, the task-type `default_image`, the source-system `default_image`, or the team's required `default_image` in that order; resolution always succeeds because the team default is required at registration. The Executor uses `resolved_image` verbatim, never consults any other source, and never maintains a local fallback. Image strings are not team-owned resources; image equality across teams carries no authority, and operators rely on audit trails and the team default rather than on image identity for tenant authorization.
- Executor ownership `scope` is a registration-time choice. A team-owned Executor is filtered by its immutable `team_id`; a system-owned Executor is filtered by its single registered tag only. The two modes share the same per-task invariants (FIFO ordering, identical `(task_id, command_id)` retry semantics, atomic claim, scope token bound to the parent task's `team_id`); the documented trade-off for `scope = system` is that one Executor process MAY see task metadata across multiple teams in one discovery response.
- Team provisioning and membership resolution occur exclusively through `/admin/*` under an authenticated system-administrator identity. The Registry does not define how that identity is authenticated beyond requiring the role. This change defines no team CRUD or membership UI. `v0006-web-ui` may bootstrap one team initially, while `v0007-auth` supplies verified operator team claims.
- There is no project-level RBAC. Project and task scopes limit where a team-owned environment or secret applies; they do not establish authorization independent of `team_id`.
- There is no Router, separate broker, or Env Registry in the planned architecture.
- State Registry owns durable task intake, the immutable task lifecycle event log, projected task state, atomic FIFO claim, assignments, Executor self events (including system-owned Executors with NULL `team_id`), team-owned environment metadata, team-owned encrypted secret values and version history, the team-default, task-type-default, source-system-default, and per-task image references, the authoritative `resolved_image` and `image_source` for every claimed task, admin registration of teams, source systems, and task types, the active-key window for HMAC scope-token signing, and the local AES-256-GCM encryption of secret values.
- State Registry does not run workloads, decide global scheduling, or enforce or validate Executor capacity. `max_capacity` and `running_count` are observations, not gating conditions.
- Executors own runtime lifecycle and local capacity enforcement. They decide when to discover and when to claim. They SHALL use `resolved_image` verbatim and SHALL NOT maintain or substitute a local image.
- A claimed task is not automatically returned to discovery after Executor failure; an explicit audited same-team recovery decision is required.
- Plaintext secrets exist only in memory while serving an authorized open-environment response and are never returned to API Gateway. The State Registry's local AES-256-GCM provider is the sole cryptographic operation: nonce bytes, ciphertext bytes, authentication tag bytes, key material, and associated-data values beyond identifier-level metadata SHALL NEVER appear in logs, audit records, or error responses.
- The State Registry is the sole issuer and verifier of open-environment scope tokens. It maintains a documented active key window for HMAC signing keys whose algorithm is allow-listed to `HS256`/`HS384`/`HS512`: each `key_id` identifies a server-controlled key, retired keys SHALL be accepted only for the documented overlap period after rotation, and key material SHALL be loaded from a secure configuration source and SHALL NOT be persisted alongside token material or logs. Token issuance happens on atomic successful claim; the protected-header `kid` SHALL equal the payload `key_id`, `expiry` SHALL be strictly later than `issued_at`, `expiry - issued_at` SHALL NOT exceed five minutes, and `issued_at` SHALL satisfy `issued_at <= server_now + 30 seconds`. Re-issuance after a transition that invalidates a token SHALL require a fresh successful claim and SHALL NOT reuse the prior `key_id`-signed envelope.
