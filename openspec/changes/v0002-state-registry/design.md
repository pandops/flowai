# Design: State Registry

## Runtime Shape

- Event listeners authenticate with a service identity bound to exactly one authorized `team_id`. Every task submission supplies that same immutable `team_id`; State Registry verifies the value against the authenticated listener authorization before writing or acknowledging the task. A mismatched team is rejected without persistence or disclosure.
- PostgreSQL stores the canonical, normalized 3NF projection of team-owned platform state plus the immutable event logs that drive it.
- A uniqueness constraint on `(team_id, source, source_task_id)` provides task-ingestion idempotency. Repeated same-team submissions return the existing canonical task and append no event; the same `(source, source_task_id)` may exist independently in another team.
- Each task belongs to exactly one immutable `team_id` and declares exactly one required tag. Each Executor service identity belongs to exactly one immutable `team_id` and registers exactly one authorized tag with State Registry, alongside Executor type, observed `max_capacity`, observed `running_count`, and runtime metadata.
- Executors discover `created` tasks only when both `tasks.team_id = executors.team_id` and `tasks.required_tag = executors.authorized_tag`. Discovery is read-only, MUST NOT reserve or assign a task, and MUST NOT read, compare, or enforce `max_capacity` or `running_count`. Discovery MAY return the same task to multiple eligible Executors in the same team, but never to an Executor from another team.
- The Executor alone decides when local capacity permits a new discovery or approval request; State Registry does not gate the request.
- Before starting, an Executor requests approval for a specific `task_id`. Approval verifies the authenticated Executor's immutable team and tag, then atomically appends a `dispatched` event, sets `tasks.executor_id`, records `approved_at`, and removes the task from subsequent common discovery lists. Exactly one same-team, same-tag concurrent requester succeeds; every later same-team competitor receives `409 task_already_dispatched` without any further event. A task identifier owned by another team is indistinguishable from an unknown identifier and returns `404` without mutation or event append.
- The assigned Executor appends `running`, `finished`, and `failed` events. Every Executor-emitted task event envelope SHALL carry `event_id`, `task_id`, `executor_id`, non-null `team_id`, `event_type`, `occurred_at`, and `payload`; `task_events.team_id` SHALL be persisted on append and SHALL inherit the parent task's team. State Registry SHALL verify that the envelope `team_id` equals the authenticated Executor's immutable `team_id` and equals the parent task's immutable `team_id` before accepting. Event-denial taxonomy: a same-team Executor whose envelope `team_id` differs from its authenticated immutable team is rejected with `403 team_mismatch`; a same-team Executor that is not the current `tasks.executor_id` is rejected with `403 not_assigned`; a foreign-team task or Executor point identifier is rejected with the non-revealing `404` shape used for an unknown identifier; out-of-order or otherwise invalid transitions are rejected without append or projection change.
- Accepted event read ordering is `(occurred_at ASC, event_id ASC)`. `event_id` is a stable monotonic identifier and serves as the idempotency key and equal-timestamp tie-breaker. If an Executor retries the same event with the same `event_id`, State Registry returns the original acceptance without appending a duplicate. After resolving an idempotent retry, State Registry rejects every new lifecycle event whose `(occurred_at, event_id)` tuple is not strictly greater than the latest accepted tuple for that task; there is no caller-supplied `accepted_sequence` override.
- API Gateway is the only operator caller. It authenticates with a trusted Gateway service identity and sends verified context containing `operator_id`, `team_id`, and `request_id`; the optional display-only `team_name` is forwarded only when the verified operator team carries one. State Registry authorizes only with the immutable `team_id`; `team_name`, when present, is display and audit context and never grants access, and its absence never weakens authorization anchored to `team_id`.
- Every operator list, point read, count, aggregation, history, control, audit, environment, and secret query starts with the trusted `team_id` predicate. The team predicate is applied before pagination, cursor construction, totals, counts, or aggregation so metadata cannot reveal another team.
- WebSocket subscription authorization is fixed to the trusted Gateway `team_id` at upgrade time. Backfill selection, replay cursors, live fan-out, and every emitted frame are team-filtered before delivery. A frame from another team is a review-blocking isolation failure.
- Environments and logical secrets belong to one team. Same-team operators manage them through API Gateway; optional project and task scope narrow applicability within that team and never authorize cross-team access. Secret plaintext is encrypted through OpenBao Transit before persistence, and immutable `secret_versions` reference the owning logical `secrets` row.
- Assigned Executors open env-style values directly from State Registry with authenticated identity and a signed scope token whose compact three-part form is `<header>.<payload>.<signature>`. The protected header carries `alg` (allow-listed to `HS256`, `HS384`, or `HS512`), `kid`, and `typ`; the payload carries `team_id`, `project_id` (required claim; nullable only when the canonical environment has no project scope), `task_id`, `environment_id`, `executor_id`, `audience` (literal `state-registry.environment.open`), `issued_at`, `expiry`, and `key_id`. State Registry signs each token with the declared allow-listed HMAC algorithm under a server-controlled key handle selected by the bound `key_id`. State Registry first verifies that the protected-header `kid` equals the payload `key_id`, then recomputes the signature under that algorithm using the server-side key handle, then compares it with a constant-time comparison before any other check. Only after the MAC verifies does it check the `key_id` against the documented active key window for rotation, the `audience` against the expected literal identifier, the `issued_at` against `server_now + 30 seconds` (premature-beyond-skew rejection), the `expiry` is strictly later than `issued_at` and no greater than five minutes after `issued_at`, and every other claim against canonical team ownership, task assignment, environment applicability, and project/task scope before decrypting any value. State Registry SHALL never log token plaintext, individual claims, MAC bytes, key material, or derived key bytes; operational logs and audit records SHALL record only the token identifier, claim presence, key identifier, decision, and outcome. State Registry SHALL reject tokens presented by an authenticated Executor whose mTLS identity is not the current assigned same-team Executor for the referenced task, and SHALL reject every token when the referenced task is in a terminal state or unassigned, before any OpenBao operation. State Registry MAY allow a retry of the same token within its TTL by the same assigned same-team Executor; the retry SHALL NOT bypass any canonical claim, transition, or assignment check, SHALL NOT extend TTL, and SHALL NOT revive expired tokens.
- Audit entries include `team_id`, actor identity and type, action, resource type and identifier, `request_id`, outcome, and timestamp. Audit metadata and logs never contain secret plaintext or decrypted environment values.

## Authorization Failure Semantics

- Invalid or absent listener, Executor, or API Gateway service credentials fail authentication or role authorization before protected data is read.
- An authenticated caller that names a task, Executor, environment, secret, control, event, or audit resource owned by another team receives the same non-revealing `404` used for an unknown identifier.
- Foreign-team rejection performs no mutation, event append, audit disclosure, pagination/count change, aggregation contribution, WebSocket subscription, or outbound OpenBao call.
- Caller-supplied headers, payload tenant fields, URL identifiers, and `team_name` are never trusted to select an authorization scope. The authenticated service binding or trusted Gateway `team_id` context establishes the only tenant scope.

## 3NF Table Ownership

State Registry persists its durable surface in a third normal form PostgreSQL schema. Each domain entity lives in its own table, every non-key attribute depends on the whole primary key, and transitive dependencies are removed into their own tables. Tenant-owned parents expose a unique `(team_id, entity_id)` key, and child tables use matching composite foreign keys or an equivalent database-enforced relationship so a child cannot reference a parent from another team. The Registry does not publish an ER diagram; this section names the tables and ownership rules directly so the migration set is unambiguous.

- `teams` owns immutable `team_id` and display metadata such as `team_name`. Changing display metadata never changes authorization identity or ownership.
- `executors` owns Executor identity, immutable `team_id`, the single authorized tag, Executor type, runtime metadata, and the latest observation columns `max_capacity` and `running_count`. Each row is keyed by `executor_id`, references `teams`, and is updated in place when the Executor reports new observations; the durable history of capacity observations lives in `executor_events`.
- `tasks` owns the canonical task record: `task_id`, immutable `team_id`, `source`, `source_task_id`, `required_tag`, `payload`, projected `current_state`, lifecycle timestamps, optional environment reference, and the foreign key `executor_id`. The unique key on `(team_id, source, source_task_id)` enforces ingestion idempotency. `tasks.executor_id` is nullable before dispatch, immutable after approval, and constrained to reference an Executor with the same `team_id`. `current_state` is updated in the same transaction as every accepted event append.
- `task_events` owns the immutable task lifecycle log. Each row is keyed by `event_id`, references the owning task with an enforced same-team relationship, and carries `executor_id`, `event_type`, `occurred_at`, and `payload`. Every row persists the parent task's immutable `team_id`; registry-emitted `created` and `dispatched` rows store that `team_id` with `executor_id = NULL`, and Executor-emitted rows store that same `team_id` with non-null `executor_id` after envelope verification. No `accepted_sequence` column or recovery bypass exists. Accepted rows are read by `(occurred_at ASC, event_id ASC)`.
- `executor_events` owns the immutable Executor self-event log keyed by `event_id`, separate from `task_events`. Every row persists `executor_id NOT NULL` and the authenticated Executor's immutable `team_id`; both are verified against the authenticated service identity and the envelope `team_id` before append. Capacity and lifecycle observations append here; the latest observation is mirrored onto `executors` in the same transaction.
- `environment_definitions` owns non-secret environment metadata, immutable `team_id`, values, and optional project/task applicability. A task reference to an environment is valid only when both rows have the same `team_id` and the project/task scope applies.
- `secrets` owns each logical secret's stable identifier, immutable `team_id`, environment association, name, applicability metadata, and revocation state. It references an environment in the same team.
- `secret_versions` owns immutable encrypted versions and OpenBao key/version metadata. Every row references `secrets`; team ownership is inherited and enforced through that parent, and plaintext is never stored.
- `audit_entries` owns append-only, team-scoped audit records containing `team_id`, actor, action, resource, `request_id`, outcome, and timestamp without plaintext values.
- `task_control_requests` owns append-only operator controls, references a task in the same team, and uses an idempotency key scoped to `(team_id, task_id, operator_id, action)`.
- The normalized relationships include `teams 1:N executors`, `teams 1:N tasks`, `teams 1:N environment_definitions`, `teams 1:N secrets`, `executors 1:N executor_events`, `executors 1:N tasks`, `tasks 1:N task_events`, `tasks 1:N task_control_requests`, `environment_definitions 1:N secrets`, and `secrets 1:N secret_versions`. Child ownership is inherited from and constrained to the parent team; no child can be reparented across teams.

## Tenant Assumptions and Boundaries

- A task, Executor, environment, secret, and operator authentication context each belong to exactly one team. Multi-team contexts and cross-team resource sharing are not part of this change.
- Team provisioning and membership resolution occur outside State Registry. This change defines no team CRUD or membership UI. `v0006-web-ui` may bootstrap one team initially, while `v0007-auth` supplies verified operator team claims.
- There is no project-level RBAC. Project and task scopes limit where a team-owned environment or secret applies; they do not establish authorization independent of `team_id`.
- There is no Router, separate broker, or Env Registry in the planned architecture.
- State Registry owns durable task intake, the immutable task lifecycle event log, projected task state, atomic start approvals, assignments, Executor self events, team-owned environment metadata, team-owned encrypted secret values and version history, controls, and access audit records.
- State Registry does not run workloads, decide global scheduling, or enforce or validate Executor capacity. `max_capacity` and `running_count` are observations, not gating conditions.
- Executors own runtime lifecycle and local capacity enforcement. They decide when to discover and when to request approval.
- A dispatched task is not automatically returned to discovery after Executor failure; an explicit audited same-team recovery decision is required.
- Plaintext secrets exist only in memory while serving an authorized open-environment response and are never returned to API Gateway.
- OpenBao Transit remains the cryptographic key service. Tenant isolation is enforced by State Registry ownership and authorization before any OpenBao operation; OpenBao ciphertext and key metadata do not replace team checks.
- The State Registry is the sole issuer and verifier of open-environment scope tokens. It maintains a documented active key window for signing keys whose HMAC algorithm is allow-listed to `HS256`, `HS384`, or `HS512`: each `key_id` identifies a server-controlled key, retired keys SHALL be accepted only for the documented overlap period after rotation, and key material SHALL be loaded from a secure configuration source and SHALL NOT be persisted alongside token material or logs. Token issuance happens on atomic task approval; the protected-header `kid` SHALL equal the payload `key_id`, `expiry` SHALL be strictly later than `issued_at`, `expiry - issued_at` SHALL NOT exceed five minutes, and `issued_at` SHALL satisfy `issued_at <= server_now + 30 seconds`. Re-issuance after a transition that invalidates a token SHALL require a fresh approval response and SHALL NOT reuse the prior `key_id`-signed envelope.
