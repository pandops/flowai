# Change: v0002-state-registry

## Why

FlowAI needs one durable, tenant-isolated source of truth before work can be executed. Tasks arriving from Jira listeners, webhooks, CI integrations, and future event listeners must be recorded once for the authorized team before an Executor from that same team can see them. The same service must preserve team-owned assignments, events, environment definitions, encrypted secrets, audit entries, and operator controls without separate Router or Env Registry services.

The State Registry owns the only mutable projection of task and Executor state. The authoritative state is reconstructed from an immutable, ordered event log so audit, replay, and external reconciliation stay deterministic across restarts and concurrent writers. Capacity belongs to the Executor: the Registry records local observations only and never gates discovery or claim on capacity, so the platform does not couple scheduling correctness to runtime capacity bookkeeping.

State Registry persists teams, tasks, Executors, assignments, lifecycle events, team-owned environment definitions and secrets, encrypted secret versions, audit, and controls in a normalized third normal form (3NF) PostgreSQL schema. The immutable `team_id` is the canonical authorization and ownership boundary. `team_name` is display and audit context only and never participates in authorization. Each domain entity lives in its own table, non-key attributes depend on the whole key, and foreign keys express and enforce team ownership without transitive redundancy.

The revised contract introduces three admin-only `/admin/*` endpoints for team, source-system, and task-type creation, requires `default_image` at team registration, replaces the earlier unimplemented v0002-draft atomic `approvals` endpoint with atomic FIFO `claim` (the `/approvals` endpoint was never accepted into `openspec/specs/` and is not a baseline State Registry endpoint), replaces ingestion-time `dispatched` lifecycle semantics with pending-before-claim plus a first `created` event on claim, replaces the OpenBao Transit secret-at-rest story with a local AES-256-GCM provider that records opaque `key_id` / `key_version` envelopes (so a future change can swap providers), and codifies Executor ownership `scope` as `team` or `system` with conditional team predicates. Image resolution moves to a four-level precedence chain (`tasks.image` -> `task_types.default_image` -> `source_systems.default_image` -> always-required `teams.default_image`) that ALWAYS resolves because the team default is required at registration; the Executor no longer carries a local fallback image. A source system identity belongs to exactly one team (a correction to the earlier "independence by source-system identity across teams" framing), and the opaque `listener_identity` reference is globally unique across `source_systems` so one listener principal maps to exactly one `(team_id, source_system_id)` pair. Dedupe uses `(team_id, source_system_id, source_id)`. Listener ingestion additionally requires `task_type_id` referencing a registered task type in the same team (`tasks.task_type_id` is non-null and constrained by `(tasks.task_type_id, tasks.team_id) = (task_types.task_type_id, task_types.team_id)`); `tasks.required_tag` is server-derived from the referenced `task_type.execution_tag` and the listener SHALL NOT submit an independently authoritative value.

## What Changes

- Add State Registry as the canonical tenant-isolated task-ingestion, task-state, assignment, history, admin-onboarding, and AES-256-GCM secret encryption service.
- Expose admin-only `POST /admin/teams`, `POST /admin/source-systems`, and `POST /admin/task-types` endpoints under an authenticated system-administrator identity. Team resources are create-only: there is no `PUT`, `PATCH`, or `DELETE` team endpoint, and no listener, Executor, or Gateway path may create or update a team. `POST /admin/teams` requires a unique `team_name` and a required opaque `default_image`. `POST /admin/source-systems` requires a `team_id` that references an existing team plus a listener identity. `POST /admin/task-types` requires a `team_id` that references an existing team and a required `execution_tag`. The State Registry SHALL NOT describe the system-administrator authentication mechanism beyond requiring the identity.
- Expose admin-only read-only `GET /admin/tags` and `GET /admin/tasks` endpoints under the same authenticated system-administrator identity. `GET /admin/tags` is a global projection of canonical task types; each entry contains EXACTLY `team_id`, `task_type_id`, and `execution_tag` (no `default_image`, no other columns) and is deterministically ordered `(team_id ASC, execution_tag ASC, task_type_id ASC)` with cursor pagination (default 50, maximum 200), supporting optional exact `team_id` and `tag` filters. `GET /admin/tasks` is a global read-only task-summary projection across every team; each entry contains EXACTLY `task_id`, `team_id`, `task_type_id`, `source_system_id`, `source_id`, `required_tag`, `current_state`, `owner_command_id`, `executor_id`, `ingested_at`, and `claimed_at` (no `image`, no `resolved_image`, no `image_source`, no `project_id`, no `environment_id`, no task payload) and is deterministically ordered `(ingested_at DESC, task_id DESC)` with cursor pagination (default 50, maximum 200), supporting optional exact `team_id`, `state`, `tag`, and `task_type_id` filters. Both endpoints reject non-admin identities before reading any row, perform no mutation to teams, task types, tasks, assignments, or events, never return task payload values, decrypted environment values, secret material, or event history, and never grant authority from cross-team tag equality. There is no `tags` table, no tag create/update/delete API, and no system-admin authentication-mechanism definition. The exact allowlists on `GET /admin/tags` and `GET /admin/tasks` do NOT change the canonical `Task` resource returned to a successful claim, to a same-team Gateway read, to a same-team Executor discovery, or to any other non-admin endpoint.
- Require every listener submission to carry exactly one immutable `team_id`, one immutable `source_system_id`, the external `source_id`, and a REQUIRED `task_type_id`. The State Registry SHALL verify that `team_id` belongs to the authenticated listener, that `source_system_id` belongs to that same team, and that `task_type_id` references a registered task type whose immutable `team_id` equals the authenticated listener's team; the registry SHALL derive `tasks.required_tag` from the referenced task type's `execution_tag` and SHALL reject any ingestion body that supplies a listener-authored `required_tag` field (whether at the top level, nested under a body wrapper, or as a request header) with `400 listener_supplied_required_tag_forbidden` without persistence or acknowledgement.
- Bind each listener and Executor service identity to exactly one authorized team; caller-supplied headers, payload fields, and `team_name` never establish authorization. Image strings are not team-owned resources; image equality or reuse carries no authority.
- Deduplicate listener retries by `(team_id, source_system_id, source_id)`. The cross-team independence wording is corrected: the same `(source_system_id, source_id)` MAY exist independently across teams only because each team registers its own source-system identity, never because one source-system identity spans teams.
- Define the task lifecycle as `pending (no event) -> created -> running -> finished | failed`. The `dispatched` state is removed; no event of that name SHALL ever exist. Ingestion commits a `pending` task with no event; the first lifecycle event `created` is appended atomically on successful claim with `executor_id = claiming_executor` and a payload meaning `task <task_id> loaded by <executor_id>`.
- Replace `POST /v1/executors/{executor_id}/approvals` with `POST /v1/executors/{executor_id}/claim`. The `/approvals` endpoint is the earlier unimplemented v0002 draft being superseded in this revision; it has never been accepted into `openspec/specs/` and is not a baseline endpoint of State Registry. The claim request carries `task_id` and the immutable `command_id`. The contract introduces `tasks.owner_command_id` (nullable before claim, set once at successful claim, immutable from claim onward). A `(task_id, command_id)` retry by the same Executor is idempotent and returns the original success; a different `command_id` for an already-claimed task receives `409 task_already_claimed`. One command MAY own many tasks; only each task is limited to one command.
- Enforce FIFO via discovery ordering `(ingested_at ASC, task_id ASC)` applied AFTER the Executor's eligibility predicate. `ingested_at` is immutable and `task_id` is the deterministic tie-breaker. A claim succeeds ONLY if the requested task is the oldest currently eligible `pending` task for that authenticated Executor inside the claim transaction; otherwise the request receives `409 older_task_must_be_claimed_first` with no mutation and no event.
- Require State Registry to persist canonical state and the immutable event log transactionally in PostgreSQL 3NF; current state is a projection derived deterministically from accepted ordered events.
- Require each task to declare exactly one required tag, exactly one immutable owning `team_id`, and exactly one immutable `ingested_at`.
- Require each Executor to register exactly one authorized tag, identity, Executor type, runtime metadata, observed `max_capacity`, observed `running_count`, and either `scope = team` (with an existing `team_id`) or `scope = system` (with `team_id = null`).
- Replace atomic same-team + same-tag approval with atomic claim that succeeds only on FIFO oldest-eligible-task-per-Executor ordering; capacity remains read-only and non-reserving.
- Require State Registry to reject invalid lifecycle transitions and every new lifecycle event whose `(occurred_at, event_id)` tuple is not strictly greater than the latest accepted same-task tuple, without appending an event or changing projected state. No `accepted_sequence` recovery override is part of this contract.
- Guarantee deterministic read ordering of accepted events by `(occurred_at ASC, event_id ASC)`, with `event_id` as the stable monotonic tie-breaker and idempotency key.
- Replace OpenBao Transit encryption with local AES-256-GCM authenticated encryption. The data key is configuration-provided (256-bit), each encryption uses a fresh random 96-bit nonce and 128-bit authentication tag, the authenticated associated data binds team identifier / logical secret identifier / version, opaque provider-neutral `key_id` / `key_version` metadata is recorded on every `secret_versions` row, startup fails closed without a configured key, every decrypt succeeds only after canonical authorization checks pass, and no plaintext, nonce bytes, ciphertext bytes, tag bytes, key material, or derived key bytes appear in logs, audit records, or error responses. The scope-token HMAC behavior is unchanged apart from replacing "zero OpenBao calls" with "zero decrypt operations". v0008 (or a future change) MAY replace the local AES-GCM provider behind the same opaque identifiers.
- Persist task events and Executor self events as separate idempotent streams, with `executor_events.executor_id NOT NULL` for every Executor self event.
- Persist normalized team ownership: `teams` owns immutable `team_id`, required `default_image`, and display metadata; `tasks`, `executors`, `environment_definitions`, `secrets`, `source_systems`, and `task_types` each belong to one team; `secret_versions` reference `secrets`; child rows inherit and enforce the owning team through foreign keys or equivalent composite constraints.
- Store team-owned Executor environment definitions and team-owned secrets with locally AES-256-GCM-encrypted, immutable secret versions. Same-team operators manage them; project and task scope restrict applicability within the team and do not grant cross-team access.
- Allow an environment definition to be either team-wide (no parent `task_id`) or task-owned (a parent `task_id` in the same team). A task-owned environment is still team-owned: its `team_id` is immutable, the parent `task_id` is constrained to a task in the same team, and only the parent task may use the definition. `secrets` rows inherit scope from the parent environment, so a secret under a task-owned environment is task-owned too.
- Open decrypted environment values only to the assigned Executor presenting a valid team-bound scope token containing `team_id`, `project_id` (required claim; nullable only when the canonical environment has no project scope), `task_id`, `environment_id`, `executor_id`, `audience`, `issued_at`, `expiry`, and `key_id`. The local AES-256-GCM decrypt operation runs only after every check passes.
- Sign every open-environment scope token with an allow-listed HMAC algorithm (`HS256`, `HS384`, or `HS512` — the "HMAC-SHA-256 or a stronger HMAC" family) using a State Registry-controlled key selected by `key_id`. Bind each token to a protected-header `kid`, a payload `key_id` that MUST equal the header `kid`, an `issued_at` whose premature tolerance is `issued_at <= server_now + 30 seconds`, an `expiry` strictly later than `issued_at` and no greater than five minutes after `issued_at`, and the literal `audience` identifier `state-registry.environment.open`. Verify the `kid`/`key_id` equality before any MAC computation, recompute the signature under the declared allow-listed algorithm and the server-side key handle, and compare it with a constant-time comparison before any other check; accept only tokens whose `key_id` falls within a documented active key window for rotation; never log token plaintext, claims, key material, or derived key bytes. The token is valid only with the authenticated assigned Executor identity, only while the referenced task is in a non-terminal state, and only while the Executor remains the assigned Executor; replay by another identity, or by the assigned Executor after terminal state or unassignment, is denied before any decrypt operation. A retry within the token TTL by the same assigned Executor MAY be allowed, but it SHALL NOT bypass canonical claim, transition, or assignment checks.
- Accept operator reads and writes only through a trusted API Gateway service identity with verified `operator_id`, `team_id`, and `request_id` context; the optional display-only `team_name` is forwarded only when the verified operator team carries one. State Registry authorizes solely with `team_id`; `team_name` is display and audit context only and its absence never weakens authorization.
- Apply the authenticated `team_id` filter before pagination, totals, counts, aggregations, and WebSocket subscription or fan-out. WebSocket frames SHALL never cross team boundaries; this is a review-blocking isolation invariant.
- Return a non-revealing `404` for foreign-team task, Executor, environment, secret, control, event, audit, source-system, or task-type identifiers and perform no mutation, event append, audit disclosure, count change, subscription side effect, or decrypt operation.
- Record audit entries with `team_id`, actor, action, resource, `request_id`, and outcome while excluding secret plaintext, decrypted environment values, nonce bytes, ciphertext bytes, authentication tag bytes, key material, and individual claim values beyond identifier-level metadata.
- Persist a REQUIRED `default_image` per team on `teams`, an OPTIONAL `default_image` per task type on `task_types`, an OPTIONAL `default_image` per source system on `source_systems`, and an OPTIONAL `image` override per task on `tasks`. Each image value is opaque to State Registry (registry repository path plus immutable digest). State Registry SHALL NOT resolve, pull, verify, mutate, or use any of them for authorization. State Registry SHALL resolve the effective image at successful claim using the precedence `tasks.image` (override) -> `task_types.default_image` (task type) -> `source_systems.default_image` (source system) -> `teams.default_image` (always required at registration, so resolution always succeeds); SHALL persist `tasks.resolved_image` and `tasks.image_source` in the same transaction that appends the first `created` event; and SHALL return `resolved_image` and `image_source` in the claim response. The Executor SHALL use `resolved_image` verbatim and SHALL NOT maintain a local fallback image. Image strings are not team-owned resources, and image equality across teams carries no authority.
- Remove Router from the planned architecture; no separate broker, queue service, or Router-owned state remains.
- Remove Env Registry from the planned architecture; all registry-owned durable state lives in State Registry.
- Replace OpenBao Transit with local AES-256-GCM authenticated encryption; a future change may introduce an external provider behind the same opaque `key_id` / `key_version` envelope.

## Tenant Assumptions

- Every task belongs to exactly one immutable team for its lifetime.
- Every Executor service identity belongs to either exactly one immutable team (`scope = team`) or to no team (`scope = system`) and registers exactly one tag. A team-owned Executor SHALL never create or update the team it binds to; only an authenticated system administrator through `POST /admin/teams` may do that.
- Every authenticated operator request context represents exactly one `operator_id` and one `team_id` and may carry `team_name` only as optional non-authoritative display and audit context.
- Teams, source systems, and task types are created only through `/admin/*` endpoints. Source systems and task types belong to one team each. A source-system identity belongs to exactly one team; cross-team access through one source-system identity is impossible.
- Project and task scopes narrow the applicability of team-owned environments and secrets; they do not create a second authorization hierarchy.
- Environment definitions and logical secrets may be scoped team-wide (default) or task-owned (parented to one task in the same team). A task-owned row is still team-owned: its `team_id` is immutable and the parent `task_id` is constrained to a task in the same team. Task ownership does not create cross-team authority, project RBAC, or a second tenant hierarchy.
- A team's `default_image` is REQUIRED at registration and immutable through any admin or operator path; corrections require a new team. A task's `image` override, a task type's `default_image`, a source system's `default_image`, and a team's `default_image` participate in image resolution only, never in authorization. Image strings are not team-owned resources; image equality between tasks in different teams is NOT tenant authority.
- Executor ownership `scope` is a registration-time choice. A team-owned Executor's discovery and claim are filtered by its single registered team; a system-owned Executor's discovery and claim are filtered by its single registered tag only, and it MAY pick up tasks from any team that uses that tag. Per-task invariants (`tasks.team_id` immutable, atomic FIFO claim, `tasks.owner_command_id` set once and immutable, scope-token binding to the parent task's `team_id`, event envelope verification against the parent task's `team_id`) are unchanged in both modes. Cross-team visibility is a documented trade-off of `scope = system`.
- The `command_id` in `POST /v1/executors/{executor_id}/claim` is supplied by the Executor and immutable from registration of the claim onward; one command MAY own multiple tasks while each task is limited to one command.

## Impact

- Change type: development
- Affected specs: `specs/state-registry/spec.md` (rewritten in full to support admin `/admin/*`, FIFO claim, `pending`/`created` lifecycle, four-level image precedence with required team default, local AES-256-GCM, source-system identity belonging to one team, and the corrected cross-team dedupe wording), `specs/executor/spec.md` (rewritten to drop `approvals`, adopt `claim`, drop local fallback, and refresh scope-conditional predicates)
- Affected ADRs: `specs/adrs.md` (rewritten in full to cover admin registration, FIFO claim, local AES-256-GCM, four-level image precedence with required team default, and the reconciliation of Executor ownership scope with task `team_id` immutability)
- Affected diagrams: `specs/diagrams/state-registry-c4-container.puml`, `specs/diagrams/state-registry-services-sequence.puml`, `specs/diagrams/state-registry-api-sequence.puml`, `specs/diagrams/state-registry-task-state-machine.puml`, `specs/diagrams/state-registry-executor-capacity-state-machine.puml`, `specs/diagrams/state-registry-image-resolution-sequence.puml` (every diagram updated; the two state-machine diagrams updated under their existing `state-machine` authorization to remove `dispatched` and old lifecycle terminology only)
- Affected test cases: 22 new E2E definitions under `specs/test-cases/` numbered contiguously after `v0002.59` (`v0002.60` through `v0002.81`) for admin team/source/task-type registration, required team `default_image`, source/task-type image precedence, shared image across teams, source_id dedupe (with corrected cross-team independence wording), FIFO discovery and claim including same-timestamp tie-break, older-task rejection, concurrent claim, idempotent same-command retry, one command owning multiple tasks, no events before claim, first `created` after claim, AES-256-GCM fail-closed / no-decrypt-on-denial, and the system-admin-only `GET /admin/tags` and `GET /admin/tasks` reads (identity enforcement and non-mutation)
- Affected code: future `state-registry/` service (3NF schema with admin tables `source_systems` and `task_types`, `tasks.ingested_at`, `tasks.owner_command_id`, `tasks.image_source`, four-level image resolution, local AES-256-GCM provider, admin endpoints), future `executor_docker_opehands/` client (FIFO claim with `command_id`, removed local fallback), and the `state-registry.openapi.yaml` schema replacements for `source_task_id` (now `source_id`), `transit_key_version` (now `key_version`), removal of `dispatched` lifecycle state, addition of `/admin/*`, `/v1/executors/{executor_id}/claim`, `TaskState` enum (`pending`, `created`, `running`, `finished`, `failed`), `ImageSource` enum (`task_override`, `task_type_default`, `source_system_default`, `team_default`), `Command`, and `Admin*` schemas
- Affected OpenAPI: `specs/openapi/state-registry.openapi.yaml` (rewritten to add admin endpoints, drop `/approvals`, drop `dispatched`, add `/claim`, required `default_image`, four-level image precedence, source_system_id / source_id dedupe, local AES-256-GCM metadata via opaque `key_id` / `key_version`, FIFO ordering, and `command_id` / `owner_command_id`)
- Superseded draft: the unimplemented standalone Env Registry proposal is preserved at `openspec/changes/archive/2026-07-14-v0003-env-registry/`; its delta specs were not synced because v0002 absorbs that ownership before implementation.
- This contract revision reconciles the proposal, design, capability deltas, proposed ADRs, diagrams, OpenAPI surface, E2E test definitions, and implementation tasks for the v0002-state-registry tenant model, including admin-only onboarding, FIFO claim, the corrected source-system identity semantics, four-level image resolution with required team default, local AES-256-GCM secret-at-rest, and team-owned versus system-owned Executor ownership scope. Runtime implementation of the State Registry service and matching Executor clients remains future work.

## Non-Goals

- Execute tasks or control Executor runtimes.
- Implement Web UI, API Gateway, user authentication, team CRUD beyond the documented `/admin/*` endpoints, or team-membership management UI in this change.
- Add project-level RBAC, project membership, cross-team sharing, cross-team task movement, or multi-team operator/Executor contexts.
- Treat `team_name`, image equality, untrusted client headers, or caller-selected tenant fields as authorization evidence.
- Add priorities, wildcard tags, tag expressions, automatic reassignment, or global scheduling optimization.
- Enforce, validate, or centrally optimize Executor capacity from State Registry; capacity remains a local Executor concern.
- Add the external cryptography provider (OpenBao Transit or otherwise) for at-rest secret encryption; this change ships local AES-256-GCM only. A future change MAY swap the provider behind the same opaque `key_id` / `key_version` envelope.
