# Test case: v0008.7-migration-is-idempotent-restart-safe

## Implements

`state-registry` — `### Requirement: State Registry migrates local-at-rest ciphertext to the active provider through a resumable per-(team_id, secret_id, version) reconciliation owned durably by State Registry in PostgreSQL`.

## Intent

Verify the migration worker's idempotency boundary: a worker
restart mid-batch resumes from the last verified checkpoint
recorded in `crypto_migration_checkpoints` keyed by
`(migration_name, team_id, secret_id, version)` inside
PostgreSQL, never re-encrypts any row whose `crypto_provider`
is already `'transit'`, never duplicates the canonical
`audit_entries` row, and produces the same final state as a
single uninterrupted run. The worker SHALL NOT consult
`audit_entries` as a source of truth; the worker's single
source of truth is `crypto_migration_checkpoints`.

## Preconditions

- The State Registry and PostgreSQL run with the v0008 binary.
- A `team-a` team-wide environment holds three logical secrets
  `secret-A`, `secret-B`, `secret-C`; each has three v0002 local
  ciphertext rows for a total of nine local rows. The canonical
  team identifier is the `team_id` of the canonical same-team
  `secrets` parent row.
- The OpenBao Transit server is reachable over mTLS; the worker
  is configured with a batch size of three rows; the secure
  runtime configuration carries the `key_id` ->
  `(mount_path, key_name)` mapping.

## Steps

1. Snapshot the persisted state of all nine rows and the
   canonical `audit_entries` rows.
2. Activate the worker; let it process exactly the first batch
   (three rows for `secret-A`); observe `crypto_provider =
   'transit'` on those three rows and observe the
   `crypto_migration_checkpoints` rows keyed by
   `(migration_name, team_id, secret_id, version)` advance
   through `state = 'in_progress'` to `state = 'verified'`;
   force-kill the worker.
3. Snapshot the persisted state, the `audit_entries` history,
   and the `crypto_migration_checkpoints` rows.
4. Restart the worker; let it run to completion; observe the
   final state.
5. Inspect the `audit_entries` history for duplicate
   `action = secret_version_migrated` rows, the
   `crypto_migration_checkpoints` rows, and the canonical
   `secret_versions` state.

## Expected outcome

- The worker resumes from the last verified checkpoint boundary
  recorded in `crypto_migration_checkpoints` after the forced
  kill; it does not re-encrypt any row whose `crypto_provider =
  'transit'`; the canonical `audit_entries` row for each
  migrated row is appended exactly once; the nine local rows
  become nine Transit rows; the worker's final state matches a
  single uninterrupted run.
- The worker checkpoint lives entirely inside PostgreSQL: the
  `crypto_migration_checkpoints` rows keyed by `(migration_name,
  team_id, secret_id, version)` advance exactly once per batch
  commit and roll back if a batch fails; the worker holds no
  in-memory-only state that survives the forced kill.
- No migrated row loses decryptability; an environment open
  with a valid scope token succeeds for every migrated row
  after step 4.
- The worker never reads the canonical `audit_entries` history
  as an authorization source or a source of truth during the
  selection or verification step.
- No plaintext, no ciphertext byte, no nonce byte, no tag
  byte, no `associated_data` value, no Transit token, no
  Transit endpoint, mount path, key name, and no raw Transit
  error body ever leaves the State Registry.
