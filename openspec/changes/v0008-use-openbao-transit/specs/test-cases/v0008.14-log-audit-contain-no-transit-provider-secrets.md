# Test case: v0008.14-log-audit-contain-no-transit-provider-secrets

## Implements

`state-registry` — `### Requirement: State Registry routes every secret write and read through a pluggable crypto provider`.

`state-registry` — `### Requirement: State Registry pins the non-revealing 404 shape to every provider failure class`.

`state-registry` — `### Requirement: State Registry records plaintext-free team audit entries`.

## Intent

Verify the v0002 plaintext-free invariant survives every v0008
provider boundary: the State Registry never logs or audits
plaintext secret values, decrypted environment values, ciphertext
bytes, nonce bytes, authentication tag bytes, key material,
derived key bytes, `associated_data` values, the Transit token,
the Transit endpoint or namespace, the Transit mount path, the
Transit `key_name`, the internal opaque `key_id` ->
`(mount_path, key_name)` mapping, the Transit ciphertext form
(v0008 pins to the documented default
`vault:v<N>:...`; the official OpenBao 2.6 public API
does not expose a configurable `version_template`), or any raw
Transit error body. Identifier-level metadata may be recorded.

## Preconditions

- The State Registry and PostgreSQL run with the v0008 binary;
  an application log and an audit capture are observable in the
  test harness.
- A Transit-encrypted secret under a `team-a` environment; a
  signed scope token; a list of simulated provider failures
  (sealed, network unavailable, ACL denied, mount absent, key
  absent, version absent, tampered ciphertext, wrong
  `associated_data`).

## Steps

1. Run a successful secret write, an environment open, a
   deployment cutover, a `state-registry crypto rotate` internal
   command, the in-process migration worker across multiple
   rows, and the failure-injection scenarios listed above;
   capture the application log and audit entries; record
   every outbound Transit call the State Registry makes.
2. Capture the network traffic at the mTLS boundaries between
   the State Registry and the Transit server for every call.
3. Apply a regex-based scanner that matches the forbidden
   payloads: v0002/v0008 plaintext patterns; v0002/v0008
   ciphertext bytes; the v0008 Transit ciphertext form (the
   documented default `vault:v<N>:...` shape since the
   official OpenBao 2.6 public API does not expose a
   configurable `version_template`); the configured Transit
   token; the configured Transit endpoint, namespace, mount
   path, and `key_name`; the internal `key_id` ->
   `(mount_path, key_name)` mapping path; and any
   `associated_data` byte sequence whose decoded value contains
   the canonical `team_id` / logical-secret-id / version
   triple.
4. Run the scanner across every captured log, audit, and
   network payload.

## Expected outcome

- The scanner reports zero matches for every forbidden payload
  class across the application log and audit capture.
- Every audit entry carries exactly the documented
  identifier-level metadata (`team_id`, `secret_id`, `version`,
  opaque `key_id`, opaque `key_version`, operation, outcome
  status class, and `request_id`).
- The application log carries no plaintext, no `associated_data`
  values, no Transit token, no Transit endpoint, namespace,
  mount path, `key_name`, no internal `key_id` ->
  `(mount_path, key_name)` mapping, no Transit ciphertext form,
  no raw Transit error body, no ciphertext byte, no nonce byte,
  no tag byte, no derived key byte, and no key material.
- Every error response body matches the non-revealing `404
  environment_unknown_or_unavailable` shape; the response is
  identical for every failure class so the endpoint cannot be
  used as a validation oracle.
- No new public HTTP endpoint was introduced by v0008 under the
  OpenAPI surface; every captured 404 came from the documented
  endpoint set.
