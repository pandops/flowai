# Test case: v0008.6-local-row-migrates-to-transit-without-persisted-plaintext

## Implements

`state-registry` — `### Requirement: State Registry migrates local-at-rest ciphertext to the active provider through a resumable per-(team_id, secret_id, version) reconciliation owned durably by State Registry in PostgreSQL`.

## Intent

Verify that the in-process migration worker converts one existing
v0002 local AES-256-GCM ciphertext row into a Transit ciphertext
row in one transaction under row-level lock, without ever
persisting, logging, auditing, or transmitting in plaintext any
value other than the verified mTLS-protected in-flight request
accepted by Transit; verify the persisted row carries the new
opaque `key_id`, `key_version`, and `crypto_provider = 'transit'`
after a successful migration step; verify the canonical
`audit_entries` row records `secret_version_migrated` with the
same plaintext-free invariant; verify the migration worker
never consults `audit_entries` as an authorization source.

## Preconditions

- The State Registry and PostgreSQL run with the v0008 binary.
- A `team-a` team-wide environment holds one logical secret
  whose one `secret_versions` row was written by v0002 and
  therefore carries `crypto_provider = 'local'`, opaque `key_id`
  / `key_version`, v0002 local ciphertext, and the v0002 local
  `associated_data` byte string `team_id=<team_id>\nsecret_id=<secret_id>\nversion=<version>\n`.
- v0008 does NOT introduce a direct `team_id` column on
  `secret_versions`; the canonical team identifier is the
  `team_id` of the canonical same-team `secrets` parent row.
- The OpenBao Transit server is reachable over mTLS and the
  State Registry is configured with the documented Transit
  configuration; the secure runtime configuration carries the
  `key_id` -> `(mount_path, key_name)` mapping.
- The in-process migration worker is started and selects the
  existing local row as one of the rows for its current batch;
  the durable `crypto_migration_checkpoints` row keyed by
  `(migration_name, team_id, secret_id, version) =
  ('local_to_transit', canonical_team_id, secret_id, version)`
  exists in `state = 'in_progress'`.

## Steps

1. Snapshot the persisted row's ciphertext, `key_id`,
   `key_version`, `crypto_provider`, `migrated_at`, the canonical
   `secrets` parent's team_id, and the canonical `audit_entries`
   row.
2. Activate the migration worker; observe its progress until
   the selected row's `crypto_provider = 'transit'` and the
   matching per-row checkpoint in
   `crypto_migration_checkpoints` (keyed by
   `(migration_name, team_id, secret_id, version)`) advances to
   `state = 'verified'`.
3. Capture a network capture during the worker's encrypt and
   decrypt calls; capture the application log, audit entries,
   and the `crypto_migration_checkpoints` content.
4. Open the same team-wide environment through the assigned
   Executor with a valid scope token and observe the response.

## Expected outcome

- The persisted row's `crypto_provider` flips from `'local'` to
  `'transit'` in one transaction under row-level lock; the row is
  never visible to a reader in an intermediate state;
  concurrent writers and readers see either the complete old
  envelope or the complete new envelope; the persisted
  ciphertext is the new Transit ciphertext whose embedded key
  version parses from the documented default
  `vault:v<N>:...` shape; the new opaque `key_id` is a non-empty
  string matching the documented pattern; the new opaque
  `key_version` is an integer `>= 1`; the row carries a fresh
  `migrated_at` timestamp; the row's `(secret_id, version)`
  identity and the canonical `secrets` parent's team ownership
  are unchanged.
- The canonical `audit_entries` row records action
  `secret_version_migrated`, outcome `accepted`, and identifier-
  level metadata (canonical `team_id` derived from the `secrets`
  parent, `secret_id`, `version`, opaque `key_id`, opaque
  `key_version`, `request_id`) only; no plaintext, no v0002
  ciphertext byte, no new Transit ciphertext byte, no
  `associated_data` value, no Transit token, no Transit
  endpoint, namespace, mount path, `key_name`, and no
  `key_id` -> `(mount_path, key_name)` mapping is present.
- The captured network payload contains the
  `POST /v1/<mount>/encrypt/<key_name>` request with the
  verified mTLS-protected in-flight plaintext (the only network
  destination for plaintext during migration); the captured
  `X-Vault-Token` header never appears in a log, audit, or
  network-capture metadata. No `audit_entries` row is consulted
  by the worker during the verification step.
- `crypto_migration_checkpoints` advances in the same
  transaction as the envelope rewrite; the checkpoint state
  remains inside PostgreSQL; the worker holds no in-memory-only
  state that survives a restart.
- Step 4 returns `200` with the decrypted value served by the
  active provider; the canonical `audit_entries` row records
  the open through the now-Transit row.
