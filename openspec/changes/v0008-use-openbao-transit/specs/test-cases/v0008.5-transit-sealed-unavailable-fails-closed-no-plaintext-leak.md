# Test case: v0008.5-transit-sealed-unavailable-fails-closed-no-plaintext-leak

## Implements

`state-registry` — `### Requirement: State Registry pins the non-revealing 404 shape to every provider failure class`.

`state-registry` — `### Requirement: State Registry routes every secret write and read through a pluggable crypto provider`.

## Intent

Verify that every documented Transit-side failure class — sealed
Transit server, Transit network unavailable, ACL denial, mount
absent, key absent, version absent — and the absence of a
`POST /v1/<mount>/rewrap/<key_name>` call path (the documented
Transit rewrap endpoint has no `associated_data` parameter and is
intentionally not used by v0008) — fails closed with the v0002
single non-revealing `404 environment_unknown_or_unavailable`
shape; no provider error body, no Transit endpoint, namespace,
mount path, `key_name`, `key_id` -> `(mount_path, key_name)`
mapping, no Transit token, and no plaintext ever leave the
State Registry. The corresponding audit entry uses the
documented `provider_xxx` outcome status class plus
identifier-level metadata only.

## Preconditions

A `team-a` task is claimed by `executor-1`; a same-team environment
holds a Transit-encrypted secret whose `crypto_provider = 'transit'`;
a signed open-environment scope token is valid under every
canonical authorization check; the test harness can stub the Transit
side to simulate each failure class.

## Steps

1. Open the environment with the valid token; record the success
   baseline.
2. Stub Transit to return the documented sealed state and observe
   the response.
3. Drop the Transit network connection and observe the response.
4. Stub Transit to return the documented ACL-denied response and
   observe the response.
5. Stub Transit to return the documented mount-not-found response
   and observe the response.
6. Stub Transit to return the documented key-not-found response and
   observe the response.
7. Stub Transit to return the documented version-not-found response
   and observe the response.
8. Capture the application log and audit entries for steps 2 through
   7.

## Expected outcome

- Step 1 returns `200` with the decrypted values in memory.
- Steps 2 through 7 each return the same non-revealing `404
  environment_unknown_or_unavailable` shape with zero plaintext
  disclosure and zero plaintext disclosure through any error
  response, audit entry, or application log.
- The audit entry uses the corresponding documented outcome status
  class (`provider_unavailable` for sealed or network failure,
  `provider_forbidden` for ACL denial, `provider_mount_unknown` for
  mount absence, `provider_key_unknown` for key absence) plus
  identifier-level metadata (`team_id`, `secret_id`, `version`,
  opaque `key_id`, operation, outcome status class, `request_id`).
- The application log and audit entries contain no Transit token,
  no Transit endpoint, namespace, mount path, key name, no raw
  Transit error body, no Transit ciphertext form, no plaintext, no
  ciphertext byte, no nonce byte, no tag byte, no `associated_data`
  value, and no derived key bytes.
- The persisted row continues to carry `crypto_provider = 'transit'`;
  a single failed decrypt never flips the row's provider marker.
