# Test case: v0008.8-dual-read-mixed-local-and-transit-rows-via-provider-marker

## Implements

`state-registry` — `### Requirement: State Registry migrates local-at-rest ciphertext to the active provider through a resumable per-(team_id, secret_id, version) reconciliation owned durably by State Registry in PostgreSQL`.

`state-registry` — `### Requirement: State Registry opens environments only for assigned same-team Executors`.

## Intent

Verify that during the migration window the State Registry serves
mixed local and Transit rows through the row's persisted
`crypto_provider` marker with no plaintext exchange between the two
providers; verify the public contract surface (response body, audit
entries, opaque `key_id` / `key_version`) is unchanged regardless of
which provider served the read.

## Preconditions

- The State Registry and PostgreSQL run with the v0008 binary.
- A `team-a` team-wide environment contains two logical secrets:
  `secret-A` whose three rows are all `crypto_provider = 'local'`
  (not yet migrated); `secret-B` whose three rows are all
  `crypto_provider = 'transit'` (already migrated).
- The OpenBao Transit server is reachable over mTLS; the local
  provider implementation is still loaded by the active runtime
  configuration.

## Steps

1. Through the assigned same-team Executor `executor-1`, open the
   environment with a valid scope token; observe the response
   covers both secrets and the audit entries record both reads.
2. Inspect the response, the audit entries, and the application
   log for any provider-side disclosure (provider name, mount
   path, key name, internal `key_id` -> `(mount_path, key_name)`
   mapping, ciphertext form, or `associated_data` value).
3. Let the in-process worker convert the three `secret-A` local
   rows to Transit rows in deterministic batches; observe the
   response covers all five secrets on a second open.

## Expected outcome

- Step 1 returns `200` with the decrypted values for both secrets
  in memory only; one set of rows is decrypted through the local
  provider, the other through the active provider; no plaintext
  crosses from one provider to another; no provider side detail
  appears in the response body, the audit entries, or the
  application log.
- Step 2 contains no provider name, no Transit endpoint, no Transit
  namespace, no Transit mount path, no Transit `key_name`, no
  internal `key_id` -> `(mount_path, key_name)` mapping, no raw
  Transit error body, no Transit ciphertext form, no
  `associated_data` value, no Transit token, no plaintext, no
  ciphertext byte, no nonce byte, no tag byte, no key material,
  and no derived key bytes beyond identifier-level metadata.
- Step 3 returns `200` with the decrypted values for all five
  secrets; the canonical `audit_entries` rows record one open per
  request; the persisted rows for `secret-A` now carry
  `crypto_provider = 'transit'` and the documented opaque `key_id`
  / `key_version`; the persisted rows for `secret-B` are unchanged.
- The non-revealing `404 environment_unknown_or_unavailable` shape
  remains the single denial response across all reads.
