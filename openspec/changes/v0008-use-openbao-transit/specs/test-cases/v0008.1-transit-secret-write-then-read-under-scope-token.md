# Test case: v0008.1-transit-secret-write-then-read-under-scope-token

## Implements

`state-registry` — `### Requirement: State Registry routes every secret write and read through a pluggable crypto provider`.

`state-registry` — `### Requirement: State Registry opens environments only for assigned same-team Executors`.

## Intent

Verify the v0008 happy path: a same-team operator stores a secret under
a team-wide environment through trusted API Gateway; the State Registry
encrypts the value through the configured OpenBao Transit engine and
records the opaque public `key_id` and `key_version`; the assigned
same-team Executor opens the environment through `GET /v1/environments/
{environment_id}/open?task_id={task_id}` and receives the decrypted
value in memory only.

## Preconditions

- A `team-a` task is claimed by authenticated `team-a` Executor
  `executor-1` (assignment `tasks.executor_id = executor-1`,
  `tasks.owner_command_id = C-1`) and references a same-team
  environment.
- An authenticated system administrator has created `team-a`
  through `POST /admin/teams`.
- The OpenBao Transit server is reachable over mTLS with a verified
  peer certificate; the State Registry is configured with a Transit
  `key_name` that has been pre-created out of band with
  `aes256-gcm96`, `deletion_allowed=false`, `exportable=false`,
  `allow_plaintext_backup=false`, `min_decryption_version=1`, and
  `min_encryption_version=1`.
- The State Registry is started with valid Transit credentials, mount
  path, key name, and verified mTLS trust anchors.
- The configured Transit key has produced exactly one ciphertext for a
  prior write under test; that ciphertext is the active `key_version`.

## Steps

1. Through Web UI and API Gateway under trusted Gateway context for
   `team-a`, create a logical secret under the team-wide environment,
   providing `name`, plaintext `value`, and the team scope.
2. Inspect the response body for the new secret and inspect the
   persisted `secret_versions` row.
3. The assigned `executor-1` calls `GET /v1/environments/
   {environment_id}/open?task_id={task_id}` with a freshly signed
   open-environment scope token issued by the State Registry and
   carried in the `X-FlowAI-Scope-Token` header.
4. Inspect the response body, the application log, and the audit
   entries that follow.

## Expected outcome

- Step 1 returns `201` with `secret_id` and a `SecretVersion` whose
  `key_id` matches `^[A-Za-z0-9][A-Za-z0-9._:-]*$` and whose
  `key_version` is an integer `>= 1`. No value, ciphertext byte,
  nonce byte, tag byte, Transit ciphertext form (`vault:v<N>:...`),
  `associated_data` value, or Transit token is present in the
  response body.
- Step 2 shows the persisted row carries `crypto_provider = 'transit'`,
  a non-empty ciphertext, the documented opaque `key_id`, the documented
  opaque integer `key_version`, and a freshly signed canonical
  `audit_entries` row with action `secret.create`, outcome `accepted`,
  and identifier-level metadata only.
- Step 3 returns `200` with `OpenEnvironmentResponse` containing the
  decrypted value in memory; no plaintext appears outside memory; no
  Transit ciphertext form, `associated_data` value, Transit token,
  Transit endpoint, mount path, key name, or raw Transit error body
  is present in the response body, audit entry, or application log.
- The persisted row's `crypto_provider`, opaque `key_id`, and opaque
  `key_version` are unchanged from step 2.
