# Test case: v0008.9-cutover-refuses-local-key-removal-until-all-rows-verified

## Implements

`state-registry` — `### Requirement: State Registry disables the local provider only after every row is verified`.

## Intent

Verify the cutover gating: the `state-registry crypto cutover`
internal command authenticated by the existing deployment
identity runs one immediate transactional consistency scan
over the canonical tables; it is accepted only when zero
`crypto_provider = 'local'` rows exist, every
`migrated_at IS NOT NULL` row has a matching `verified`
checkpoint keyed by `(migration_name, team_id, secret_id,
version)` in `crypto_migration_checkpoints` with
`verified_at >= migrated_at`, no per-row checkpoint is in
`state IN ('pending','in_progress','failed')` (the
absence of `in_progress` rows is the worker-idle proof), and
the active provider's
`GET /v1/<mount>/keys/<key_name>` succeeds; otherwise the
cutover is rejected and audited without plaintext disclosure.

## Preconditions

- The State Registry and PostgreSQL run with the v0008 binary.
- The deployment identity can sign the `state-registry crypto
  cutover` internal command.
- A `team-a` team-wide environment contains four logical
  secrets; three rows have `crypto_provider = 'transit'` and one
  row still carries `crypto_provider = 'local'`.
- v0008 does NOT introduce a separate verification-report
  table or a freshness-timestamp artifact; the cutover scan
  is the entire gate.

## Steps

1. Invoke the `state-registry crypto cutover` internal
   command; the signed deployment identity authenticates the
   call; observe the rejection response.
2. Run the in-process worker to convert the remaining local
   row to a Transit row; observe the persisted state and
   the per-row `crypto_migration_checkpoints` row keyed by
   `(migration_name, team_id, secret_id, version)` advance to
   `state = 'verified'`.
3. Invoke the cutover internal command again; observe the
   acceptance response.
4. Invoke the cutover internal command a third time after
   tampering with the canonical `secret_versions` table to
   leave one row in `'local'`; observe the rejection
   response.
5. Inspect the audit entries for the rejection and the
   success.

## Expected outcome

- Step 1 returns the documented rejection shape (a defined
  non-`200` indication that names the failing gate without
  revealing plaintext or provider detail); the audit entry
  records action `crypto.cutover`, outcome `rejected`,
  outcome status class `failed`, and identifier-level metadata
  only; no plaintext, no provider detail, and no per-row
  content appears in the response or the audit.
- Step 2 produces a single migrated row whose
  `crypto_provider = 'transit'`; the per-row checkpoint in
  `crypto_migration_checkpoints` advances to `state =
  'verified'`; the absence of `in_progress` rows is the
  worker-idle proof.
- Step 3 returns the documented acceptance indication; the
  audit entry records action `crypto.cutover`, outcome
  `succeeded`, outcome status class `accepted`, and
  identifier-level metadata only; the State Registry reloads
  with `crypto.local.enabled = false` and refuses any
  subsequent read of a row whose marker is `'local'` with the
  non-revealing `404 environment_unknown_or_unavailable`
  shape.
- Step 4 returns the documented rejection because the
  consistency scan finds at least one row in
  `crypto_provider = 'local'`; the audit entry records the
  rejection without plaintext or provider detail; no public
  HTTP endpoint is required to invoke the internal command
  at any time.
- The persisted `crypto_provider` and opaque `key_id` /
  `key_version` are unchanged for any already-migrated row
  throughout the test.
- No new public HTTP endpoint was introduced by the cutover
  under the OpenAPI surface; the OpenAPI surface for
  `/admin/*` and the documented secret / open endpoints is
  unchanged.
