# Test case: v0008.10-transit-rotation-creates-new-latest-version-new-writes-use-it

## Implements

`state-registry` — `### Requirement: State Registry rotates new writes to a new Transit key version while retaining historical AAD-bound key versions`.

`state-registry` — `### Requirement: State Registry stores team-owned secrets with immutable versions`.

## Intent

Verify that the `state-registry crypto rotate` internal
command authenticated by the deployment identity calls
`POST /v1/<mount>/keys/<key_name>/rotate` on the canonical
Transit key named in the deployment configuration. The
rotate call succeeds with no documented response body. The
canonical Transit key gains a new (latest) key version.
Subsequent encrypt calls that do not specify `key_version`
use the new latest version. Existing Transit ciphertext from
prior versions remains decryptable through the active
provider as long as `min_decryption_version` permits.
Ordinary rotation NEVER decrypts existing rows, NEVER calls
`POST /v1/<mount>/rewrap/<key_name>` (which has no
`associated_data` parameter and cannot authenticate v0008
ciphertext), and NEVER raises `min_decryption_version` past
any still-referenced version. The opaque public `key_id`
is a deployment-time stable identifier mapped to
`(mount_path, key_name)` through the secure runtime
configuration; rotate does NOT change `key_id`.

## Preconditions

- The State Registry and PostgreSQL run with the v0008 binary.
- The OpenBao Transit server is reachable over mTLS; the
  configured Transit key has been pre-created out of band
  with `aes256-gcm96`, `deletion_allowed=false`,
  `exportable=false`, `allow_plaintext_backup=false`,
  independent `min_decryption_version` and
  `min_encryption_version` floors.
- v0008 pins the implementation to the documented default
  ciphertext shape `vault:v<N>:...`; the official OpenBao
  2.6 public API does not expose a configurable
  `version_template`, so v0008 parses the documented default
  strictly.
- The canonical Transit key is at some known initial latest
  version `<N_initial>` before the test begins.
- A `team-a` team-wide environment contains one logical
  secret whose one row was written before the rotate; the
  row's persisted ciphertext embeds the documented default
  `vault:v<N_initial>:...` shape with key version
  `<N_initial>` and is decrypted normally.
- A same-team Executor `executor-1` is the assigned Executor
  for a `team-a` task that references the environment.

## Steps

1. Inspect the historical row's opaque `key_id` and
   `key_version`. Read the canonical key via
   `GET /v1/<mount>/keys/<key_name>` and record the
   `min_decryption_version` and `min_encryption_version`.
2. Open the environment with a valid scope token and
   observe the response.
3. Invoke the `state-registry crypto rotate` internal
   command signed by the deployment identity against the
   canonical key name. Observe that the rotate endpoint
   succeeds with no documented response body. Then read
   `GET /v1/<mount>/keys/<key_name>` and observe that the
   canonical key has a new latest version `<N_initial + 1>`
   and that neither `min_decryption_version` nor
   `min_encryption_version` was changed by the rotate call.
4. Store a new secret value through trusted API Gateway
   context; inspect the new `SecretVersion`.
5. Open the environment again with a valid scope token;
   observe that both the historical row and the new row
   decrypt successfully through the active provider.

## Expected outcome

- Step 1 records opaque `key_id` (resolved through the
  secure runtime configuration's `(mount_path, key_name)`
  mapping that is never exposed) and opaque `key_version =
  <N_initial>`; the row carries `crypto_provider = 'transit'`;
  the persisted ciphertext embeds the documented default
  `vault:v<N_initial>:...` shape with key version
  `<N_initial>`.
- Step 2 returns `200` with the decrypted value; the active
  `min_decryption_version` permits the read.
- Step 3 succeeds: `POST /v1/<mount>/keys/<key_name>/rotate`
  is the documented request and the documented success
  response is no body; `GET
  /v1/<mount>/keys/<key_name>` then shows the canonical
  key now lists versions that include `<N_initial + 1>` as
  the new latest; the rotate call itself did NOT change
  `min_encryption_version` and did NOT change
  `min_decryption_version`; the audit entry records action
  `crypto.rotate`, outcome `succeeded`, the previous and new
  latest version, the unchanged opaque `key_id`, and
  identifier-level metadata only.
- Step 4 records opaque `key_id` (resolved through the
  secure runtime configuration) and opaque `key_version =
  <N_initial + 1>` on the new row; the new persisted
  ciphertext embeds the documented default
  `vault:v<N_initial + 1>:...` shape; the audit entry
  records action `secret.create`, outcome `accepted`.
- Step 5 returns `200` with both decrypted values in memory
  only; the historical row's ciphertext is read by the
  active provider under its embedded older key version
  `<N_initial>` WITHOUT being re-encrypted; the new row's
  `key_version = <N_initial + 1>` matches the new latest;
  the public opaque envelopes on both rows match the
  documented pattern; the historical row's `key_version`
  and ciphertext are unchanged.
- No plaintext is ever persisted or transmitted; no
  Transit error body, no Transit token, no Transit
  endpoint, namespace, mount path, `key_name`, or
  `key_id` -> `(mount_path, key_name)` mapping ever
  appears in any audit or application log.
- No rewrap call is recorded; the State Registry does NOT
  call `POST /v1/<mount>/rewrap/<key_name>`; rotate did NOT
  raise `min_decryption_version` past any still-referenced
  version; the opaque `key_id` is unchanged.
- No new public HTTP endpoint is required to invoke rotate.
