# Test case: v0008.13-scope-token-hmac-remains-unchanged-after-transit-provider

## Implements

`state-registry` — `### Requirement: State Registry signs open-environment scope tokens with an allow-listed HMAC and a server-controlled rotating key`.

`state-registry` — `### Requirement: State Registry opens environments only for assigned same-team Executors`.

## Intent

Regression boundary: the HMAC scope-token wire format and
verification order documented in v0002 are unchanged after the
v0008 provider swap. The State Registry still uses
`HS256 / HS384 / HS512` for the compact three-part signed token;
the protected header still carries allow-listed `alg`, `kid`, and
`typ = scope-token+json`; the payload still carries `team_id`,
`project_id`, `task_id`, `environment_id`, `executor_id`,
`audience`, `key_id`, `issued_at`, and `expiry`; the verification
order still matches kid == key_id first, then MAC under
constant-time comparison, then every canonical claim, then same-
team assignment, then non-terminal task state. The active
provider boundary is unrelated to this test.

## Preconditions

- The State Registry and PostgreSQL run with the v0008 binary.
- The State Registry HMAC scope-token signing key window is
  configured; the documented active `key_id` is in effect.
- A `team-a` task is claimed by authenticated `team-a` Executor
  `executor-1` (assignment `tasks.executor_id = executor-1`,
  `tasks.owner_command_id = C-1`); a same-team environment holds
  a Transit-encrypted secret.
- The active Transit server is reachable over mTLS.

## Steps

1. Issue a freshly signed open-environment scope token from the
   State Registry; inspect its header, payload, signature, and
   the documented conditions for an authorized open.
2. Submit the token in the `X-FlowAI-Scope-Token` request header
   on `GET /v1/environments/{environment_id}/open?task_id=
   {task_id}` and observe the response.
3. Mutate each token field one at a time (header `alg`,
   header `kid`, header `typ`, payload `audience`, payload
   `key_id`, payload `issued_at`, payload `expiry`,
   payload `project_id`, payload `task_id`, signature) and
   observe the response for every mutation.
4. Replay a token after the referenced task reaches terminal
   state; observe the response.
5. Inspect the audit entries for the valid, the mutated, and the
   terminal-state replays.

## Expected outcome

- The fresh token's protected header carries the allow-listed
  `alg`, the verified `kid`, and `typ = scope-token+json`; the
  payload carries every documented claim; the signature is
  computed under the allow-listed `HS256 / HS384 / HS512`
  algorithm; the MAC verifies under constant-time comparison.
- Step 2 returns `200` with the decrypted values in memory only.
- Step 3 returns the non-revealing `404
  environment_unknown_or_unavailable` shape for every mutated
  field; the State Registry never reaches the active provider
  on any failed step.
- Step 4 returns the non-revealing `404
  environment_unknown_or_unavailable` shape with zero plaintext
  disclosure.
- The audit entries record identifier-level metadata only; the
  active Transit provider is contacted at most once per request,
  only after every canonical authorization check passes, and
  never on a denied path.
