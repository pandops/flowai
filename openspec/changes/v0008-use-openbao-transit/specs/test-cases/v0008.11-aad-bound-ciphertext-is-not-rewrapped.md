# Test case: v0008.11-aad-bound-ciphertext-is-not-rewrapped

## Implements

`state-registry` — `### Requirement: State Registry rotates new writes to a new Transit key version while retaining historical AAD-bound key versions`.

`state-registry` — `### Requirement: State Registry binds associated_data to exactly (team_id, secret_id, version)`.

`state-registry` — `### Requirement: State Registry pins the non-revealing 404 shape to every provider failure class`.

## Intent

Prove that v0008 AAD-bound ciphertext rows are NEVER sent to
`POST /v1/<mount>/rewrap/<key_name>` because the documented
Transit rewrap endpoint accepts only `ciphertext`, `context`,
`key_version`, `nonce`, `reference`, `batch_input` — and has
NO `associated_data` parameter — so rewrap cannot
authenticate a v0008 ciphertext. Ordinary `rotate` does
NOT raise `min_decryption_version` past any still-referenced
version; the historical AAD-bound rows remain bound to their
embedded older key version and continue to decrypt through
the active provider under that older version. The opaque
public `key_id` is a deployment-time stable identifier mapped
to `(mount_path, key_name)` through the secure runtime
configuration; rotate does NOT change `key_id`.

## Preconditions

- The State Registry and PostgreSQL run with the v0008 binary.
- The OpenBao Transit server is reachable over mTLS; the
  configured Transit key has been pre-created out of band
  with `aes256-gcm96`, `deletion_allowed=false`,
  `exportable=false`, `allow_plaintext_backup=false`,
  independent `min_decryption_version` (set to `1`) and
  `min_encryption_version` floors.
- v0008 pins the implementation to the documented default
  ciphertext shape `vault:v<N>:...`; the official OpenBao
  2.6 public API does not expose a configurable
  `version_template`, so v0008 parses the documented default
  strictly.
- A `team-a` team-wide environment contains two historical
  Transit rows whose persisted ciphertexts embed the
  documented default shape with key versions `<N_old_1>` and
  `<N_old_2>` (both `<= 5`, for example).
- The deployment has previously invoked
  `state-registry crypto rotate`, so the canonical Transit
  key now lists additional versions `<N_old_1 + 1>`,
  `<N_old_2 + 1>`, ..., and the new latest is some
  `<N_latest >> max(N_old_1, N_old_2)>`.
- A same-team Executor `executor-1` is the assigned
  Executor for a `team-a` task that references the
  environment.

## Steps

1. Read the canonical key via
   `GET /v1/<mount>/keys/<key_name>` and record the
   documented `min_decryption_version` and
   `min_encryption_version`.
2. Open the environment with a valid scope token; observe
   that BOTH historical rows decrypt successfully through the
   active provider with their embedded older key versions.
3. Store a new secret value through trusted API Gateway
   context; inspect the new `SecretVersion` and confirm its
   embedded key version matches the canonical key's new
   latest `<N_latest>`.
4. Inspect the captured network traffic between the State
   Registry and Transit for every call the worker makes
   during this test. Inspect the audit history. Inspect the
   application log.
5. Invoke `state-registry crypto cutover` or any other code
   path that the State Registry exposes; observe that v0008
   does NOT issue a request to
   `POST /v1/<mount>/rewrap/<key_name>` for any row.
6. Attempt an end-to-end scenario where a hypothetical
   deployment operator tries to issue a
   `POST /v1/<mount>/keys/<key_name>/config` request that
   raises `min_decryption_version` past the older key
   versions; observe that the State Registry SHALL refuse to
   issue such a request as part of v0008.

## Expected outcome

- Step 1 returns the documented JSON response; the recorded
  `min_decryption_version` is `1`; the recorded
  `min_encryption_version` is unchanged by any v0008 rotate
  invocation.
- Step 2 returns `200`; the historical rows decrypt
  successfully through the active provider without being
  re-encrypted; the response carries plaintext only in
  memory; the audit history for these opens records only
  identifier-level metadata.
- Step 3 records a new row whose persisted ciphertext
  embeds the documented default `vault:v<N_latest>:...`
  shape; the audit entry records `secret.create`, outcome
  `accepted`.
- Step 4's network-capture SHALL contain zero requests to
  `POST /v1/<mount>/rewrap/<key_name>` for any AAD-bound
  ciphertext row; the audit history SHALL contain no record
  of a rewrap call; the application log SHALL contain no
  rewrap call trace. Plaintext SHALL exist only in State
  Registry process memory between the local decrypt step
  and the active encrypt step of the migration worker (if
  any row in scope is still local); for normal open paths,
  plaintext SHALL exist only between the active provider's
  `Decrypt` response and the response serialization, and
  SHALL travel only inside the verified mTLS-protected
  in-flight Transit request.
- Step 5 confirms that the State Registry has no code path
  that issues a rewrap call. The cutover procedure is a
  transactional consistency scan over
  `crypto_migration_checkpoints` and `secret_versions`, not
  a bulk decryption or rewrap. New Transit-native rows
  written directly through the active provider carry
  `migrated_at IS NULL`, do NOT require a checkpoint row,
  and are trusted through their successful provider write
  transaction.
- Step 6 confirms that v0008 never raises
  `min_decryption_version` past a key version that is
  still referenced by an AAD-bound ciphertext row. The
  deployment procedure that retires historical versions
  requires an explicit future migration change and is out of
  scope for v0008.
- No new public HTTP endpoint is required to invoke rotate
  or cutover.
- No plaintext, no ciphertext byte, no nonce byte, no tag
  byte, no `associated_data` value, no Transit token, no
  Transit endpoint, namespace, mount path, key name, and no
  raw Transit error body ever leaves the State Registry.
